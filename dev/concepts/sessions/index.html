    Sessions¶

    A session is one conversation: its messages, the runs that answered them, every tool call with its result, and the settings it ran with. The daemon keeps each session as an append-only event log, and every client renders the session from those events.

    Trees and delegation¶

    A session you start is a root. When its agent delegates a task with delegate_subagent, the daemon creates a child session for the subagent, under the root; the subagent may delegate in turn, up to the configured depth. Together they form a session tree. Each subagent has a short handle, such as explore_1a2b3c4d, by which the agents address it: to read its result, send it a message, or stop its turn. A subagent reports every turn it finishes to its parent, and runs on whether or not the parent waits. See Delegation, Agent messaging, and the delegation tools.

    Usage, permission modes, and approvals granted "for the session tree" all apply to the whole tree; /usage shows the selected session and its tree.

    Where sessions live¶

    Sessions are stored per directory under ~/.cookie-agent/sessions/, each tree in its own folder with its subagents below it and the artifacts its tools retained. A session exists on disk from its first message. Its directory decides where it is listed: the TUI shows the sessions of the directory it was started in, and Ctrl+A in its session picker switches to every directory's; the web page lists every directory's. See Lifecycle and persistence.

    A session's directory is decided once, when it is created, after its runtimes have attached: it is the workspace of its first attachment that has one, as that runtime reported it, canonical and absolute on the runtime's machine. What a client typed never decides it, so ~/web typed in the browser and /home/ada/web sent by the TUI are one directory, listed together. A session without a workspace keeps the client's directory as the daemon resolves it, or as typed when it cannot. Subagents share their parent's directory, and sessions created before this rule keep the directory they recorded.

    Paths are stored canonical and absolute and shown short: a path of a runtime that reports its home directory reads ~ and ~/… under that home, the runtime's own and not the client's, and a path of a runtime that reports none stays absolute. See Home.

    Ownership¶

    One process writes a tree at a time. The daemon that opens a tree takes its owner.lock; another cookie process, such as a standalone TUI beside a running daemon, can read the tree but shows it as a read-only snapshot until the owner exits. Clients of one daemon share its ownership, so they all write. See Tree-scoped session ownership lock.

    History that lasts¶

    The log is a compatibility surface. Each session records the history format it was written in (currently 1); a later build reads it tolerantly, skipping what it does not know, and a build that changes the format converts older logs when it opens them, keeping the originals as events.jsonl.v<N>.bak. cookie sessions upgrade converts a directory's sessions at once. See History formats and Compatibility.

    Changing history¶

    • Revert removes a message and everything after it, subagents it started included, and puts the message back into the composer. It needs an idle session and is refused when the session gained events the client has not shown. See Revert.
    • Fork copies a session up to a message into a new, independent session. See Fork.
    • Compaction replaces older context with a summary when the context fills, or on /compact. See Compaction.
    • Delete removes a whole tree from disk: the root, its subagents, their events, and their artifacts. Only a root is deleted, after you confirm; it is refused while a session of the tree runs, while another process owns the tree, and when the root gained events since you looked. It cannot be undone. See Delete.

    What a session is bound to¶

    A session has one selection (agent, model, variant, preset) shared by every client, one permission mode for its tree, and the runtimes it attaches. A run freezes its model binding and system prompt when it starts, so changes to the configuration apply from the next run. See Agents and presets and Runtimes.

    MCP servers and ACP agents on runtimes¶

    A runtime hosts MCP servers and ACP agents on its own machine. Declare them in the runtime's mcp.servers and acp.agents tables, all in the daemon's config.toml: under [runtimes.<id>] for a template and for a runtime that dials in as <id> (a table without command), and under [runtimes.local] for the daemon's machine. MCP servers and ACP agents cover the servers and agents themselves; this page covers hosting them on a runtime.

    MCP servers¶

    The runtime process (cookie runtime serve on the remote machine, or the daemon's process for [runtimes.local]) hosts the template's mcp.servers itself, so commands, working directories, and URLs are resolved on the runtime's machine. A server's scope says how many copies run:

    • scope = "workspace" (the default): each coding instance starts its own copy for its workspace, in that workspace unless the server sets a cwd. Right for servers about a repository, such as a language server.
    • scope = "runtime": the runtime starts one copy when it starts, in its user's home directory unless the server sets a cwd, and every workspace of the runtime shares it until the runtime stops. Right for servers about the machine, such as a browser.
    [runtimes.labpc]
command = ["ssh", "-o", "BatchMode=yes", "labpc", "cookie", "runtime", "serve", "--stdio"]
startup_timeout_ms = 30000

[runtimes.labpc.mcp.servers.rust_analyzer]
command = "rust-analyzer-mcp"

[runtimes.labpc.mcp.servers.browser]
command = "npx"
args = ["-y", "chrome-devtools-mcp@latest"]
scope = "runtime"

[runtimes.local.mcp.servers.docs]
command = "docs-mcp"
    • Connecting. An instance connects every enabled workspace-scoped server before it answers the daemon, and waits for the runtime-scoped ones' first attempt, which the runtime started when it initialized without holding up its answer; so a session's first use of the instance lists their tools. startup_timeout_ms covers these first attempts; raise it for servers that start slowly. A server that fails publishes no tools, and clients viewing a session attached to the instance (any instance of the runtime, for a runtime-scoped server) get an error naming it.
    • Tools. A workspace-scoped server's tools are the instance's tools, named <server>_<tool> like any MCP tool and gated by the mcp permission. When another attachment offers the same name, they are prefixed with the attachment name like the built-in tools. A runtime-scoped server's tools are the runtime's own: a session gets them once however many of the runtime's workspaces it attaches, prefixed with the runtime ID when another tool takes the name, and they run without a workspace.
    • Drops and retries. The runtime restarts a dropped server (1 s, 2 s, 4 s) with its tools still published, and drops them when every attempt fails. A failed server is retried when a session that uses the instance is created or opened, when the instance is attached or retried (r in /runtime), and with r on the server in /mcp.
    • Status. /mcp lists the servers of every instance as <runtime> at <workspace>, a runtime-scoped server once as <runtime>, runtime-wide, and, while no instance of a connected runtime hosts it, a workspace-scoped one as <runtime>, in each workspace, which "starts with a workspace" (client protocol 1.13.0). The /runtime panels list each attachment's servers, the runtime's shared ones included, with their state, tool count, and failure, and the machines view lists every server of each connected runtime, so a runtime's servers show before any session opens a workspace of it. Each lists its tools by the server's own names, those its filters left out apart (client protocol 1.36.0). Edits to a runtime's table reach it at once (see Live changes).

    ACP agents¶

    A runtime hosts ACP agents, external coding agents that take a session's or a subagent's turns over the Agent Client Protocol (see the ACP agents spec, and the ACP agents guide for setting up Claude Code, Codex, and Gemini CLI). Declare them exactly where MCP servers go: [runtimes.local.acp.agents.<agent>] for the daemon's machine, and [runtimes.<id>.acp.agents.<agent>] for a template or a runtime that dials in.

    [runtimes.local.acp.agents.claude]
command = ["npx", "-y", "@agentclientprotocol/claude-agent-acp"]
description = "Claude Code"

[runtimes.labpc.acp.agents.codex]
command = ["npx", "-y", "@agentclientprotocol/codex-acp"]
env = { CODEX_HOME = "/home/ada/.codex" }
    Key Type Default Meaning
    command array of strings required The program and its arguments, run without a shell on the runtime's machine, in its home directory. On Windows, a bare program name also finds a .cmd or .bat launcher on PATH, such as npx's.
    env table of strings {} Variables merged over the runtime's environment.
    description string "" Shown where the agent is listed when its daemon document gives none; at most 512 bytes without control characters.
    enabled boolean true A disabled agent is listed as unavailable.
    • IDs. The table key is an agent ID (lowercase letters, digits, and single inner hyphens) and the agent's ID: [runtimes.local.acp.agents.claude] is the agent claude. Runtimes that declare the same key offer the same agent. A daemon agent document of that ID without an acp block keeps the ID; the declarations are ignored and the configuration status says so.
    • Which runtime runs it. A session runs the agent on the one runtime it attaches that offers it. With none, or with two, the agent cannot run in that session: creating the session, starting a run, or delegating is refused, saying which runtimes offer it, and a session that runs an ACP agent cannot attach a second runtime that offers it. See Which runtime runs it.
    • Availability. An agent of local or of a template is available whenever the daemon runs, since the daemon starts its runtime on demand; an agent of a runtime that dials in is available while that runtime is connected, and listed as unavailable while it is away.
    • The daemon-side document. Cookie settings come from the agent document of its ID, ~/.cookie-agent/agents/<agent>.md, shared by every runtime that offers it, whose acp block marks it as the agent's (see ACP agent documents). Without one the agent has mode all, the first offering runtime's description, and the default rules.
    • Changes. A changed acp table reaches a connected runtime at once: it starts the new agents, stops the removed ones, and reports the change.
    • Processes. Each agent runs one process per runtime, shared by its sessions, started on its first turn and stopped after [acp] idle_shutdown_ms with no turn in progress, with its runtime, and with the daemon.

The coding runtime’s end of the runtime protocol.

serve answers one daemon over a frame transport. It offers one capability, coding, and opens an instance of it for every workspace the daemon asks for (capability/open): the workspace’s tools and project skills. It answers runtime/context with an instance’s AGENTS.md, and prepares and executes calls of every instance concurrently. It keeps each prepared call under its prepared ID until the daemon executes or releases it, runs executions concurrently, sends their progress back with tool/progress, and tells the daemon with tool/detachable when a call reaches its detach point. Each instance hosts the template’s workspace-scoped MCP servers in its workspace, the directory a stdio server starts in unless it configures a cwd (a relative one resolves against the workspace; docs/site/specs/runtimes.md section 3): it connects them before it answers capability/open, declares their tools next to its built-in ones, reconnects dropped ones with the shared reconnect policy, and reports their status with mcp/changed and a changed tool list with capability/tools_changed. The runtime-scoped ones (scope = "runtime") run once for the runtime, in its home directory unless they configure a cwd: they start connecting when runtime/initialize is accepted, without holding up its reply, and every capability/open waits for their first attempt (which each server’s timeout_ms bounds). Their tools are the runtime’s own, outside any instance: declared with runtime/tools_changed and prepared without an instance; every configured server’s status goes out with runtime/mcp_changed. It returns on runtime/shutdown or when the transport ends, cancelling what still runs and stopping its MCP servers.

in_process_connector runs it on a task of the daemon’s own process over an in-memory frame pair; that is how the daemon’s local coding runtime runs.

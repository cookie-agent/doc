The memory folder, <data_root>/memory (docs/site/specs/memory.md section 4): its advisory lock, its first-start defaults, the machine memory folders that renaming and merging machines move, and the memory store: URLs (url), the file format and revisions (file), the limits (limits), reads, listings, and changes (store), when memories were last read (reads), search (search), the similar-memory check (similar), and the snapshot a session’s model sees (snapshot, rendered by render).

Every change to memory or to the machine registry holds MemoryLock, because two plain cookie processes are two daemons sharing one data root. Functions that change folders take the held lock as proof.

Modules§

agents
The agent memory files the daemon keeps (docs/site/specs/memory.md section 16.7): one agents/<agent>.md for every agent of the agent registries that is not internal, whose description and two keywords the daemon owns.
file
The memory file format (docs/site/specs/memory.md section 4.3, with the stamps of section 16.9.6) and revisions (section 4.4).
format
How memory reads out ages and sizes (docs/site/specs/memory.md section 16.9.4 and 16.9.7): 3 weeks, 5 days, 1.4 KB, 812 bytes. The wording lives in the protocol crate, so the clients show ages and sizes the way the model reads them.
limits
The [memory] limits as one value (docs/site/specs/memory.md sections 11 and 16.9.7): one size limit per kind of memory document, and the snapshot’s room. They are read from the configuration at each operation, so config.apply and config.reload take effect at once.
projects
The memory folders of projects (docs/site/specs/projects.md section 3): memory/projects/<name>/, which the project registry (crate::projects) moves, empties, and gives an overview memory whose description the daemon owns.
reads
When each memory was last read (docs/site/specs/memory.md section 16.9.6), kept outside the memory files in memory/.reads.json, a map from memory URL to time. A model’s memory_read and a snapshot that shows a memory whole count as reads; a client’s does not.
render
The memory snapshot’s text, which the protocol crate renders so the clients show the same turn the model reads.
search
Memory search (docs/site/specs/memory.md sections 16.9.3 and 9.3).
similar
Whether a new memory repeats one that exists (docs/site/specs/memory.md section 16.9.5). A memory a model creates is first compared with the memories in the same place: the same project, the same machine, the user categories, or the agent’s file. The comparison uses descriptions and keywords, lowercased, with filler words left out, and matches as search does (section 16.9.3): no embeddings and no model call.
snapshot
Taking a memory snapshot (docs/site/specs/memory.md section 7.1): the user categories, the run’s agent’s file, the index of the session’s machines’ memories, and the session’s project’s overview and index (docs/site/specs/projects.md section 7), each fitted to its limit on rendered text. Each memory is first filtered by the run’s memory rules (section 7.5): one they allow is shown, one they ask for is listed by URL and description only, and one they deny is left out uncounted. Every memory shown carries when it was modified, its size, and its kind’s limit (section 16.9.7); the snapshot records when it was taken, so its ages render the same every time.
store
Reading, listing, and changing memory files (docs/site/specs/memory.md sections 4 and 8, as section 16.9 amends them: stamps, size limits per kind of memory, model writes without revisions, and the similar-memory check).
url
Memory URLs (docs/site/specs/memory.md section 5) and the names they are made of (section 4.2).

    Tools¶

    This page shows each built-in tool exactly as Cookie Agent sends it to the model: its name, its description, and the JSON Schema of its parameters. Provider adapters place these three fields in their own request format but do not rewrite them. It also states each tool's contract: what a call does, its output, retention, limits, and how clients display it.

    Cookie Agent publishes tools according to the active agent's permissions and the capabilities of the selected model. Tool argument objects are strict: unknown fields and wrong types are rejected.

    A tool is sent only when the active agent has an allow or ask rule for the tool's permission. A tool whose permission is none needs no rule: it is always sent and every call is allowed. Some tools have further conditions, noted under each tool. MCP and plugin tools are described by their servers and plugins; this page covers only how clients display MCP tools.

    To see which tools a real session sent with its latest request, expand the tools block under the system prompt in the TUI transcript.

    Execution concurrency¶

    Tool providers declare whether each tool is safe to overlap with sibling calls from the same model turn through ToolSpec::concurrency. ToolConcurrency is Exclusive by default; parallel execution requires an explicit Parallel declaration.

    Tools Eligibility Coordination
    read, read_artifact, bash, webfetch, stop_background Parallel Each call owns its execution and streaming state.
    write, edit Parallel Matching prepared serialization keys serialize mutations to the same target.
    delegate_subagent Parallel Delegate admission serializes durable child reservation and session creation internally.
    send_message Parallel Message acceptance serializes guard checks and the durable append inside the recipient actor.
    MCP tools Parallel Each MCP server's service mutex serializes calls to that server; different servers can overlap.
    skill, get_subagent_result Exclusive These calls interact with session-scoped state.
    Plugin and otherwise undeclared tools Exclusive External declarations cannot currently opt in.

    All parallel-eligible calls in the turn are dispatched together without a fan-out limit. Exclusive calls run one at a time after the parallel calls have finished. Results remain associated with their tool call IDs, while terminal events are persisted in completion order.

    Tool call failures¶

    A failed tool call terminates with a failure code and a message for the model:

    Code Meaning
    execution_failed The tool ran, or tried to, and failed.
    operation_changed What the call was prepared and approved against changed before it ran, such as an MCP tool list or a restarted runtime.
    prepared_capability_lost The prepared call was lost, for example in a daemon restart between preparation and execution.
    permission_denied A permission rule denied the call.
    runtime_unavailable The runtime or MCP server that owns the tool is reconnecting or dropped during the call. The call is not retried for the model; the tool stays published while its owner reconnects.
    unsupported_platform The tool cannot run on this platform.
    invalid_url, redirect_error, timeout, transport_error, unsupported_content_type webfetch failures (see Webfetch).

    Tool display¶

    Every built-in tool describes its calls to clients as typed display blocks (the structured tool display spec). Display never enters model history: the output, title, and metadata the model reads are the same with or without it.

    • Presentation. tool_call_started.presentation carries a human title (such as Edit src/main.rs or Run `cargo test`), a hint for icons and grouping, the primary_argument shown beside the title, arguments (the call's arguments as blocks), and, for edit and write, a preview of what the call will do.
    • Results. A result's display replaces the live progress display when the call ends.
    • Diffs. edit and write show a diff with 1-based file line numbers and five lines of context on each side of each change. Changes whose context overlaps or touches share a hunk. A preview is as_of: prepare and a result as_of: execute; the two differ when the file changed between preparation and execution. A side with no lines in a hunk starts at the line before it (0 at the top of the file), as a unified diff numbers it.
    • Budget. A result's blocks share 64 KiB serialized. A block that had to be cut counts what it left out (omitted, omitted_lines, or omitted_rows) and, where its complete content exists, names it in full: an executed edit or write retains its complete diff (as unified-diff text, text/plain, named <file>.diff) and bash names its retained output. Previews and read excerpts have no full: nothing is retained when a call is prepared, and a read page is the file itself.

    The per-tool Display sections below list each tool's hint, arguments, preview, and result blocks.

    Filesystem tools¶

    read's limit must be positive. The path is resolved when the call is prepared; the content is read when it executes. A text line longer than 4 KiB is cut and ends with a [line truncated: N more bytes] marker, and a page that would exceed the result size limit stops early with a continue with offset=N note (also reported as next_offset in the metadata). Media files are checked against the size limits before they are read in full.

    write takes the file's complete content. edit requires oldString to identify one unambiguous replacement. Preparation checks the replacement against the current content so a mismatch fails before approval, but the edit itself is applied to the file's content at execution: changes made while an approval was pending are kept, and an oldString that no longer matches fails the call. Both tools publish through a staged file renamed over the target. Writes and edits that resolve to the same file share a serialization key and run one at a time, in call order, so same-file edits in one turn apply on top of each other.

    Tool results may include image, PDF, audio, or video attachments. Attachments are validated, content-addressed, and supplied to models as file parts rather than embedded in text output.

    Display¶

    Paths are shown as the call's display argument shows them: relative to the workspace, or under ~. A path relative to the workspace (a display argument, an AGENTS.md file's name) separates its components with / on every platform. An absolute path (the workspace root a runtime reports, the path in a read page, a write's or an edit's result) is spelled the platform's way; on Windows it is the canonical long form without the \\?\ verbatim prefix, which is kept only where the path needs it (longer than MAX_PATH, or naming a device such as CON). The title and display argument already name the file, so no argument block repeats the path, and an edit's or a write's new text shows in its preview diff rather than again as an argument. A diff's and an excerpt's language comes from the path's extension (rs is rust, py is python, and so on; an extension the table does not know is passed on lowercased).

    read write edit
    Hint file_read file_write file_edit
    Title Read <path> Write <path> Edit <path>
    Arguments key_value of offset and limit when the call gives them – key_value replace all: yes when set; newString as code in the path's language only when there is no preview (a call that failed to prepare)
    Preview – diff against the file preparation finds (created when there is none) diff of the edit applied to the content preparation read
    Result file_excerpt of the page (start_line is offset + 1, total_lines the file's), table (name, type) of a directory page, or media of the retained attachment diff against the text the write replaced diff built from the ranges the edit replaced
    • edit's diff comes from the replaced byte ranges, not a diff algorithm. Each replacement covers the whole lines it touches; replacements whose lines overlap (several on one line, for example) are one change, and lines oldString and newString share at either end are context. With replaceAll, each replacement is its own change, and the changes share hunks where their context overlaps.
    • write's diff is a line diff of the old and new text when both are UTF-8 of at most 1 MiB. Otherwise the diff has no hunks and counts the lines each side has (a side that is not text counts its newline-separated lines; a file that cannot be read counts none).
    • A read excerpt holds the page's lines as the output shows them, without line numbers (a cut long line keeps its [line truncated: N more bytes] marker), up to 64 KiB; the budget cuts the rest.

    Media reads¶

    When read targets an image (PNG, JPEG, GIF, WebP), PDF, audio file (MP3, WAV, Ogg, FLAC), or video container (MP4/MOV/WebM/MKV/AVI/FLV/MPEG/WMV/3GPP), the file is sniffed by content (never by extension alone), strictly validated, and retained as an attachment. Whether the attachment reaches the model depends on two checks, in order:

    1. Model capability. The selected model must declare the matching input modality in the catalog (for example image for image/png). If it does not, the call fails with a tool error naming the model and the missing capability.
    2. Family deliverability. The provider's wire API must accept the media kind either inside a tool result or in a following user turn (see the delivery matrix). If it does not, the call fails with a tool error naming the family.

    Both rejections are ordinary tool errors: the model sees the reason and can recover (for example by asking the user, or by sampling the file through bash). Size is clamped to the smaller of the model's advertised limit and the provider's inline limit (Anthropic: 7.5 MiB raw images, 10 MiB once base64-encoded; Bedrock: 3.75 MiB images, 4.5 MiB documents, ≈18.7 MiB raw video; Vertex: 7 MiB images; Gemini API: 14 MiB for any media, keeping the base64 request under its 20 MiB cap; other families: 20 MiB images, PDFs, and audio, or 25 MiB video). Media goes in the tool result when the family's wire API accepts it there; otherwise, when the API accepts that kind in user messages, it is sent as a file in one emitted user turn immediately after the tool result. Each model also advertises per-kind count limits, enforced per request (catalog models: 20 images, 5 PDFs, 5 audio files, and 2 videos, 1 on Bedrock). When the history holds more parts of a kind than the limit, the oldest are replaced in the outgoing request by a placeholder such as [image omitted: over the model's per-request image limit]; the saved history keeps them. The elided count grows in steps of half the limit, so later media appends to an unchanged prompt prefix (and prompt cache) until the limit is reached again, at the cost of sending as few as half the limit's parts right after a step. The latest user message is never elided: a request fails only when that message alone attaches more parts than the limit. Media parts do not contribute to context fit estimates, except video, which carries a flat conservative cost.

    Before the count applies, every file part in the outgoing request that the attempt's model cannot take is replaced by a placeholder: user attachments, tool results' attachments, and emitted user messages alike. That covers a session that moved to another model, and a fallback to a model without the kind. A part fits when the model accepts its kind and media type within its byte limit, in a user turn for user and emitted messages and in a tool result for a tool result's attachment (the delivery matrix). The placeholder says why, for example [image omitted: acme/text-model does not accept images (screenshot.png, 471 KB)], [image omitted: acme/model does not accept image/webp (…)], [image omitted: larger than the 3.8 MB acme/model accepts (…)], or [image omitted: acme/model does not accept images in tool results (…)]. It depends only on the history and the model, so the prompt prefix stays cacheable; the saved history keeps the files.

    MCP media blocks (images, audio, embedded resource blobs) follow the same gate and delivery selection. Blob resources without a declared MIME type are retained under the sniffed type. Results that would exceed the combined attachment budget keep what fits and degrade the rest to inline notes. The MCP wire format cannot author arbitrary additional messages.

    Media does not survive context pressure. Tool-output elision removes the parent result and all of its emitted messages as one unit, and compaction checkpoints drop attachments. The model can re-read the source file to recover it.

    bash takes one complete command. It is background-capable: the host adds background (default false), and the timeout applies in the background too, so a command that keeps running, such as a dev server, needs timeout: 0. The command's standard input is empty: tools take no input while they run. Standard output and standard error are streamed separately during execution and retained as separate artifacts for the terminal result.

    The command runs in its own session and process group (a job object on Windows). When the shell exits, whatever it left in that group is killed, so cmd & and nohup cmd & do not outlive the call; only a process that leaves the group, such as one started with setsid, does.

    A bash call reaches its detach point as soon as its command runs; its detach note is Process <pid>. In the background it keeps its timeout and process-group cleanup.

    Display¶

    bash
    Hint shell
    Title Run `<command>`, the whole command on one line; clients cut it to the width they have
    Arguments the command as code in sh
    Preview –
    Result one terminal block: stdout and stderr segments in the order they were read, with exit_code

    Terminal text keeps SGR colour sequences (ESC [ … m); every other escape sequence and control character but newline and tab is removed. An escape sequence split across two reads of a pipe is held until it is whole. Live progress appends each chunk to block 0 with its stream, so the live display is the same terminal block as it grows. The block holds at most 64 KiB of output: the rest, and whatever the display budget cuts, is counted in omitted_lines, and a cut block's full names the call's retained output: the first declared stream (stdout, then stderr) that outgrew its preview and was kept as an artifact. When neither stream was kept (both fit their previews), the model's output holds everything and full is absent.

    A call looks like {"url":"https://docs.quantumcookie.xyz/", "raw":false}. The URL must start with a lowercase http:// or https:// prefix; any other scheme is rejected with invalid_url before a request is sent. One permission check uses the initial URL including its query string. Without a matching rule the call is denied. Explicit ask rules still use the normal approval flow.

    Output starts with four header lines (final_url, status_code, content_type, and truncated), followed by a blank line and the text body verbatim. Body newlines are physical newlines, not JSON escapes. Structured url, final_url, status_code, content_type, and truncated fields remain in result metadata. HTML (text/html or application/xhtml+xml) is rendered by html2text at width 80 unless raw is true. Text types, JSON, XML, JavaScript, form data, and +json/+xml types pass through as text; raw and non-HTML text use UTF-8 lossy decoding. Binary types are rejected, including in raw mode. Missing or invalid Content-Type is treated as application/octet-stream and rejected.

    The request has a 30-second overall timeout, inherits environment proxies, and uses reqwest's default redirect policy (10 hops). Redirect hops are not permission-checked. HTTP error statuses are returned with their text bodies. There are no additional SSRF, host/IP, DNS, or userinfo checks.

    Downloads are streamed to a fixed 16 MiB cap, or 4 MiB for HTML that is converted to text. Over-cap responses return the fetched prefix with truncated: true, not an error. The caps have no input or configuration parameter. Full results use the standard event log and result store. The standard Bounded policy retains oversized output and sends a preview to the model. read_artifact pages the retained header and body by physical line; its zero-based offset 5 starts at the body. Follow next_offset for successive pages. Metadata is separate and is not paged.

    Errors distinguish invalid_url, redirect_error, timeout, transport_error, and unsupported_content_type (which names the content type). permission_denied uses the standard policy-denial path and its structured tool_denied reason.

    Background calls¶

    A tool that declares background support (bash, delegate_subagent, and a runtime's own tools that declare it) can run in the background, as the background tool calls spec describes:

    • The host owns the argument. It adds background (a boolean, defaulting to the tool's background_default) to the tool's schema and removes it before the tool prepares the call, so the tool never sees it and an approval covers the call either way.
    • Detaching. A call the model starts with background: true, or one the user moves to the background (run.tool_background; the TUI's background button), detaches once the tool reaches its detach point. A call that finishes first returns as an ordinary result. Detaching commits an immediate result for the call, Started in the background as job job_1a2b3c4d. … or User manually moved this call to the background; it is still running as job job_1a2b3c4d. …, ending with Stop it with stop_background(job_1a2b3c4d). and followed by the tool's note, and the run goes on. Cancelling the run no longer reaches the call.
    • Reporting. When the call ends, the engine accepts one producer message owned by tool { tool_call_id } that steers into the active run or wakes the idle session: <background_result job="…" tool="…" status="…"> wrapping exactly what the foreground result would have said, its output previewed with a read_artifact hint into the retained output for anything omitted. status is completed, failed, or stopped. The call reports only after its immediate result is committed; a revert past the call, deleting its session, or the daemon stopping kills it without a report.
    • Stopping. stop_background (job) stops a background call of the session tree and returns once it has ended; it needs no permission and is published only while a background-capable tool is. A user stops one with session.background.stop. Either way the call still reports, with status="stopped" and a first line saying who stopped it.
    • Subagents report themselves. A delegate_subagent call in the background, or moved there, gets no job: its immediate result names the subagent's handle, and every turn the subagent finishes reports to the parent as a <subagent_report handle="…" status="…"> producer message owned by subagent { session_id }, keyed by the turn's run ID so it reports once. A foreground call's first turn is its tool result instead. The subagent's running turn lists among the parent's background calls under its handle, and stop_background with the handle cancels that turn (status="cancelled"; an idle subagent is an error). Cancelling the parent's run does not reach its subagents: a foreground call it was waiting on ends cancelled with the detach note, and the subagent reports its turn as if the call had been moved to the background.

    Retained tool output¶

    Tools declare ToolOutputDeclaration::Single or an ordered list of 1 to 8 named streams. Names are unique, case-sensitive ASCII path segments, 1 to 64 bytes, using letters, digits, _, -, and .; . and .. alone are forbidden. The same validator governs declarations and the stream argument of read_artifact.

    The runtime keeps bounded previews and counts of accepted text chunks in memory. A stream that fits its preview is stored nowhere else: the result output holds all of it and it has no artifact. Once a stream outgrows its preview, its bytes are buffered and written in batches to a temporary file, hashed as they are written, and published as a full artifact at completion. An artifact keeps at most the first 128 MiB of a stream; past that only the last mebibyte is kept, after a marker line counting the dropped bytes, and the stream's dropped_bytes and the result's read hint report the loss. A single output has at most one artifact; named output gets a generic manifest when any stream has an artifact, and the manifest lists every declared stream. Declaration order determines model rendering. Bash uses the same named-output interface as other tools; it does not build its own retained-output manifest.

    Each stream receives its own configured [tool_output] line/byte preview limits. Only truncated streams receive a read_artifact(artifact="<digest>", stream="<stream>", offset=...) hint, where the digest identifies the manifest. Single-output hints omit stream and the heading. A partial-line byte cut points back to that line, so readback does not skip unseen text. Aggregate preview construction also reserves 16 KiB for headings/hints inside the existing 2 MiB output bound; when necessary, previews are reduced with truthful read hints.

    ToolProgress.output carries at most 8 typed chunks and 64 KiB of authoritative text per delta. Its optional display is a delta of the live display, independent of the output: append { index, text, stream? } appends to a text (or, with a stream, a terminal) block, creating it when index is just past the list, and replace { blocks } replaces the list. The message and an append's text are each limited to 1 KiB; the runtime caps the cumulative live-display budget at 64 KiB per call, and the messages' at another 64 KiB, without stopping authoritative output. bash appends to block 0 with each chunk's stream.

    A result's display is a list of display blocks; empty means nothing to show, and a result a tool completes with ToolCompletion::single and no display shows its output as one text block. Each built-in tool's blocks are listed in its Display section, and Tool display describes the shared rules. Final display replaces live display; the daemon sanitizes its blocks, drops kinds it does not know (with a diagnostic naming the plugin or runtime that sent them), and fits the list to its own 64 KiB serialized budget, cutting a block to whole lines and counting the rest in its omitted_lines. A prepared call's presentation (its title, hint, primary argument, and display blocks of its arguments and preview) is fitted the same way. Control characters are sanitized while newlines and tabs remain usable in display text. Display is never included in model history.

    Executors return ToolCompletion: Single/Named supplies terminal output once, whereas Streamed finalizes accepted deltas without resending them. Resupplying terminal output after streaming is an error. Failures and cancellation preserve accepted output as incomplete, retain the correct terminal status, and expose the error alongside output previews to the model. Terminal events carry retained_output references and final display; replay does not recapture chunks.

    The self-paginating read, read_artifact, and get_subagent_result tools declare an absolute truncation opt-out. Their requested page is returned in full without artifact retention or truncation metadata, regardless of [tool_output]. Callers bound these results with each tool's offset/limit arguments. A requested page above the event schema's 2 MiB output limit fails with a resource-limit tool error; it is never silently truncated. The delegate_subagent terminal result also opts out, because its teaser preview is bounded by [subagent_output] instead; the owner of the delegation flow is the only place it is bounded. MCP and plugin tools remain subject to normal truncation. External opt-out would require a future extension-protocol capability and is not currently authorable.

    Artifacts are content-addressed by SHA-256, deduplicated, and newly created with mode 0600 on Unix. Their digest is verified when content is first read. A missing or corrupt artifact produces a normal tool error and does not prevent the engine or session from opening. Artifacts are written without fsync and without a store-wide lock (each publish is one atomic rename), so a crash or power loss can lose an artifact a durable event already references. Reads then report the output as unavailable, and model history replaces a lost attachment with a short note instead of failing.

    Artifacts are collected only when a session is reverted. The revert deletes the digests that the cut-away events (and any delegated children the revert deletes) referenced, directly or through a generic manifest, unless an event still in the tree's logs references them too. The sweep is skipped while any session of the tree runs or a capture is still publishing its terminal references. Artifacts orphaned any other way, such as by a crash or a cancelled capture, stay in the tree's artifacts/ directory until the tree is deleted.

    MCP tools¶

    MCP tools are shown with the hint generic, the published tool name as the title, and their arguments as one json block (none for an empty object). A result shows its text content as text (consecutive text parts as one block, joined as the output joins them), each retained image, audio, or embedded resource blob as media in place of its placeholder, and structured_content that the text does not already hold as json. structured_content also stays in the result's metadata, which the model reads.

    Goal checklist tools¶

    goal_get returns the current root goal's objective, status, revision, and entire checklist. goal_update { items } replaces the entire ordered checklist; each item contains only description and finished, with no item ID. The session actor serializes replacements, and the last accepted update wins. The tool has no goal_id or expected_revision parameter or lost-update protection. Its target is the current/latest session goal when the engine actor accepts the update, so an older run's update can intentionally affect a newly activated active or paused goal. Lifecycle changes do not change an already-admitted run's tool set. Updates reject if the current goal is absent or terminal, even when the tool remains in an admitted run. Engine-owned goal IDs and revisions remain; SessionGoalLifecycleParams.goal_id and expected_revision apply to user lifecycle RPC controls, not model checklist updates.

    The model cannot set an objective, pause, resume, or cancel. Empty checklists preserve the active or paused lifecycle; nonempty all-finished checklists complete it even while paused. The root must verify evidence before marking items finished. Both tools return the full state without display truncation. Neither declares a permission: setting the goal is what publishes them, and they act on that goal alone, so permission rules do not govern them and every call is allowed.

    Delegation and skills¶

    Delegation tools start, inspect, and cancel owned subagent sessions. Skill tools load configured skill instructions for the current turn. Their availability and targets are derived from the frozen agent policy.

    When delegation is available, its provider also freezes the currently eligible target IDs and agent descriptions into the run's system prompt under <tool_instructions provider="builtin.delegate">. The list uses the same depth ceiling and enabled-target filtering as delegate_subagent; no section is added when no target is available.

    delegate_subagent, get_subagent_result, stop_background, and send_message address subagents by a short tree-unique handle (<agent_type>_<8 hex>, e.g. explore_1a2b3c4d) or a full session UUID. A handle is generated when the session is created and resolves only within the caller's tree; a partial handle, another tree's handle, or a fabricated value is rejected with a self-repairing error that lists the live candidates as handle — description — status plus their UUIDs. Detach notes and reports pre-wrap the handle, for example [subagent session explore_1a2b3c4d] Each time its turn ends you get a <subagent_report handle="explore_1a2b3c4d">. … and [subagent session explore_1a2b3c4d; completed; 79 lines; use get_subagent_result with session_id "explore_1a2b3c4d" for the full output]. The report previews the turn's final message per [subagent_output], with its line breaks and tabs kept and other control characters folded to spaces. A report over the limit shows its first and last lines around a marker such as [… 200 lines omitted. Read more: get_subagent_result(session_id="explore_1a2b3c4d", offset=20)]; a complete one ends in full output shown. Terminal and lifecycle results keep the UUID under the unified session_id metadata key and add handle. resume_session_id accepts the same two forms, and a terminal child woken by send_message reports as running until its new turn ends.

    Agent messaging¶

    memory_edit¶

    memory_edit(new: string, old: string, revision: string, url: string)

    Description sent to the model:

    Replace the one occurrence of `old` in a memory's body with `new`, at the revision memory_read returned. Fails when `old` occurs zero or several times; include more context to make it unique. An agent:// memory keeps the description and keywords the daemon gives it, and a project's overview its description. Never save secrets.

    Only when memory_read is sent too. A delegated run may write only its own agent's memory, agent://<agent>.

    memory_delete¶

    memory_delete(revision: string, url: string)

    Description sent to the model:

    Delete one memory at the revision memory_read returned. machine:// and project:// memories are deleted. user:// and agent:// memories cannot be deleted: for those, the call clears the body and keeps the file with its description and keywords, so the category or agent file stays.

    Only when memory_read is sent too. A delegated run may write only its own agent's memory, agent://<agent>.

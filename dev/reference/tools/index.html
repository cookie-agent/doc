    Tools¶

    This page shows each built-in tool exactly as Cookie Agent sends it to the model: its name, its description, and the JSON Schema of its parameters. Provider adapters place these three fields in their own request format but do not rewrite them. It also states each tool's contract: what a call does, its output, retention, limits, and how clients display it.

    Cookie Agent publishes tools according to the active agent's permissions and the capabilities of the selected model. Tool argument objects are strict: unknown fields and wrong types are rejected.

    A tool is sent only when the active agent has an allow or ask rule for the tool's permission. A tool whose permission is none needs no rule: it is always sent and every call is allowed. Some tools have further conditions, noted under each tool. MCP and plugin tools are described by their servers and plugins; this page covers only how clients display MCP tools.

    Execution concurrency¶

    Tool providers declare whether each tool is safe to overlap with sibling calls from the same model turn through ToolSpec::concurrency. ToolConcurrency is Exclusive by default; parallel execution requires an explicit Parallel declaration.

    Tools Eligibility Coordination
    read, read_artifact, bash, webfetch, stop_background Parallel Each call owns its execution and streaming state.
    write, edit Parallel Matching prepared serialization keys serialize mutations to the same target.
    delegate_subagent Parallel Delegate admission serializes durable child reservation and session creation internally.
    send_message Parallel Message acceptance serializes guard checks and the durable append inside the recipient actor.
    MCP tools Parallel Each MCP server's service mutex serializes calls to that server; different servers can overlap.
    skill, get_subagent_result Exclusive These calls interact with session-scoped state.
    Plugin and otherwise undeclared tools Exclusive External declarations cannot currently opt in.

    All parallel-eligible calls in the turn are dispatched together without a fan-out limit. Exclusive calls run one at a time after the parallel calls have finished. Results remain associated with their tool call IDs, while terminal events are persisted in completion order.

    Tool call failures¶

    A failed tool call terminates with a failure code and a message for the model:

    Code Meaning
    execution_failed The tool ran, or tried to, and failed.
    operation_changed What the call was prepared and approved against changed before it ran, such as an MCP tool list or a restarted runtime.
    prepared_capability_lost The prepared call was lost, for example in a daemon restart between preparation and execution.
    permission_denied A permission rule denied the call.
    runtime_unavailable The runtime or MCP server that owns the tool is reconnecting or dropped during the call. The call is not retried for the model; the tool stays published while its owner reconnects.
    unsupported_platform The tool cannot run on this platform.
    invalid_url, redirect_error, timeout, transport_error, unsupported_content_type webfetch failures (see Webfetch).

    Cancelling a run¶

    Interrupting a run (run.cancel: the TUI's Ctrl-C or double Esc, the web client's Stop or Escape, a stop signal to cookie run) cancels every call it has in the foreground at once, and each call ends as cancelled:

    • bash kills the command's whole process group (a job object on Windows) with no grace period. Output still in flight drains for at most 250 ms, so a process that left the group and holds the pipes open does not hold the call.
    • A runtime's or plugin's tool gets tool/cancel. The coding runtime and the plugin SDK drop a call that has not stopped 3 s later, a second after the engine stopped waiting for it (below).
    • An MCP tool stops waiting and sends the server notifications/cancelled for the request, as a call that reaches timeout_ms does.
    • webfetch drops its request.
    • A foreground delegate_subagent stops waiting; its subagent keeps running and reports its turn (see Background calls). Its result says so: The user interrupted this run. Subagent `<handle>` keeps running; its <subagent_report> arrives when its turn ends., followed by the handle's note.

    Every other interrupted call ends with a result that names who stopped it: Interrupted by the user before it finished. for run.cancel, and for other cancellations a wording that names their cause, such as Interrupted by engine shutdown before it finished. (background tools spec, section 14). The engine waits at most 2 s for a call to stop on its own. A call still running then ends as cancelled with ; cleanup deadline elapsed added to that result, its late result is dropped, and the run records RunCancelled without waiting further. Calls in the background belong to the session, not the run, and keep running; stop_background stops them.

    Tool display¶

    Every built-in tool describes its calls to clients as typed display blocks (the structured tool display spec). Display never enters model history: the output, title, and metadata the model reads are the same with or without it.

    • Presentation. tool_call_started.presentation carries a human title (such as Edit src/main.rs or Run `cargo test`), a hint for icons and grouping, the primary_argument shown beside the title, arguments (the call's arguments as blocks), and, for edit and write, a preview of what the call will do.
    • Results. A result's display replaces the live progress display when the call ends.
    • Diffs. edit and write show a diff with 1-based file line numbers and five lines of context on each side of each change. Changes whose context overlaps or touches share a hunk. A preview is as_of: prepare and a result as_of: execute; the two differ when the file changed between preparation and execution. A side with no lines in a hunk starts at the line before it (0 at the top of the file), as a unified diff numbers it.
    • Budget. A result's blocks share 64 KiB serialized. A block that had to be cut counts what it left out (omitted, omitted_lines, or omitted_rows) and, where its complete content exists, names it in full: an executed edit or write retains its complete diff (as unified-diff text, text/plain, named <file>.diff) and bash names its retained output. Previews and read excerpts have no full: nothing is retained when a call is prepared, and a read page is the file itself.

    The per-tool Display sections below list each tool's hint, arguments, preview, and result blocks.

    Filesystem tools¶

    read numbers lines from 1, and its offset is the 1-based line (or directory entry) to start at: offset=1, the default, is the first line, and an offset of 0 is refused. A negative offset counts back from the end: offset=-50 starts at the 50th line (or entry) from the end, so with the default limit it reads the last 50, and one reaching back past the first line starts at line 1. A file read from the end is read twice, once to count its lines. limit, 2000 lines or entries when left out, must be positive. An offset past the last line or entry is an error, except that line 1 of an empty file is an empty page. The metadata's offset is the line the page started at; the arguments keep the offset as given. The path is resolved when the call is prepared; the content is read when it executes. A text line longer than 4 KiB is cut and ends with a ... [line truncated: N more bytes] marker. A page that leaves lines or entries out ends with a continuation marker that names the 1-based offset to read next: [N more lines; continue with offset=M] (or entries for a directory) when the limit stopped it, and [page cut at the result size limit; continue with offset=M] when it would have exceeded the result size limit. The metadata reports the same offset as next_offset. Media files are checked against the size limits before they are read in full.

    memory_read and read_artifact page the same way: the same 1-based offset, the same limit and its default, the same numbering, line cut, page cap, and continuation marker (Memory tools, read_artifact).

    write takes the file's complete content and says whether it Created <path> (N bytes). or Replaced <path> (N bytes).. edit requires old_string to occur exactly once, or at least once with replace_all, and reports Edited <path>: N replacement(s).. When it occurs some other number of times, the call fails with `<old_string>` occurs N times in <path>; include more context so it occurs once or set `replace_all`, the echoed text cut to 200 characters. A path that is not there fails read and edit with <path> does not exist. All three refuse arguments they do not define. Preparation checks the replacement against the current content so a mismatch fails before approval, but the edit itself is applied to the file's content at execution: changes made while an approval was pending are kept, and an old_string that no longer matches fails the call. Both tools publish through a staged file renamed over the target. Writes and edits that resolve to the same file share a serialization key and run one at a time, in call order, so same-file edits in one turn apply on top of each other.

    Tool results may include image, PDF, audio, or video attachments. Attachments are validated, content-addressed, and supplied to models as file parts rather than embedded in text output.

    Display¶

    Paths are shown as the call's display argument shows them: relative to the workspace, or under ~. A path relative to the workspace (a display argument, an AGENTS.md file's name) separates its components with / on every platform. An absolute path (the workspace root a runtime reports, the path in a read page, a write's or an edit's result) is spelled the platform's way; on Windows it is the canonical long form without the \\?\ verbatim prefix, which is kept only where the path needs it (longer than MAX_PATH, or naming a device such as CON). The title and display argument already name the file, so no argument block repeats the path, and an edit's or a write's new text shows in its preview diff rather than again as an argument. A diff's and an excerpt's language comes from the path's extension (rs is rust, py is python, and so on; an extension the table does not know is passed on lowercased).

    read write edit
    Hint file_read file_write file_edit
    Title Read <path> Write <path> Edit <path>
    Arguments key_value of offset and limit when the call gives them – key_value replace all: yes when set; new_string as code in the path's language only when there is no preview (a call that failed to prepare)
    Preview – diff against the file preparation finds (created when there is none) diff of the edit applied to the content preparation read
    Result file_excerpt of the page (start_line is the 1-based offset, total_lines the file's), table (name, type) of a directory page, or media of the retained attachment diff against the text the write replaced diff built from the ranges the edit replaced
    • edit's diff comes from the replaced byte ranges, not a diff algorithm. Each replacement covers the whole lines it touches; replacements whose lines overlap (several on one line, for example) are one change, and lines old_string and new_string share at either end are context. With replace_all, each replacement is its own change, and the changes share hunks where their context overlaps.
    • write's diff is a line diff of the old and new text when both are UTF-8 of at most 1 MiB. Otherwise the diff has no hunks and counts the lines each side has (a side that is not text counts its newline-separated lines; a file that cannot be read counts none).
    • A read excerpt holds the page's lines as the output shows them, without line numbers (a cut long line keeps its [line truncated: N more bytes] marker), up to 64 KiB; the budget cuts the rest.

    Media reads¶

    When read targets an image (PNG, JPEG, GIF, WebP), PDF, audio file (MP3, WAV, Ogg, FLAC), or video container (MP4/MOV/WebM/MKV/AVI/FLV/MPEG/WMV/3GPP), the file is sniffed by content (never by extension alone), strictly validated, and retained as an attachment. Whether the attachment reaches the model depends on two checks, in order:

    1. Model capability. The selected model must declare the matching input modality in the catalog (for example image for image/png). If it does not, the call fails with a tool error naming the model and the missing capability.
    2. Family deliverability. The provider's wire API must accept the media kind either inside a tool result or in a following user turn (see the delivery matrix). If it does not, the call fails with a tool error naming the family.

    Both rejections are ordinary tool errors: the model sees the reason and can recover (for example by asking the user, or by sampling the file through bash). Size is clamped to the smaller of the model's advertised limit and the provider's inline limit (Anthropic: 7.5 MiB raw images, 10 MiB once base64-encoded; Bedrock: 3.75 MiB images, 4.5 MiB documents, ≈18.7 MiB raw video; Vertex: 7 MiB images; Gemini API: 14 MiB for any media, keeping the base64 request under its 20 MiB cap; other families: 20 MiB images, PDFs, and audio, or 25 MiB video). Media goes in the tool result when the family's wire API accepts it there; otherwise, when the API accepts that kind in user messages, it is sent as a file in one emitted user turn immediately after the tool result. Each model also advertises per-kind count limits, enforced per request (catalog models: 20 images, 5 PDFs, 5 audio files, and 2 videos, 1 on Bedrock). When the history holds more parts of a kind than the limit, the oldest are replaced in the outgoing request by a placeholder such as [image omitted: over the model's per-request image limit]; the saved history keeps them. The elided count grows in steps of half the limit, so later media appends to an unchanged prompt prefix (and prompt cache) until the limit is reached again, at the cost of sending as few as half the limit's parts right after a step. The latest user message is never elided: a request fails only when that message alone attaches more parts than the limit. Media parts do not contribute to context fit estimates, except video, which carries a flat conservative cost.

    Before the count applies, every file part in the outgoing request that the attempt's model cannot take is replaced by a placeholder: user attachments, tool results' attachments, and emitted user messages alike. That covers a session that moved to another model, and a fallback to a model without the kind. A part fits when the model accepts its kind and media type within its byte limit, in a user turn for user and emitted messages and in a tool result for a tool result's attachment (the delivery matrix). The placeholder says why, for example [image omitted: acme/text-model does not accept images (screenshot.png, 471 KB)], [image omitted: acme/model does not accept image/webp (…)], [image omitted: larger than the 3.8 MB acme/model accepts (…)], or [image omitted: acme/model does not accept images in tool results (…)]. A user's file has its label just before it, and the reason joins the label instead, so the model can still copy the file to a machine with transfer: [file screenshot.png, 471 KB, artifact 5f2c81d0; not shown: acme/text-model does not accept images]. It depends only on the history and the model, so the prompt prefix stays cacheable; the saved history keeps the files.

    MCP media blocks (images, audio, embedded resource blobs) follow the same gate and delivery selection. Blob resources without a declared MIME type are retained under the sniffed type. Results that would exceed the combined attachment budget keep what fits and degrade the rest to inline notes. The MCP wire format cannot author arbitrary additional messages.

    Media does not survive context pressure. Tool-output elision removes the parent result and all of its emitted messages as one unit, and compaction checkpoints drop attachments. The model can re-read the source file to recover it.

    Background calls¶

    A tool that declares background support (bash, delegate_subagent, and a runtime's own tools that declare it) can run in the background, as the background tool calls spec describes:

    • The host owns the argument. It adds background (a boolean, defaulting to the tool's background_default) to the tool's schema and removes it before the tool prepares the call, so the tool never sees it and an approval covers the call either way. An ACP agent's own subagent takes no prompts, so no result could reach it from the background: its calls always run in the foreground, and one that asks for background: true fails with a note to use its harness's own background tools.
    • Detaching. A call the model starts with background: true, or one the user moves to the background (run.tool_background; the TUI's background button), detaches once the tool reaches its detach point. A call that finishes first returns as an ordinary result. Detaching commits an immediate result for the call, Started in the background as job job_1a2b3c4d. … or User manually moved this call to the background; it is still running as job job_1a2b3c4d. …, ending with Read its output so far with `read_artifact(artifact="job_1a2b3c4d")`. Stop it with `stop_background(job="job_1a2b3c4d")`. and followed by the tool's note, and the run goes on. Cancelling the run no longer reaches the call.
    • Reading it while it runs. read_artifact takes the job ID in place of a digest. With nothing else, it returns a snapshot: a line naming the job, the call, and how long it has run, then the output so far rendered as the call's result would render it if it ended now, its omission markers naming the job (read_artifact(artifact="job_1a2b3c4d", stream="stdout", offset=21)). With a stream, offset, or limit it pages one stream of the output as it stands, the same content the finished artifact will hold, and a page of a running call ends with [job job_1a2b3c4d is still running: N lines so far]; offset=-50 reads its newest 50 lines. Once the call ends, its job ID reads the output it published, among the last 64 calls to end, until the daemon restarts; after that, the digest its <background_result> names still reads. The output is the engine's own capture, so this works for every tool that streams output, on every machine.
    • Reporting. When the call ends, the engine accepts one producer message owned by tool { tool_call_id } that steers into the active run or wakes the idle session: <background_result job="…" tool="…" status="…"> wrapping exactly what the foreground result would have said, its output previewed with a read_artifact hint into the retained output for anything omitted. status is completed, failed, or stopped. The call reports only after its immediate result is committed; a revert past the call, deleting its session, or the daemon stopping kills it without a report.
    • Stopping. stop_background (job) stops a background call of the session tree and returns once it has ended; it needs no permission and is published only while a background-capable tool is. A user stops one with session.background.stop. Either way the call still reports, with status="stopped" and a first line saying who stopped it.
    • Subagents report themselves. A delegate_subagent call in the background, or moved there, gets no job: its immediate result names the subagent's handle, and every turn the subagent finishes reports to the parent as a <subagent_report session_id="…" status="…"> producer message owned by subagent { session_id }, keyed by the turn's run ID so it reports once. A foreground call's first turn is its tool result instead. The subagent's running turn lists among the parent's background calls under its handle, and stop_background with the handle cancels that turn (status="cancelled"; an idle subagent is an error). Cancelling the parent's run does not reach its subagents: a foreground call it was waiting on ends cancelled with the detach note, and the subagent reports its turn as if the call had been moved to the background.

    Retained tool output¶

    Tools declare ToolOutputDeclaration::Single or an ordered list of 1 to 8 named streams. Names are unique, case-sensitive ASCII path segments, 1 to 64 bytes, using letters, digits, _, -, and .; . and .. alone are forbidden. The same validator governs declarations and the stream argument of read_artifact.

    The runtime keeps bounded previews and counts of accepted text chunks in memory. A stream that fits its preview is stored nowhere else: the result output holds all of it and it has no artifact. Once a stream outgrows its preview, its bytes are buffered and written in batches to a temporary file, hashed as they are written, and published as a full artifact at completion. An artifact keeps at most the first 128 MiB of a stream; past that only the last mebibyte is kept, after a marker line counting the dropped bytes, and the stream's dropped_bytes and the result's read hint report the loss. A single output has at most one artifact; named output gets a generic manifest when any stream has an artifact, and the manifest lists every declared stream. Declaration order determines model rendering. Bash uses the same named-output interface as other tools; it does not build its own retained-output manifest.

    Each stream receives its own configured [tool_output] line/byte preview limits. Only truncated streams receive a read_artifact(artifact="<digest>", stream="<stream>", offset=...) hint, where the digest identifies the manifest and offset is the 1-based line of the first line the preview left out, as read_artifact takes it. (The stream's next_offset in retained_output stays the zero-based index of that line.) Single-output hints omit stream and the heading. A partial-line byte cut points back to that line, so readback does not skip unseen text. Aggregate preview construction also reserves 16 KiB for headings/hints inside the existing 2 MiB output bound; when necessary, previews are reduced with truthful read hints.

    ToolProgress.output carries at most 8 typed chunks and 64 KiB of authoritative text per delta. Its optional display is a delta of the live display, independent of the output: append { index, text, stream? } appends to a text (or, with a stream, a terminal) block, creating it when index is just past the list, and replace { blocks } replaces the list. The message and an append's text are each limited to 1 KiB; the runtime caps the cumulative live-display budget at 64 KiB per call, and the messages' at another 64 KiB, without stopping authoritative output. bash appends to block 0 with each chunk's stream.

    A result's display is a list of display blocks; empty means nothing to show, and a result a tool completes with ToolCompletion::single and no display shows its output as one text block. Each built-in tool's blocks are listed in its Display section, and Tool display describes the shared rules. Final display replaces live display; the daemon sanitizes its blocks, drops kinds it does not know (with a diagnostic naming the plugin or runtime that sent them), and fits the list to its own 64 KiB serialized budget, cutting a block to whole lines and counting the rest in its omitted_lines. A prepared call's presentation (its title, hint, primary argument, and display blocks of its arguments and preview) is fitted the same way. Control characters are sanitized while newlines and tabs remain usable in display text. Display is never included in model history.

    Executors return ToolCompletion: Single/Named supplies terminal output once, whereas Streamed finalizes accepted deltas without resending them. Resupplying terminal output after streaming is an error. Failures and cancellation preserve accepted output as incomplete, retain the correct terminal status, and expose the error alongside output previews to the model. Terminal events carry retained_output references and final display; replay does not recapture chunks.

    The self-paginating read, read_artifact, and get_subagent_result tools declare an absolute truncation opt-out. Their requested page is returned in full without artifact retention or truncation metadata, regardless of [tool_output]. Callers bound these results with each tool's offset/limit arguments. read and read_artifact cut each line after 4 KiB and stop a page before it passes the 2 MiB output limit, ending it with the offset to read next; a get_subagent_result page above that limit fails with a resource-limit tool error. No page is silently truncated. The delegate_subagent terminal result also opts out, because its teaser preview is bounded by [subagent_output] instead; the owner of the delegation flow is the only place it is bounded. MCP and plugin tools remain subject to normal truncation. External opt-out would require a future extension-protocol capability and is not currently authorable.

    Artifacts are content-addressed by SHA-256, deduplicated, and newly created with mode 0600 on Unix. Their digest is verified when content is first read. A missing or corrupt artifact produces a normal tool error and does not prevent the engine or session from opening. Artifacts are written without fsync and without a store-wide lock (each publish is one atomic rename), so a crash or power loss can lose an artifact a durable event already references. Reads then report the output as unavailable, and model history replaces a lost attachment with a short note instead of failing.

    Artifacts are collected only when a session is reverted. The revert deletes the digests that the cut-away events (and any delegated children the revert deletes) referenced, directly or through a generic manifest, unless an event still in the tree's logs references them too. The sweep is skipped while any session of the tree runs or a capture is still publishing its terminal references. Artifacts orphaned any other way, such as by a crash or a cancelled capture, stay in the tree's blobs/ directory until the tree is deleted.

    Deferred tools¶

    On a model that loads deferred tools natively, or one deferral is attempted on (see providers for which models are), MCP and plugin tools, and the built-in groups marked deferred below, are sent deferred ([deferred_tools] sends a group up front): the model sees their names in announcements, not their definitions, until it loads them with tool_search: select:<name> loads tools by exact name, and keywords load the best matches. A loaded tool stays callable. The deferred tools spec has the details: tool rounds, announcements, and compaction.

    Every tool belongs to a group: its MCP server, its plugin, or one of the built-in providers below. Announcements list deferred tools under their group, with the group's summary the first time a round announces it; an MCP server's summary is the instructions it sends when it connects. A provider whose tools are all deferred sends its prompt sections (its <tool_instructions>, see the system prompt) with the first load of one of its tools instead of in the system prompt.

    goal_get returns the current root goal's objective, status, revision, and entire checklist. goal_update { items } replaces the entire ordered checklist; each item contains only description and finished, with no item ID. The session actor serializes replacements, and the last accepted update wins. The tool has no goal_id or expected_revision parameter or lost-update protection. Its target is the current/latest session goal when the engine actor accepts the update, so an older run's update can intentionally affect a newly activated active or paused goal. Lifecycle changes do not change an already-admitted run's tool set. Updates reject if the current goal is absent or terminal, even when the tool remains in an admitted run. Engine-owned goal IDs and revisions remain; SessionGoalLifecycleParams.goal_id and expected_revision apply to user lifecycle RPC controls, not model checklist updates.

    The model cannot set an objective, pause, resume, or cancel. Empty checklists preserve the active or paused lifecycle; nonempty all-finished checklists complete it even while paused. The root must verify evidence before marking items finished. Both tools return the full state without display truncation. Neither declares a permission: setting the goal is what publishes them, and they act on that goal alone, so permission rules do not govern them and every call is allowed.

    Delegation and skills¶

    Delegation tools start, inspect, and cancel owned subagent sessions. Skill tools load configured skill instructions for the current turn. Their availability and targets are derived from the frozen agent policy.

    When delegation is available, its provider also freezes the currently eligible target IDs and agent descriptions into the run's system prompt under <tool_instructions provider="builtin.delegate">. The list uses the same depth ceiling and enabled-target filtering as delegate_subagent; no section is added when no target is available.

    delegate_subagent, get_subagent_result, stop_background, and send_message address subagents by a short tree-unique session ID (<agent_type>_<8 hex>, e.g. explore_1a2b3c4d; the tools' texts call it the session ID, the docs sometimes its handle) or a full session UUID. It is generated when the session is created and resolves only within the caller's tree; a partial ID, another tree's, or a fabricated value is rejected with a self-repairing error that lists the live candidates as id — description — status plus their UUIDs. Detach notes and reports pre-wrap it, for example [subagent session explore_1a2b3c4d] Each time its turn ends you get a <subagent_report session_id="explore_1a2b3c4d">. … and [subagent session explore_1a2b3c4d; completed; 79 lines; use `get_subagent_result(session_id="explore_1a2b3c4d")` for the full output]. The report previews the turn's final message per [subagent_output], with its line breaks and tabs kept and other control characters folded to spaces. A report over the limit shows its first and last lines around a marker such as [… 200 lines omitted. Read more: get_subagent_result(session_id="explore_1a2b3c4d", offset=21)]; a complete one ends in full output shown. Terminal and lifecycle results keep the UUID under the unified session_id metadata key and add handle. resume_session_id accepts the same two forms, and a terminal child woken by send_message reports as running until its new turn ends.

    In a root session with the global runtime attached, delegate_subagent also takes capabilities: the runtime capabilities the child works through, each written <runtime_id>/<capability_id> with a workspace when the capability takes one (see Delegating to runtimes). It is required when the root has nothing but global attached, optional when it has other attachments too, and absent everywhere else, where a child inherits its parent's attachments. Each runtime it names is checked as delegate@<runtime>, and every runtime starts before the child is created: one that cannot start fails the call and creates nothing. A root with only global is told in its system prompt that no machine is attached (runtimes).

    Memory tools¶

    The memory tools search, read, and change the memories the global runtime keeps; see Memory.

    They follow the filesystem tools where they can. memory_read pages a memory's body as read pages a file: under the metadata header, the body's lines numbered from 1, a 1-based offset (default 1, a negative one counting back from the end), a limit (default 2000), the same 4 KiB line cut, page cap, continuation marker, and error for an offset past the last body line. memory_write reports Created <url> (N bytes). or Replaced <url> (N bytes)., memory_edit Edited <url>: 1 replacement., and a memory that is not there is <url> does not exist. memory_edit takes old_string and new_string, as edit does, and preparation checks that old_string occurs exactly once in the body, so an edit that cannot apply fails before anyone is asked to approve it, with `<old_string>` occurs N times in the body of <url>; include more context so it occurs once (the echoed text cut to 200 characters). What stays different on purpose: an edit matches the body only and has no replace_all; a replacing write needs the session to have read the memory as it is now, and is refused otherwise with an operation_changed error; a bad memory URL is an invalid_url error; a delete is final; the permission actions are memory and memory_write by URL; and the write tools run one at a time.

    Cron tools¶

    The cron tools manage the daemon's scheduled prompts (cron spec). Every one but cron_list is checked under cron, with the target kind of each job it touches as a resource: session, subagent, or new; cron_update that changes a job's kind is checked for both. cron_list shows only the jobs whose kind the rules allow or ask for. A target an agent names is "self", a session below its own, or a new-session template; anything else is refused whatever the rules say. Agents never set a job's permission mode or pin its model.

    Webhook tools¶

    The webhook tools manage the daemon's webhooks (webhooks spec), URLs whose requests reach a session as <webhook_event> messages. They are the webhooks group of the global runtime, deferred by default. Every one but webhook_list is checked under webhook, with the target kind of each webhook it touches as a resource: session, subagent, or new. A root run asks by default, since a webhook opens a public URL. webhook_list shows only the webhooks whose kind the rules allow or ask for. Targets resolve as the cron tools' do. Agents never set a webhook's permission mode or pin its model, and see its secret only in the result of the call that made it.

    Asset tools¶

    Assets are files an agent gives the user (spec): charts, diagrams, HTML pages, Markdown reports, or any other file. An asset belongs to the session tree that wrote it (scope: "session", the default, deleted with the tree) or to its project (scope: "project", kept in the project's assets, or the shared store of sessions in no project). The model names an asset by its handle, such as asset_3f9a1c2e. Writing an asset again replaces it; there are no versions.

    The tools are checked under the asset action, whose resource is what a call does: read (read_asset, list_assets, and an <attach asset=…/> tag), write (write_asset), or delete (delete_asset). Assets have no owner: a rule applies the same to every asset a session can see. share_link is checked under its own action, share.

    write_asset¶

    Save a file as an asset, a file you give the user, or replace an asset you saved before.

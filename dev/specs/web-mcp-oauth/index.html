    MCP OAuth from the web client¶

    Status: implemented (2026-10-21), in client protocol 1.11.0; section 7 records how it landed. It closes the one parity gap the web client spec left open ("MCP OAuth, whose redirect must reach a loopback listener").

    1. Goal and scope¶

    The protocol already splits OAuth between client and daemon:

    • the daemon holds the PKCE verifier and exchanges the code;
    • the client gives mcp.auth.begin a redirect_uri, and hands the URL the browser lands on to mcp.auth.complete.

    The TUI binds a loopback listener for this (OAuthCallbackListener). The web client cannot, and the daemon accepts only loopback redirects, so the web client has no sign-in for MCP servers.

    This spec lets the web client use its own page as the redirect. It covers both the daemon serving the page and the page hosted anywhere else.

    Out of scope: model-provider sign-ins. Providers whose client IDs are fixed to a localhost redirect need a device-code or paste-back flow of their own.

    2. Daemon¶

    • Redirect URIs. mcp.auth.begin accepts, besides today's loopback form:
    • https:// URIs, with a host, no user info and no fragment; any path and query are allowed;
    • http:// to a loopback IP literal or localhost, with any path and query, since the page may itself be served from loopback.

    Everything else is refused as today, with a message naming the accepted forms. - Safety. Only a client holding the token can call begin, and the code is single-use. The verifier never leaves the daemon, so a code sent to an unexpected URI cannot be exchanged by anyone else. The state check in mcp.auth.complete is unchanged. - Client registration. - With dynamic client registration, the daemon registers the redirect the flow uses. - When a stored dynamic registration was made for a different redirect, the daemon registers again instead of reusing it. - A configured client_id is used as is. If its server refuses the redirect, the error reaches the client unchanged, and the docs explain that the redirect must be allowed on the server's side. - Protocol. Accepting more values is additive, but older daemons refuse them, so this is a client protocol minor bump. The web client offers sign-in only from that minor on.

    3. Web client¶

    • The redirect is the page itself. The URI is the page's own URL with ?oauth=callback, for example https://yunhao-labserver.tail34018a.ts.net/?oauth=callback. The OAuth server appends code and state.
    • Starting. The MCP server's "Sign in" button:
    • calls mcp.auth.begin;
    • records the pending server in sessionStorage and localStorage (cookie.oauth_pending), keyed by state with a 10-minute expiry;
    • opens authorization_url in a new tab.

    If the browser blocks the new tab, it navigates the current tab instead. - Finishing. When the page loads with oauth=callback: 1. it removes code and state from the address bar at once (history.replaceState); 2. it connects as usual; 3. it calls mcp.auth.complete for the pending server with the full callback URL; 4. it shows the result, "Signed in to <server>" or the daemon's error.

    If another tab of the page started the flow, the callback tab passes the URL to that tab over a BroadcastChannel (cookie-oauth) and closes itself. The original tab completes the flow and refreshes the MCP list. With no other tab listening, the callback tab completes the flow itself. - Paste fallback. While a sign-in is pending, the MCP sheet shows "Paste the address you landed on". This covers the system browser on a phone, which on iOS does not share storage with the installed app, and any other case where the callback lands somewhere the flow cannot continue from. Pasting calls mcp.auth.complete with the pasted URL. - Cancel calls mcp.auth.cancel and clears the pending entry. - HTTPS note. When the page is on plain http at an address that is not loopback, the sheet warns that most OAuth servers refuse such redirects. It suggests tailscale serve or another HTTPS front, and links to the remote-access guide. The button stays available, since some servers allow it.

    4. Tests¶

    • Daemon: redirect validation cases. Accepted: https with a path and query, loopback http, and localhost. Refused: https with user info or a fragment, a non-loopback http, and other schemes. Also a dynamic registration redone for a new redirect, and an end-to-end flow against the existing mock OAuth server with an https-style redirect.
    • Web, browser suite: against a mock OAuth server in the scenario daemon's config, three flows:
    • sign in through a new tab with the BroadcastChannel handoff;
    • sign in in the same tab;
    • the paste fallback.

    Also check that the address bar is cleaned and that a stale or mismatched state is refused.

    • The web guide: signing in to MCP servers.
    • The MCP page: web sign-in, the redirect a configured client must allow, and HTTPS.
    • The protocol changelog: the minor bump.
    • The web-client spec: the parity line updated.

    None.

    7. Implementation notes (2026-10-21)¶

    Implemented as specified, in client protocol 1.11.0. The daemon side is client_redirect_uri and is_callback_for in crates/mcp/src/oauth.rs; the page's rules are crates/web/src/oauth.rs, its calls crates/web/src/workspace/oauth.rs, and its version gate cookie_agent_client_state::mcp::daemon_accepts_page_redirects. Details the spec left open, and the few additions:

    • Registration per flow. The daemon never reuses a dynamic registration across sign-ins: every mcp.auth.begin clears the server's stored credential and registers a client for its own redirect. A stored registration for another redirect therefore cannot be reused, which section 2 asks for; a test pins it.
    • application_type. A dynamic registration declares native for a loopback redirect and web for an https one (OIDC Dynamic Client Registration allows only loopback or custom-scheme redirects for native clients). It used to be native always.
    • The callback's query. mcp.auth.complete also checks that the callback carries every query parameter of the redirect itself, so oauth=callback must be there. A loopback redirect no longer needs a port (section 2 allows any loopback address with any path and query).
    • The tab that started. It is the tab whose sessionStorage holds the state. The browser copies sessionStorage into a tab a script opens, so the page empties the new tab's copy; the tab that comes back is then a client of its own. The new tab is opened blank during the click and sent to the authorization URL once mcp.auth.begin answers, so popup blockers let it through. Its opener is cleared before it leaves.
    • Handoff. The callback tab posts {kind: "callback", state, url} on cookie-oauth and waits 1.5 s for {kind: "taken", state}. One channel object per page, so a tab never hears itself.
    • One sign-in per server. The daemon runs one flow per server, so a new pending entry for a server replaces an older one. A completion that fails forgets the entry only when the daemon's flow ended (a mistaken address leaves it waiting); Cancel forgets it at once.
    • Refused callbacks. A callback whose state this browser does not know (or that already finished) is not completed, and the page shows its address with Copy the address, since the address bar no longer has it: that is how the paste fallback reaches the installed app on iOS. An expired entry is forgotten and the page says to start again.
    • While waiting. The server's row says it waits and offers Open the sign-in again (mcp.auth.begin with the same redirect returns the same URL). A server's needs_auth message shows muted, not as an error; the outcome of a sign-in shows above the servers.
    • Tests. The browser suite's mock is scripts/web-e2e/mock-oauth.py (registration, an authorization endpoint that approves at once and refuses unregistered redirects, PKCE-checked token exchange, a minimal Streamable HTTP MCP endpoint), behind three servers (oauth-tab, oauth-same, oauth-paste) in the scenario daemon's config; the scenario is mcp_sign_in. The blocked new tab is simulated with window.open returning null, and the paste flow with a stand-in tab whose URL the scenario follows itself. The HTTPS warning is checked at a non-loopback name that Chrome maps to the daemon's loopback.

    Held sessions: stopped and failing automatic runs¶

    Status: implemented (2026-10-26; client protocol 1.34.0, plugin protocol 1.19.0); see the implementation notes at the end.

    1. Problem¶

    A session starts runs of its own for producer messages: subagent reports, agent mail, plugin and runtime producers, cron fires into the session, and goal reminders. On 2026-10-25 a session looped: its run failed at once with a non-retryable 400, the failure released the subagent report it carried, and the next reconcile started a new run with it, about twice a second, 16,000 events in fifteen minutes. The user's Stop cancelled one run and the next started at once.

    [model_retry] bounds the retries of one model attempt inside a run; nothing bounded the runs a producer message starts. A bound alone is not enough either: an engine-made goal reminder is a new producer message, so counting failures "since the last message" lets goal mode retry forever.

    2. The rule¶

    A session is held when its automatic runs have stopped:

    • Stopped: the user cancelled its run (Stop in a client, run.cancel; user decision of 2026-10-25: Stop also stops what would start next).
    • Failing: its runs failed more than [model_retry] standard_retries times in a row (negative: never held for failures). The count is of consecutive failed runs since the last run that completed or the user's last input or resume; producer messages, goal reminders included, never reset it. Each retry before the hold waits the model retry backoff (1 s, 2 s, 4 s, ... up to backoff_ceiling_ms).

    The bound and the refusals follow the user's proposal of 2026-10-26: producers are refused while a session holds failed messages, as cron skips, and the user clears the state with a Resume in place of Send.

    A run interrupted by a daemon restart is neither: it resumes once, as now, and a failure of that run counts.

    While a session is held, nothing starts a run on its own, and nothing new is accepted for it, as a cron fire is skipped while the job's previous fire is still undelivered:

    Producer While held
    Plugin and runtime producers (producer.send) Refused with the error session_held (its reason in data); the producer may send again after a resume.
    Agent mail to the session From the session's parent: a resume (section 4). From any other agent: refused to the sender's tool call, the session is held (<reason>); it takes mail once the user or its parent resumes it.
    A cron fire into the session Skipped, recorded as skipped (session held); a skip is not a failure (cron spec section 4.4).
    A subagent's completion report Deferred, not refused: it stays with the delegation and is delivered on resume, as the engine already re-sends a report its parent has not accepted.
    Goal reminders Not made; the goal stays active and its reminders continue after a resume.

    Messages accepted before the hold stay pending in the log and go with the resume. Nothing is lost and nothing is sent until the user acts.

    3. Recording it¶

    Two additive events, so the hold survives restarts and clients show it:

    • automatic_runs_held { reason }: appended when the session becomes held. reason is open: stopped, or failing with failures (the count) and error (the last run's model error summary).
    • automatic_runs_resumed {}: appended by a resume (section 4), with the user's origin.

    The session is held while its latest of the two is automatic_runs_held. SessionMeta carries held: { reason } | null, so session lists badge it.

    4. Resuming¶

    session.resume { session_id, content? }: clears the hold (automatic_runs_resumed) and starts one run with every pending producer message and, when given, content as the user's input. The failure count starts over. Refused when the session is not held (session_not_held) or is running.

    • A plain message while held (run.start, session.input, an older client) resumes the same way: it is the user acting.
    • No discard (user decision of 2026-10-26): Resume always sends the pending messages.
    • The parent resumes a held subagent (user decision of 2026-10-26): its delegate_subagent with the child's resume_session_id, or its send_message to the child, clears the child's hold as the user's message does, with the parent's prompt or mail as the input. Only the session's own parent can; other agents in the tree are refused. A held subagent's turn reports to the parent as failed, with the hold's reason in the report (status="held"), so the parent can decide.

    5. Clients¶

    • Web: while the viewed session is held, the composer's Send and Queue buttons are replaced by Resume, which sends the composer's text, if any, with the held messages. A line in the transcript says why: Stopped by you or Failed 4 times: Anthropic request failed (400) ..., with the pending messages counted (2 messages waiting).
    • TUI: the same line; Enter in the composer resumes (the hint row says Enter resume), and a Resume button in the line, with its hover, does the same.
    • Session lists badge a held session (held).

Implementation notes (2026-10-26)<a class="headerlink" href="#9-implementation-notes-2026-10-26" title="Permanent link">¶</a></h2> <p>Where the implementation differs from the text above, this section wins.</p> <ul> <li><strong>Method name.</strong> <code>session.resume</code> already opens a session, so the resume is <code>session.held.resume { session_id }</code> → <code>{ resumed }</code>. It is idempotent: a session that is not held answers <code>resumed: false</code>, and there is no <code>session_not_held</code> error. With text in the composer, the clients send it as a normal message, which clears the hold.</li> <li><strong>Refusals reuse existing codes.</strong> A plugin's or runtime's <code>producer.send</code> gets <code>producer_rejected</code> with <em>the session is held (...)</em> as its detail, instead of a new <code>session_held</code> error, so the plugin and runtime error surfaces are unchanged. Agent mail fails with <code>send_message:recipient_held: the session is held (...)</code>.</li> <li><strong>The engine's own producers are accepted and wait.</strong> Subagent turn reports, delegation completions, background tool results, and goal controls are recorded while held and go with the resume, which the hold already guarantees. Goal reminders are not made.</li> <li><strong>A stop</strong> is a <code>run_finished</code> <code>cancelled</code> whose envelope origin is a client or the user. A cancel the engine makes (shutdown, a parent stopping its subagent) does not hold. A stop holds only when something could start a run on its own: a pending producer message, an active goal, or a live producer registration (a background call, a subagent, a plugin or runtime). With nothing such, there is nothing to hold, and the composer keeps Send.</li> <li><strong>A revert</strong> that leaves producer messages waiting from before the cut holds the session as a stop does, so the next run is the user's; what arrives later (a surviving background call's result) wakes it as before.</li> <li><strong>The failure count</strong> runs back from the latest event to the last <code>completed</code> run, <code>user_input_submitted</code>, or <code>automatic_runs_resumed</code>; <code>interrupted</code> runs are skipped, and producer messages never reset it. The held state is that walk's result, so it survives restarts.</li> <li><strong>Subagent reports keep their status.</strong> A report is rendered at the child's run end, before the hold is recorded, so it says <code>failed</code> or <code>cancelled</code> as before rather than <code>held</code>, and a hold sends no report of its own (one would wake the parent, which could undo the user's stop).</li> <li><strong>Clients.</strong> The transcript records each hold as a warning row and each resume as an info row. The web composer shows <strong>Resume</strong> in place of Send and Queue, with a <em>Held — ...</em> status line after the transcript. The TUI draws a banner on the conversation's last row with a <em>resume</em> button (<code>PointerTarget::HeldResume</code>), and Enter in an empty composer resumes. Session lists show a held session as <code>SessionActivity::Held</code>, sorted with the active ones: a pause before its title on the web (red when held for failures, <code>held: <reason></code> as its tooltip), and <code>⏸</code> in the TUI (added 2026-10-26).</li> <li><strong>Tests:</strong> <code>crates/engine/src/runtime/tests/held_sessions.rs</code> (failures to the budget and a resume, a stop, a goal that keeps failing, the parent's and a sibling's mail, the push), the cron skip in <code>tests/crons.rs</code>, the updated delegation and producer tests, <code>client_state::held</code>,

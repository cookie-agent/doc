    Runtimes: Daemon, Global Runtime, and Coding Runtimes¶

    Status: implemented (all four phases, product decisions approved 2026-10-15); the manual end-to-end check against labpc that phase 4 names passed on 2026-10-20: an ssh template and a dial-in runtime, the daemon built from 85710393d and the remote runtime from the b2ddb9e72 musl release build. This document is the governing specification for splitting tool execution and workspace context out of the engine into attachable runtimes. Section Open questions lists anything still undecided.

    The runtime capabilities spec later changed parts of this one: a runtime offers capabilities over one connection that serves every workspace (runtime protocol 5), instances are keyed by (runtime ID, capability, workspace), templates no longer substitute {workspace}, runtimes can dial in, and the daemon serves sessions of any directory. Where the two differ, that spec governs.

    1. Goal and scope¶

    Cookie Agent aims to cover both coding-agent use (opencode) and personal assistant use (openclaw). Both need the agent's tools to live somewhere other than the process that runs the model loop: a session may work in a repository on another machine, in several workspaces at once, or with no workspace at all.

    Today the daemon is a workspace. EngineOptions.cwd locates the session store, roots permission paths, resolves relative tool paths, feeds the <working_directory> prompt block, finds AGENTS.md and project skills, and selects the workspace configuration layer. The built-in tools are constructed once for that directory.

    After this work the processes split three ways:

    clients (TUI, CLI, later others)
   │  client protocol (WebSocket / in-memory)
daemon = gateway
   │  config, agents, sessions, model loop, permissions, approvals,
   │  delegation, goals, messaging, compaction, artifacts
   │  base layer tools · global runtime (in-process)
   │  runtime protocol (stdio / in-memory)
coding runtimes, one per workspace (local in-process, remote via a command)

    In scope (the milestone): the runtime seam, session attachments, the runtime protocol, and remote coding runtimes launched by command. The milestone ends when a session on the local daemon works in a repository on another machine (labpc over ssh) end to end.

    Out of scope: a persistent or discoverable daemon, runtimes that dial in, channel adapters (chat apps), schedulers and other openclaw-style triggers, web clients, and runtime kinds other than coding. Producer messages are the only notification path, and in this milestone they stayed a daemon-side plugin feature; runtime protocol 4 later opened them to runtimes (see external producers).

    2. Vocabulary¶

    Term Meaning
    Daemon Today's daemon, unchanged in process model: plain cookie runs it in-process, cookie daemon serves it over WebSocket. It is the gateway. Its working directory now only locates the session store and stamps cwd_identity.
    Base layer Tools the daemon implements itself for its own orchestration. Always present, never detachable.
    Runtime A source of tools, workspace context, and producer messages.
    Runtime kind A free-form label a runtime declares for itself in runtime/initialize, such as global or coding; templates do not declare it. The daemon only displays it: behaviour follows from what a runtime reports (its workspace, tools, and skills), never from its kind, so runtimes of new kinds need no daemon change.
    Runtime template A configured way to start runtimes: [runtimes.<id>]. The <id> is the runtime ID.
    Runtime instance A running runtime: one per (runtime ID, canonical workspace). Shared by every session attached to it.
    Attachment A durable session fact binding a session to a runtime instance under a session-unique attachment name.
    Attachment name The name the runtime instance reports for itself in runtime/initialize; used as the tool prefix on collisions. Model-facing text calls this an attachment (see the memory spec).
    Machine The computer a runtime runs on; the daemon groups runtimes into machines. Added by the memory spec.

    3. Layers¶

    Layer Runs in Tools Context
    Base layer daemon delegate_subagent, get_subagent_result, send_message, skill, goal_get, goal_update, read_artifact (new), stop_background none
    Global runtime (global) daemon process, in-process trait calls top-level [mcp] servers and [plugins], webfetch (declared Fallback), memory tools (memory spec) user skills (~/.agents/skills, ~/.cookie-agent/skills), memory snapshot
    Coding runtime (coding) built-in local instance in the daemon process; others in child processes read, write, edit, bash, webfetch, plus MCP servers from its template workspace root, platform, AGENTS.md, project skills

    Plugins exist only on the daemon, hosted by the global runtime. Hosting MCP servers is up to each runtime, not part of the runtime contract: coding runtimes host them, and a runtime that does not rejects a template that lists some. No runtime hosts plugins.

    Rules:

    • The global runtime never offers read, write, edit, or bash. Those exist only where a coding runtime is attached.
    • Every daemon always has the local coding runtime template for its own working directory. There is no flag to disable it.
    • New sessions attach global and local (the daemon's working directory) by default. A session may detach either. A session with no coding runtime is valid: it has the base layer and whatever the global runtime offers.
    • Artifact reads move from read to the base layer's read_artifact { artifact, stream?, offset, limit }, so a session with no coding runtime can still page through retained output. artifact is the 64-hex digest and stream an optional stream name; the model-facing artifact://<digest>[/<stream>] URI form is removed. Truncation hints read read_artifact(artifact="<digest>", stream="stdout", offset=…). read becomes filesystem-only. The persisted artifact://sha256/<digest> form in ArtifactReference is internal and unchanged.
    • read_artifact needs no permission rule: it can only reach the session tree's own artifacts. The read: {"artifact://*": allow} pattern and the artifact:// pass-through in permission resource resolution go away.

    4. Configuration¶

    4.1 Templates¶

    [runtimes.labpc]
command = ["ssh", "labpc", "cookie", "runtime", "coding", "--stdio", "--workspace", "{workspace}"]
env = { }                     # additions to the inherited environment
startup_timeout_ms = 10000
shutdown_grace_ms = 3000

[runtimes.labpc.mcp.servers.rust_analyzer]
command = "rust-analyzer-mcp"
    • Runtime IDs match [a-z][a-z0-9_]{0,31} because they become tool-name prefixes. global and local are reserved.
    • [runtimes.local] may exist without command; it only carries the mcp table for the built-in local coding runtime. Any other template requires a nonempty command. Templates accept no plugins table.
    • Templates do not declare a kind. The command decides what runs, and the runtime reports its kind in runtime/initialize, so there is one source of truth. The mcp table is still parsed strictly when the configuration loads; a runtime that hosts no MCP servers rejects a nonempty one at initialize.
    • A template whose command contains {workspace} needs a workspace: attach and session creation require one. A template without the placeholder takes none, and supplying one is an error.
    • {workspace} is substituted as one whole argv element, with no shell interpretation by cookie. A command that reaches a remote shell (ssh) is responsible for quoting; the reference docs must say so.
    • The child inherits the daemon's environment plus env, because ssh needs SSH_AUTH_SOCK and similar variables.
    • Template MCP servers are sent to the runtime in runtime/initialize and run on the runtime's machine. MCP OAuth stays global-runtime-only (its credential store is the daemon's mcp-oauth.json); a template server with oauth enabled fails validation. Static-header HTTP servers are allowed.
    • Top-level [mcp] and [plugins] keep their current meaning and belong to the global runtime.
    • Plugin environment changes: plugins, like MCP servers and runtimes, now inherit the daemon's environment, and env adds to it instead of replacing it. This drops today's env_clear(), so a plugin also sees provider API keys that the daemon reads from its environment.

    4.2 Removed¶

    • The workspace configuration layer: <cwd>/.cookie-agent/config.toml and <cwd>/.cookie-agent/agents/ are no longer read. Configuration is the user layer only. config_paths.workspace, workspace_mcp_servers, McpConfigTarget::WorkspaceFile, the TUI's "project config.toml" MCP target, and AgentDocumentSource::Workspace go away.
    • BuiltinTools::new(workspace): coding tools take their workspace from the runtime instance.
    • The lazy MCP server setting and the lazy-not-connected status. Every enabled server connects eagerly (section 6.4); an authored lazy key is an unknown field.

    No migration or compatibility decoder is added (see AGENTS.md). A leftover workspace file is ignored silently because it is simply never opened; the docs say so. AGENTS.md files under .cookie-agent/agents/ are context, not configuration, and keep working (section 8).

    5. Session attachments¶

    5.1 Events (additive, versionless)¶

    • RuntimeAttached { name, runtime_id, kind, workspace } where workspace is the canonical path the runtime reported (absent for global).
    • RuntimeDetached { name }.

    A session's attachment set is the fold of these events. SessionCreated stays as it is; creation writes one RuntimeAttached per initial attachment in the same append. A session whose log holds no RuntimeAttached or RuntimeDetached event at all was created before this change and is read as attached to global and local.

    5.2 Operations¶

    • Attach and detach are accepted only while the session has no active run (SessionRunning otherwise), so the set is fixed for every run.
    • Creating a session or attaching a runtime connects it eagerly (section 6.4). Attach waits for the instance to start and for runtime/initialize; failure rejects the attach and records nothing.
    • The runtime chooses its attachment name and returns it from runtime/initialize; clients do not supply one. The global runtime returns global. A coding runtime returns <runtime ID>_<workspace basename>, with the basename lowercased, every character outside [a-z0-9_] replaced by _, repeats collapsed, and the result capped at 32 bytes: labpc in ~/cookie-agent is labpc_cookie_agent. Because the name is fixed per instance, it is the same in every session that attaches that instance.
    • If a session already has an attachment with the returned name (two workspaces with the same basename), the daemon appends _2, _3, and so on for that session.
    • Delegated children inherit the parent's attachments. delegate_subagent accepts an optional runtimes list of the parent's attachment names that narrows the child's set. The child's log records its own RuntimeAttached events so the child is self-describing. Changed 2026-10-17: the runtimes argument is gone; every delegated child inherits the root session's attachments.
    • Reopening a session in a daemon that does not have its instances running (after a restart, or a session created by another daemon) connects them when the session is opened, with the same rules as creation.

    6. Tool composition¶

    The model's tool list should change as rarely as possible: every change costs the provider's prompt cache and can confuse a model that has already called a tool by name.

    6.1 Minimal change, not frozen¶

    The tool set is not frozen. As today, published_tool_definitions recomputes it on every model turn. Instead, the sources of change are reduced so that the list only changes when something really appeared or went away:

    • no lazy connections: everything a session can use is connected when the session is created or opened (section 6.4);
    • short disconnects are bridged by reconnecting before any tool is dropped (section 6.4);
    • only real collisions rename tools (section 6.3).

    What remains is the user attaching or detaching a runtime, an MCP server or runtime that cannot be reached at all, and an MCP server changing its own tool list.

    6.2 Collision enum¶

    Every runtime tool declares collision: prefix | fallback (default prefix).

    • prefix: on a collision the tool is published as <attachment>_<name>.
    • fallback: on a collision the tool is hidden. The global runtime's webfetch uses this.

    Base layer names are reserved: a runtime tool with a base name is always treated as colliding.

    6.3 Collisions¶

    Names are computed from the current tool set every time it is composed:

    • A name offered by exactly one source is published bare.
    • When several prefix tools offer one name, the bare name is removed and each of them is published as <attachment>_<name>. Attaching labpc at ~/api to a session whose local runtime is at ~/web therefore turns bash into local_web_bash and labpc_api_bash; detaching labpc turns local_web_bash back into bash.
    • A runtime tool that collides with a base layer name is published as <attachment>_<name>; the base tool keeps its name.
    • An override tool keeps the bare name, and the other tools of that name are prefixed (or hidden, if fallback). Several overrides of one name are all prefixed, with a diagnostic. An override never takes a base layer name. Each plugin composes as its own source, prefixed with the plugin's name (see the plugins spec).
    • fallback tools are hidden whenever a non-fallback tool offers the same name. When both declare the same parameters schema, as both webfetch tools do, the model sees no change.
    • A published name longer than 64 bytes is dropped with a diagnostic.
    • Delegated children compose the same way from their own attachments.

    Inside one runtime, names are unique; that runtime enforces it with today's MCP claim rules. MCP tools inside a runtime keep the <server>_<tool> form, so a prefixed one reads <attachment>_<server>_<tool>.

    6.4 Connection policy¶

    The same rules apply to MCP servers (in the global runtime and in coding runtimes) and to runtime instances.

    • Eager connect. When a session is created or opened, the daemon makes sure every attached runtime instance is started and every enabled MCP server in it has finished its connection attempt before the session's first run. Instances and servers already up are reused; the global and local instances start with the daemon.
    • Failure at connect. A server or runtime that fails to connect publishes no tools, and every client viewing the session gets an error message naming it and the reason. It is retried the next time a session that uses it is created or opened, and on demand from the /mcp or /runtime panel.
    • Disconnect. When a connected server or runtime drops, the daemon reconnects (restarting the process for stdio servers and runtimes) up to 3 times with 1 s, 2 s, and 4 s backoff. While it reconnects, its tools stay published and calls fail fast with runtime_unavailable, so a brief drop never changes the tool list. If every attempt fails, its tools are dropped and clients get an error message.

    6.4.1 Addendum 2026-10-22: MCP server scope and working directory¶

    A runtime template's MCP server takes scope = "workspace" (the default, the hosting described above) or scope = "runtime"; a top-level [mcp] server takes none and fails validation with one.

    • Start. A runtime-scoped server starts once per runtime process, when the runtime accepts runtime/initialize. The reply does not wait for it; every capability/open waits for its first attempt, bounded by its timeout_ms, and reports it before replying. It reconnects with the policy above and stops with the runtime.
    • Tools. Its tools are the runtime's own, outside any instance (runtime/tools_changed, prepared without an instance). A session composes them once per runtime, after the first attachment of that runtime, under the runtime's ID as their composition source, so a collision publishes <runtime>_<server>_<tool>; they run with an origin of the runtime without a workspace.
    • Listing. The runtime reports every configured server at initialize and with runtime/mcp_changed: the runtime-scoped ones live, the workspace-scoped ones as configured. mcp.server.list shows a runtime-scoped server once without a workspace and a workspace-scoped one no instance hosts as "starts when a workspace opens", so a connected runtime's servers are visible before any workspace opens.
    • Working directory. A stdio server without cwd starts in the instance's workspace (workspace-scoped), in the runtime user's home (runtime-scoped), or in the daemon user's home (top-level); a relative cwd resolves against the same directory. Before, it inherited the process's directory, which for a Windows runtime started by Task Scheduler is C:\Windows\System32.
    • Compatibility. Runtime protocol 1.5.0 and client protocol 1.13.0, additive. A runtime hosts every server per workspace for a daemon older than 1.5.0.

    6.5 Routing¶

    The name map resolves a published name to (attachment, runtime tool name). Preparation, permission decision, and execution keep today's sequence; Arc::ptr_eq publication checks become (attachment, instance generation, spec) equality, so a runtime restart between publication and preparation fails with the existing OperationChanged path.

    7. Permissions and approvals¶

    • Rules gain an optional runtime selector written as an action suffix in agent documents and session overlays: bash@labpc, read@local. A plain action with no selector applies on every runtime and to the base layer, so existing agent documents keep working unchanged. A qualified rule is more specific than an unqualified one at the same resource specificity.
    • The selector matches the runtime ID, not the attachment name, so it is stable across sessions.
    • Permission actions are free-form labels a tool declares ([a-z][a-z0-9_]{0,31}), so a runtime can introduce its own, such as browse. An action no rule names is denied, so a new runtime's tools stay hidden until an agent or the session overlay grants their action. The daemon gives meaning only to the actions of its own tools: read and write take file paths (${workspace_dir}, workspace-relative resources), and delegate, message, and skill belong to the base layer. Every other action matches plain wildcard patterns. A tool may also declare no permission at all (see background tool calls).
    • ${workspace_dir} and relative resources resolve against the workspace of the runtime that prepared the call. Base layer and global tools have no workspace; path-relative patterns never match them.
    • Approval grants and tree grants record the runtime ID. A grant only applies to calls on the same runtime ID. Grant events written before this change have no runtime ID and are read as local.
    • The approval classifier's prompt names the runtime and its workspace instead of "the workspace".

    7.1 Addendum 2026-10-22: the mcp default¶

    An action no rule names stays denied and hidden, with the mode default of list_runtimes (runtime delegation spec section 4) as the exception. mcp joins it: when an agent document, the synthesized built-in default included, has no mcp key in any form (mcp@<runtime> included), the daemon supplies mcp: {"*": ask} for the primary, all, and subagent modes; internal agents get none.

    Mode mcp
    primary, all, subagent "*": ask
    internal none
    • A declared mcp key replaces the default entirely, as for list_runtimes: an agent with only "my_chrome_*": ask is offered only those tools, and mcp: deny hides them all. A key with only a runtime selector counts as declared, so mcp@labpc: allow leaves the other runtimes' MCP tools hidden.
    • The default rule is part of the frozen agent snapshot like the others, so tool visibility, call evaluation, and approvals treat it as any rule. A snapshot frozen before this change has no default and keeps its rules.
    • session.permission.get and the session preview report an action whose agent rules are exactly its mode default with the source default (the list_runtimes default too, which was reported as agent_document before); the TUI's and the web client's /permissions panels show it so. No wire change: default is an existing PermissionRuleSource value. A document that spells out the default rule itself reads the same.
    • The same day the memory actions lost their mode defaults (memory spec section 9.2, note of 2026-10-22): memory and memory_write are denied unless the agent document or the session overlay names them. Later that day they gained defaults chosen by whether the run is delegated, not by mode (memory spec section 16.9.11), which the view reports with the source default as well.

    8. Workspace context¶

    At admission, for each attached coding runtime, the daemon asks the runtime for its context (runtime/context):

    • Workspace block. <working_directory> is replaced by one <runtimes> block listing each attachment's name, kind, workspace, platform, and whether its tools are prefixed. It is frozen like today's block. Changed 2026-10-17: global is left out; with one other runtime the prompt gives only its working directory and platform, and with several it lists them and each of their tools' descriptions names its runtime (see System prompt).
    • AGENTS.md. The admission request carries the run's preset. Each coding runtime applies today's lookup to its own workspace: the preset's .cookie-agent/agents/<preset>/AGENTS.md, else .cookie-agent/agents/AGENTS.md, then <workspace>/AGENTS.md, under the existing size rule. Presets themselves are still defined only by the daemon's user layer. AgentMdLoaded gains an attachment field; one event per runtime that returned a file. Replay and compaction pinning treat the latest event per attachment as current.
    • Skills. The global runtime contributes user skills; each coding runtime contributes project skills found from its repository root down to its workspace (today's discovery, run on the runtime's machine). Bodies and the supporting-file sample travel in the context reply; ${COOKIE_SKILL_DIR} expands to the absolute path on the runtime's machine. Project skills shadow user skills as today. Same-named project skills from two attachments follow the prefix rule. A skill's allowed-tools grants apply to the tools of the attachment that contributed it; user skills' grants are unqualified.

    Skills are read once when an instance initializes, matching today's "no hot reload". AGENTS.md is read at every root admission, as today.

    9. Runtime protocol¶

    JSON-RPC 2.0, one message per line over stdio, or frames over an InProcessStream. The protocol version is an integer starting at 1 and must match exactly; a mismatch fails initialize with both versions in the diagnostic. The local coding runtime speaks this protocol over the in-memory transport so the local and remote paths are one code path. The global runtime does not; it is called in-process through the same Rust trait.

    Method Direction Purpose
    runtime/initialize daemon → runtime Version, runtime ID, requested workspace (when the template takes one), and settings: tool_output and agent_md limits and the template's MCP servers. A runtime rejects settings it does not support. Reply: version, kind, attachment name, and tool declarations and skills; when they apply, canonical workspace and platform.
    runtime/tools_changed runtime → daemon Tool list changed; the daemon re-lists before the next model turn (section 6.1).
    runtime/context daemon → runtime Per-admission context for the run's preset: AGENTS.md.
    tool/prepare daemon → runtime Name, arguments, session, run, turn context. Reply: prepared ID, operation identity, permission resource, policy labels, presentation, display argument, serialization key, concurrency.
    tool/revalidate, tool/execute, tool/release daemon → runtime Execute or discard a prepared call. execute replies with the terminal result and inline media (bounded by today's attachment budget).
    tool/progress runtime → daemon Display deltas and output chunks under today's 64 KiB / 8-stream bounds. The daemon owns capture and artifact retention.
    tool/cancel daemon → runtime As the call's cancellation token.
    tool/detachable runtime → daemon An executing call reached its detach point. Superseded tool/stdin and the job/* messages in runtime protocol 3 (see background tool calls).
    mcp/changed runtime → daemon The status of the template's MCP servers and the ones that failed (section 6.4), merged into mcp.changed.
    mcp/reconnect daemon → runtime Reconnect one MCP server, or retry the failed ones when a session that uses the instance is created or opened.
    runtime/shutdown daemon → runtime Graceful stop, then termination after shutdown_grace_ms.

    ToolPreparationContext.cwd and workspace_root disappear from the daemon side; the runtime fills them from its own workspace.

    Runtime protocol 4 adds producer messaging for runtimes: a runtime that declares it may send producer messages to the sessions attached to it (see external producers).

    10. Lifecycle and failure¶

    • The global and local instances start with the daemon. Other instances start when a session that attaches them is created or opened, or when they are attached, and stay up until the daemon exits.
    • Connection, reconnection, and failure follow section 6.4.
    • Runtime stderr is captured into bounded diagnostics, as plugin stderr is.
    • When a runtime drops, calls in flight, backgrounded ones included, fail with a new runtime_unavailable failure code. Tool calls are never retried transparently.
    • Instance status (starting, ready, reconnecting, failed, stopped) is visible to clients (section 11).

    11. Client protocol¶

    Protocol 39 → 40 (one bump per phase that changes the wire; phase 1 already used 39 for removing AgentDocumentSource::Workspace).

    • session.create gains runtimes: [{ runtime_id, workspace? }] and global: bool. Omitted means local at the daemon's directory plus global.
    • New session.runtime.attach { session_id, runtime_id, workspace } and session.runtime.detach { session_id, name }.
    • New runtimes.list: templates and live instances with status. New runtimes.changed notification on instance status changes. mcp.changed covers servers in every runtime.
    • Connection failures and drops from section 6.4 reach clients as these notifications with the failure reason; the TUI shows them as an error notice in each affected session.
    • The TUI gains a /runtime panel (attached runtimes with status, attach by template and workspace path, detach) and shows attachment names in the session status line. The MCP panel shows servers from every runtime and edits global-runtime servers only.

    12. Crate changes¶

    This lands open review item 9 (extract tool_api into a leaf crate):

    • runtime_api (new leaf crate): the tool trait, prepared-tool types, ToolSpec with collision, progress and stdin abstractions that do not depend on OutputHub, OutputCapture, or ArtifactRouter, and the runtime protocol types. Depends on protocol (or identity) only and knows nothing about MCP.
    • mcp (new crate, from engine/src/mcp.rs): the MCP client and registry, shared by the global runtime in the daemon and by coding_runtime. OAuth stays on the daemon side.
    • coding_runtime (from today's tools): read, write, edit, bash, webfetch, fs_cap, runtime-side MCP hosting, skills and AGENTS.md discovery, and the protocol server loop.
    • engine: base layer tools (delegate, message, skill, goal, read_artifact) move in or into an engine-side module; it gains the runtime registry, attachment fold, composition, and the protocol client.
    • cookie_agent: cookie runtime coding --stdio --workspace <path>. The subcommand needs no provider configuration and exits on stdin EOF.

    13. Phases¶

    Each phase lands with all gates green and updates the user-facing docs it changes (architecture.md, configuration, protocol, tools, system prompt).

    1. Runtime seam, in-process (protocol 39 only for removing the workspace agent source).

    Compatibility v1: Stable Protocols, Session History, Media Input, and Tool Display¶

    Status: implemented (decisions of 2026-10-17 below; phases A to H landed by 2026-10-19, see section 15). This spec governs compatibility for the client protocol, the plugin protocol, the runtime protocol, and session history. The protocols froze at 1.0.0 and have since grown only by minor versions, and history at format 1; Schemas links each protocol's current version. Where earlier specs or references disagree, this one wins.

    1. Goal and scope¶

    Nothing outside this repository speaks cookie-agent's protocols or reads its session logs yet. This is the last change free to break them. Afterwards, four surfaces carry a compatibility promise:

    1. Plugins written against plugin protocol 1.x keep working with every daemon that speaks 1.x, and the protocol grows without breaking them.
    2. Runtimes written against runtime protocol 1.x likewise.
    3. Clients (the TUI, the CLI, a future HTML client, third-party clients) written against client protocol 1.x likewise.
    4. Session history keeps loading when new events and fields are added, and a log written under an earlier history format is converted when a newer build opens it.

    The same change lands three features. Each one replaces an existing field, so each must land before the freeze:

    1. User media input. Users attach images and video (and the other kinds the selected model accepts) to their input.
    2. Structured tool display. Tools describe arguments, progress, previews, and results as typed display blocks. Each client decides how to render them, and no client branches on a tool's name.
    3. Edit context. Edits and writes show a diff with real file line numbers and five lines of context on each side.

    Out of scope: a web client implementation, daemon-side media resizing or transcoding, provider file uploads or URL reuse for media, inline image rendering in the TUI, and new coding tools (grep, glob, multi-edit). The display blocks are designed so that such tools need no client changes.

    Decided 2026-10-17¶

    • Versions. Each protocol has a semver MAJOR.MINOR.PATCH version. All three start at 1.0.0 at the freeze. CI enforces that every change bumps its version correctly (section 7).
    • Runtimes. The runtime protocol is in scope. Plugin tools speak its tool messages.
    • Major bumps. A major bump of the client, plugin, or runtime protocol is a clean break: the daemon does not keep serving the previous major. Session logs are the exception. A log written under an earlier history format is converted to the current format when a newer build opens it (section 8.7).
    • Provider hooks. provider_before_request and provider_after_response are removed.
    • Events. The event set is merged as described in section 8.2; the input-lane events stay separate. An unknown state event in an older build opens the session read-only (section 8.4).
    • Old logs. Every legacy history reader is removed. Sessions written before this change, labpc's included, stop opening, and no migration is provided.
    • Media transport. Upload and fetch are JSON-RPC methods with chunks of at most 1 MiB. There are no HTTP routes.
    • Media limits. The daemon tells clients, per model, which media it accepts, so clients hide or disable attachment options before the user can pick them. The daemon still rejects violations. A too-large asset is rejected; a client may offer "downscale and attach?" from that rejection.
    • Diff context. Diffs carry five lines of context on each side of a change.
    • Terminal colour. terminal display blocks may contain SGR colour sequences.
    • Browser access. The token moves into the handshake. [server] allowed_origins lists web origins allowed to connect, and "*" allows any origin. (Reversed 2026-10-21: the allowlist is removed; see section 10.1.)
    • Display size. Inline display stays at 64 KiB per result. A block that had to be truncated carries an artifact reference to its full content.
    • Errors. Every error carries a stable code plus a description a user can understand. An optional hint says what to do next, and optional technical detail is shown on request (section 6).

    2. Vocabulary¶

    Term Meaning
    Surface One versioned contract: the client protocol, the plugin protocol, or the runtime protocol. Session history is versioned separately (section 8.7).
    Peer The other end of a connection: a client, a plugin, or a runtime.
    Information A message a receiver learns from: results, notifications, events, hook params, initialize results, stored events.
    Command A message asking the receiver to act: client RPC params, plugin and runtime requests to the daemon (producer/*, tool/progress).
    Open enum A wire enum whose readers accept values they do not know, mapped to a documented fallback.
    State event A session event that affects projection or model history replay.
    Audit event A session event a reader can skip without changing any projection.
    History format The major version of the on-disk session log layout.
    Display block One typed unit of tool presentation (section 12).

    3. Versions¶

    3.1 Semver per surface¶

    Each surface's version is a string "MAJOR.MINOR.PATCH": three decimal integers with no leading zeros, and no pre-release or build suffix.

    Part Bumped for Effect
    MAJOR A breaking change: something removed or renamed, a meaning changed, a new required field in a message the peer receives, a closed enum grown Peers with different majors do not connect
    MINOR Any addition: a method, notification, hook, event type, display-block kind, optional field, or open-enum value Peers use it to decide what they may send
    PATCH A change that leaves every wire shape alone: a documented behaviour clarified, a validation bug fixed Informational only

    The constants live in cookie_agent_protocol: CLIENT_PROTOCOL_VERSION, PLUGIN_PROTOCOL_VERSION, and RUNTIME_PROTOCOL_VERSION, each a ProtocolVersion { major, minor, patch } that serializes as the string. The old exact numeric wire types (exact_numeric_wire_type!, ProtocolVersion 48, ExtensionProtocolVersion 1, RUNTIME_PROTOCOL_VERSION 5, and RuntimeSnapshotSchemaVersion 6) are removed. Until the freeze (phase H) the versions stay 0.x and change freely; the freeze stamps 1.0.0 on all three.

    Old builds send an integer version, so their decoders reject a string, and a new build's decoder rejects an integer. The two can never be mistaken for each other.

    3.2 Handshake¶

    Every handshake follows one pattern:

    1. The connecting side sends its full version.
    2. The receiver reads protocol_version from the raw JSON before it decodes anything else. A different major is answered with error unsupported_protocol (section 6), whose data names both versions. A malformed hello then fails as before.
    3. The reply carries the receiver's own version.
    4. The shared level is the lower of the two minors. A sender sends a method, field, hook, or block kind only if the receiver's version includes it. Because readers ignore what they do not know (section 4), a sender may leave additional information in place for older receivers; it gates only commands and anything an older receiver would misread.

    Feature strings carry only what depends on configuration, never what a version already implies. For example, producer_messaging is a feature because it is present only when configured. Both sides list theirs in the handshake. An unknown feature is ignored.

    3.3 Which surface a message belongs to¶

    • Session events (the EventPayload set) belong to the client protocol and to the plugin protocol, since both deliver them. Adding an event type bumps both minors.
    • The tool/* messages belong to the plugin protocol and to the runtime protocol. A change to them bumps both. Today a runtime protocol change silently changes the plugin wire; runtime 3 to 5 did so while the plugin protocol stayed at 1.
    • Display blocks (section 12) belong to all three.
    • Session history is not versioned by minor. Its additions follow the tolerant rules of section 8.

    4. Decoding rules¶

    4.1 Tolerate information, reject unknown commands¶

    What arrives Unknown field Unknown enum value or tag
    Information Ignored The open-enum fallback (4.2)
    Command Rejected with -32602, data.code unknown_field, and data.field set to the JSON path Rejected with -32602, data.code unknown_variant, and the path

    Commands stay strict because an ignored field in a command can silently change what happens. A sender knows the receiver's version and gates new fields on it (3.2).

    Writers stay strict. Every value a component builds is validated before it is sent or written: the same bounds, the same required fields, the same grammar as today. Strictness moves from decoders to constructors and to the writer's validation step.

    #[serde(deny_unknown_fields)] is removed from every type that crosses a surface as information. It stays on command params and on configuration (AGENTS.md's strict configuration rule is unchanged). The compatibility checker (section 7) fails when an information type's schema has additionalProperties: false.

    The JSON-RPC envelope is information on both sides. Unknown top-level members are ignored, and request IDs may be integers or strings, as JSON-RPC 2.0 allows. A frame that is not JSON, or is not a request, notification, or reply, still closes the connection.

    4.2 Open enums¶

    • Tagged enums with data (such as EventPayload and display blocks) use Open<T>: either Known(T) or Unknown { tag, raw: Value }. The raw JSON is kept so that a value can be passed on or written back unchanged. open_enum! derives the serde and schema glue.
    • Unit enums (such as SessionStatus or McpServerState) gain an Unknown variant with #[serde(other)], or become label strings.
    • Label-like values (such as diagnostic kinds and the tool kind hint) are validated strings, following the existing kind_label! pattern.
    • Every open enum documents what Unknown means where it is read. For example, an unknown session status renders as "unknown" and allows no action; an unknown tool collision mode behaves like prefix.
    • An enum is closed only when growing it is a breaking change by design (such as ProducerDeliveryMode). The schema marks open enums x-open: true (section 7).

    Protocol types do not get #[non_exhaustive]. The engine, the server, and the TUI build and match these types across crate boundaries, so #[non_exhaustive] would remove the compiler's exhaustiveness checks internally. Rust source compatibility of the crate follows its own crate semver. Only the plugin SDK's own types (its builders and ToolOutput) are #[non_exhaustive].

    5. Wire types are not internal types¶

    No surface, including stored events, embeds a type owned by oven-sdk or by engine policy. Where the engine needs data it does not otherwise model, it stores an opaque Value. It decodes that value best-effort when the value is used, never when loading. These replacements apply everywhere:

    Today Replacement
    FrozenModelBinding (embeds oven_sdk::LanguageModelDescriptor, ProviderOptions, credential and setup bindings) in events PersistedModelBinding { selection, provider_id, provider_model_id, adapter: String, resolved: ResolvedModelRef, selection_fingerprint, blueprint_fingerprint, frozen: Value }; frozen is decoded only to resume or recover
    AdaptorId, AdapterFamily as closed enums on the wire Label strings
    ModelCapabilities in tool/* turn context ToolTurnModel { model, adapter, input_media: [MediaKindLabel] }
    AgentSnapshot.schema (exact 7) and its schema 5/6 decoders No schema field; the snapshot is information
    PersistedToolResult in tool/execute Wire ToolResult (section 9.4)
    PreparedOperationIdentity built by the plugin or runtime The daemon builds the approval identity from the declared permission and resource (section 9.4)
    oven_sdk::HistoryTurn JSON in model_before_request HookHistoryMessage { role, content: [HookContentPart] }, where a part is text, file (metadata only), tool_call, or tool_result
    Raw EventPayload to plugins The public event contract (section 8) with subscription patterns (section 9.3)
    RuntimeSnapshotV1 and its schema version ModelCatalogView (section 10.4)
    ExtensionInterceptionHook enum in PluginInfo.hooks Hook name strings

    6. Errors¶

    All four protocols use one scheme:

    Code Meaning
    -32700, -32600, -32601, -32602 The standard JSON-RPC codes
    -32001 Handshake required
    -32002 unsupported_protocol
    -32003 Unauthenticated
    -32000 Any application error

    Every application error has the same shape:

    { "code": -32000,
  "message": "The selected model does not accept images.",
  "data": {
    "code": "media_unsupported",
    "hint": "Choose a model that accepts images, or remove the attachment.",
    "detail": "model anthropic/claude-haiku-5-5 declares input modalities: text",
    "kind": "image", "model": "anthropic/claude-haiku-5-5" } }
    Member Required Meaning
    message yes A description a user can understand: one or two plain sentences saying what went wrong, in the user's terms rather than the engine's. It contains no internal type or variant names, no stack traces, and no secrets. Terminal-safe, at most 1 KiB.
    data.code yes A stable snake-case machine code from an open set.
    data.hint no What the user can do about it, as one plain sentence. Present whenever there is a useful next step. Terminal-safe, at most 512 bytes.
    data.detail no Technical detail for a "details" view or logs, such as the upstream cause, a path, or a revision. Terminal-safe, at most 4 KiB. It replaces today's data.detail and debug_code.
    other data members per code Structured fields the code defines, such as kind and model above.

    The registry is one module, cookie_agent_protocol::errors. For each code it lists:

    • its data fields;
    • a message template, filled from those fields;
    • a hint template, where one applies;
    • a one-line description for the docs.

    The daemon always builds message and hint from the registry, so the same code always reads the same way. The reference docs are generated from the registry: a table of every code with its description, hint, and fields.

    How clients use it:

    • Clients branch only on data.code, never on message.
    • To show an error, a client shows message, then hint when present, and detail on request.
    • A client may substitute its own wording for codes it knows, for example to translate, or to show a "Downscale and attach?" action for media_too_large.
    • For a code it does not know, message and hint are already readable, so new codes need no client change.

    Peers' errors. Plugins and runtimes follow the same shape in errors they send. The SDK fills message from the error the plugin returns and requires it to be nonempty. When the daemon surfaces a peer's error to a user, such as a failed tool call or a plugin that cannot start, it keeps the peer's message and names the peer. Tool failures shown to the model keep their own model-facing text; this shape is for people.

    The existing numeric codes move into data.code. Examples:

    Today data.code
    -32020 no_runnable_model
    -32022 session_owned_elsewhere
    -32030, -32031 tree_usage_*
    -32040 config_apply_refused
    The provider-connect codes Unchanged string codes
    The runtime protocol's -32010/-32011/-32012 unsupported_protocol (-32002), already_initialized or initialize_rejected, not_initialized

    The several meanings -32602 carries today (stale revert, fork idempotency, rename, goal, producer, and plugin rejections) become -32000 with their own codes.

    The TUI's local copy of -32022 and its match on the message "stale revert" are removed. debug_code is removed from error data.

    7. Compatibility checker and test sets¶

    7.1 The checker¶

    crates/protocol/scripts/check-compat.py replaces check-event-payload-additive.py and check-extension-protocol-additive.py. crates/protocol/scripts/check-schema-additive.sh runs it in CI.

    Baselines live in crates/protocol/compat/<surface>/, with surfaces client, plugin, runtime, and events. Each holds:

    • version: the version the baseline was taken at;
    • methods.json: every method and notification with its direction, its kind (request or notification), and its params and result schema roots;
    • schemas/*.schema.json: every root, generated by cargo run -p cookie_agent_protocol --example generate.

    The generator covers every root, including the ones missing today: config.*, plugins.*, provider.connect, and all tool/* messages.

    Rules. The checker walks nested definitions and compares each type by its role. It knows a type's role from methods.json: a type that is only a command's params, a type that only flows as information, or both (strictest rule wins).

    Change Information type Command params
    Field added (optional) minor minor
    Field added (required) minor (writer always sets it) major
    Field removed or renamed major major
    Field type changed major major
    Optional field became required minor major
    Bound tightened (maxLength, maxItems, range) major minor
    Bound loosened major minor
    Value added to an x-open enum minor minor
    Value added to a closed enum major major
    Value removed from any enum major major
    const changed major major
    additionalProperties: false on an information type rejected outright –
    Method or notification added minor minor
    Method or notification removed major major
    No schema change patch or none patch or none

    Loosening a bound on information is major because older readers may still enforce the old bound on data they store.

    The checker computes the required bump and fails unless the surface's version constant has at least that bump against the baseline's version. crates/protocol/scripts/update-compat-baseline.sh regenerates a baseline and refuses when the constant is too low.

    Events. Every EventPayload tag must be in the events baseline, and new tags are added only through the update script. Today 20 of the 86 tags are not in the baseline at all.

    The existing self-test scripts become one mutation test of check-compat.py covering every row of the table.

    7.2 Test sets¶

    Recorded at the freeze (phase H), each in a directory the tests refuse to regenerate (COOKIE_UPDATE_* switches do not apply to them):

    • crates/protocol/compat/corpus/client/1.0.0/: a recorded TUI session's requests, with the notifications and replies it received.
    • crates/protocol/compat/corpus/plugin/1.0.0/ and .../runtime/1.0.0/: recorded conversations of the Python reference plugin (section 9.6) and the coding runtime.
    • crates/engine/tests/fixtures/history/1/: real multi-run session trees from a scripted run against a fake provider (section 8.8).

    What the tests prove:

    • New builds accept old data. Recorded requests replay against the daemon, recorded plugin and runtime messages replay against the SDK and the daemon, and recorded logs open, project, and rebuild model history equal to a recorded snapshot.
    • Readers tolerate future data. "Future" fixtures inject unknown fields, enum values, event tags, block kinds, methods, and notifications at every level. The client, the SDK, the daemon, and the history loader must accept them.

    Old readers meeting new data is covered by the checker (7.1), since old code cannot run in tests.

    Each later minor release adds its own corpus directory next to the earlier ones.

    8. Session history¶

    8.1 Legacy readers removed¶

    Removed with all their decoders, defaults, and tests:

    • the events session_reverted, context_rehydrated, plugin_event_added, tool_stdin_submitted, delegate_finished, and user_input_recalled (the old form);
    • dropping stored text_delta, reasoning_delta, and tool_call_progress lines;
    • the legacy plugin_diagnostic kinds;
    • the AgentSnapshot schema 5 and 6 wire structs, and the workspace document-source alias;
    • the plugin { plugin } producer owner;
    • legacy_local_runtime;
    • ignoring event_schema_version;
    • stripping checklist item ids;
    • the defaults for a missing capability (runtime_attached) or attachment (agent_md_loaded/agent_md_skipped), and the rule that a log with neither attach event is attached to global and local;
    • output_chunk on tool_call_progress;
    • the GoalReminderKind default.

    user_input_recalled_v2 and delegate_finished_v2 take the plain names user_input_recalled and delegation_finished (8.2).

    The fixtures events-schema-18.jsonl, -20.jsonl, and -21.jsonl are deleted.

So does every other event not listed above.

    Checked against the code (2026-10-18):

    • delegate_queued is written on the parent, in the parent run, when the invocation is at hand, so delegation_progressed { stage: queued } carries its invocation_id. Tree loading pairs queued children with their parent run through the invocation's delegation_progressed { stage: started }.
    • delegate_child_terminated is written runless to the child session and sets the child's own status. It is not a parent-side delegation record, so it stays as is.
    • producer_diagnostic is read only by the validator and the TUI. The goal hold lives in memory, not in a projection, so the event merges into diagnostic.

    8.3 Internal types out of history¶

    • session_created, run_started, delegation_reserved, and FrozenInternalAgentFallback::Model store PersistedModelBinding (section 5) instead of FrozenModelBinding.
    • run_started stops storing selected_suffix next to an agent.fallback_chain it duplicates. It stores the fallback start index instead.
    • The seven revision IDs repeated in session_created, run_started, and delegation_reserved are stored on session_created and on a later event only where they changed.

    8.4 State and audit events¶

    Every event type is classed as state or audit:

    • State: anything the projection, model history, delegation recovery, goals, producers, approvals, or usage read.
    • Audit: everything else, such as diagnostic, model_request_prepared, model_replay_evaluated, model_tools_published, and the approval_step kinds the projection ignores.

    events.md lists the class of every event.

    A writer stamps "skippable": true in the envelope of every audit event.

    Unknown events. A reader meeting an unknown event tag:

    • skips it if the envelope says skippable;
    • otherwise loads the session in render-only mode. Clients can view and subscribe, but run.start, session.submit_input, revert, fork, and compaction fail with data.code session_requires_newer_engine. A diagnostic names the event.

    Additive rules for writers:

    • A new optional field on an existing event must be safe to ignore: its absence means the old behaviour.
    • A field whose absence would be misread needs a new event type.
    • A new open-enum value must have a fallback that is safe for old readers.

    8.5 The loader¶

    • Unknown envelope keys are ignored, on line 1 as well.
    • Validation:
    • Cross-event validation failures during load quarantine the record: it is skipped and tainted, with a diagnostic, instead of failing the open.
    • Full validation stays strict for appends.
    • A non-increasing seq ends the readable log at that line. The session opens read-only, with a diagnostic, instead of failing.
    • Nothing derived is recomputed on read:
    • Stored approval operation fingerprints and delegation request fingerprints are trusted.
    • An in-flight delegation whose reservation does not verify becomes unrecoverable for that delegation alone, instead of failing the tree load.
    • wire_resolved and comparisons with today's built-in internal-agent IDs are not used by load validation.
    • Size caps are writer-only.
    • Unknown data survives. Each loaded record keeps its raw line.
    • Fork, publish, and conversion copy the raw bytes of records they did not fully understand (unknown, degraded, or quarantined).
    • Artifact liveness scans raw lines for artifact://sha256/ references.
    • A metadata cache that does not decode is rebuilt from events.jsonl, instead of the session disappearing from the list.
    • The best-effort decoder stops re-decoding a whole payload once per bad leaf; it locates failures with serde_path_to_error.

    8.6 Envelope¶

    { "engine_version": "0.5.0", "session_id": "…", "run_id": null, "seq": 1,
  "timestamp": "…", "origin": "user", "skippable": true, "payload": { … } }

    skippable is written only when true.

    8.7 History format and conversion¶

    session_created carries history_format: 1. A reader handles a log as follows:

    • No history_format: a pre-1.0 log. It is not converted, and the open fails with the existing unsupported-era error.
    • Same format: read under 8.4 and 8.5.
    • Higher format: the open fails with data.code session_requires_newer_engine.
    • Lower format: converted.

    The history format bumps only when a change cannot follow 8.4's additive rules.

    Converters are pure functions from the old log's JSON lines to new lines. They never use old Rust types. Each lives in crates/engine/src/events/convert/v<N>_to_v<N+1>.rs, is registered in one table, and is kept, so they chain: a format-1 log opened by a format-3 build converts 1 to 2 to 3.

    When a log is converted:

    • Owned open: converts the whole tree under its owner.lock: the root log, every child log, the metadata cache, and subagents/index.json. Each file is written next to the original and fsynced. Each original is renamed to events.jsonl.v<N>.bak, and the new file is renamed into place. A failure leaves the originals untouched.
    • Read-only open: converts in memory only.
    • cookie sessions upgrade [--all]: converts every session up front.

    Backups are kept until the user deletes them.

    A test-only converter from format 0 to format 1 exercises the machinery before the first real converter exists.

    This is the governing exception to AGENTS.md's rule against migrations.

    8.8 Golden logs¶

    A scripted run against the engine's fake provider records real session trees. It covers:

    • text, reasoning, and native replay;
    • tool calls, including background and failed ones;
    • approvals (asked, granted, denied, tree grants);
    • delegation (foreground, background, resumed);
    • summary and native compaction;
    • goals and producer messages (steer, queue, discard);
    • revert and fork;
    • user images and video;
    • display blocks of every kind.

    The trees are committed under crates/engine/tests/fixtures/history/1/, with a snapshot of each tree's projection and model history. Tests open them read-only and owned, and compare against the snapshot.

    9. Plugin and runtime protocols¶

    9.1 Handshake¶

    plugin/initialize and runtime/initialize share one shape.

    Daemon → peer params:

    { "protocol_version": "1.0.0", "engine_version": "0.5.0",
  "features": ["producer_messaging"] }

    The runtime variant keeps its existing members (runtime_id, settings, MCP servers). The plugin result:

    { "protocol_version": "1.0.0", "name": "issues", "version": "1.2.0",
  "features": [],
  "capabilities": { "producer_messaging": false, "subscribe_events": ["run_*", "tool_call_*"],
    "subscribe_bus": false, "publish_bus": false,
    "intercept": [{ "hook": "tool_before_call", "on_error": "block" }] },
  "tools": { "tools": [], "prompt_sections": [] } }

    The runtime result keeps capabilities, its list of offered capabilities, with the new protocol_version and features.

    • Majors are compared from raw JSON first (3.2).
    • An unknown hook name or an unknown feature in a result gets a diagnostic for that entry only; the plugin still starts.
    • An unknown tool-declaration field is ignored. The writer validates its own declarations.
    • Known values that need a newer daemon are skipped with a diagnostic when the daemon's version is below the one that introduced them, for example a collision mode.
    • The SDK exposes the daemon's version, engine_version, and features to plugin code.

    9.2 Tolerance on both ends¶

    Section 4 applies to every plugin/*, tool/*, and producer/* message.

    Commands the daemon receives (producer/*, tool/progress, plugin/emit) are strict. A peer gates new fields on the daemon's version.

    What changes from today:

    • SDK decoding:
    • A hook whose params carry unknown fields still runs.
    • An unknown event or bus message decodes as Unknown instead of being dropped silently.
    • SDK timeouts:
    • plugin/emit_result waits at most interception_timeout_ms; past that, emit_bus resolves as dropped.
    • Today a lost result hangs emit_bus.
    • Daemon messages from plugins:
    • Plugin connections no longer accept the runtime-only capability/tools_changed and mcp/changed.
    • tool/release or tool/cancel with params the daemon cannot read fails loudly (a diagnostic) instead of being ignored.

    9.3 Hooks and events¶

    • Hooks removed: provider_before_request and provider_after_response.
    • on_error on each intercept entry is allow (the default) or block. With block, a hook that times out, crashes, rejects, or answers malformed blocks its operation:
    • a tool call is blocked;
    • an input, fork, or revert is refused;
    • a model request fails the attempt.

    Today every failure fails open, so a tool_before_call policy plugin stops enforcing when its params change. - model_before_request carries messages: [HookHistoryMessage] (section 5) and model: { provider_id, model_id, adapter }. A replacement's messages are validated as today. - message_end carries content: [HookAssistantPart], where a part is text, reasoning (text only), tool_call, or file (metadata only). It no longer carries the persisted type. - user_before_input carries content: UserContent, with file parts as metadata only. A transform may change or remove parts but not add files. - agent_before_start.prompt_context gets a defined, documented shape instead of an ad-hoc json!. - subscribe_events is a list of tag patterns (* matches any suffix). Plugins receive plugin/event { session_id, context_id, seq, event }, where event is the stored event's payload under the public event contract. An unknown tag reaches the SDK as Unknown. An empty list subscribes to nothing, and ["*"] subscribes to everything.

    9.4 Tool messages¶

    • Turn context: tool/prepare and tool/execute carry turn: { agent, model: ToolTurnModel } (section 5).
    • Prepare result: PreparedCall drops operation. It carries:
    • permission, permission_resource, and normalized_arguments, as today;
    • presentation v2 fields the runtime owns: title, hint, primary_argument, arguments, and preview (section 12.2).

    The daemon builds the approval identity (PreparedOperationIdentity) from the declared permission, the resource, the normalized arguments, and its own tool identity. Non-Rust peers no longer reproduce a digest byte for byte. - Execute result: tool/execute returns ToolResult { output: ToolCompletionOutput, title?, display: [DisplayBlock], metadata?, attachments, additional_messages, failed }. The daemon builds PersistedToolResult from it. media stays as is. - Progress: tool/progress carries display as a block delta (section 12.3).

    9.5 SDK¶

    • ToolOutput becomes a builder: text, title, display blocks, metadata, attachments, and failed.
    • ToolContext::progress can send a display delta.
    • New per-tool hook: prepare_presentation(call) -> Presentation for the title, hint, arguments, and preview.
    • Exposed to plugin code: the negotiated version, engine_version, and features.
    • Crate versioning: the SDK has its own crate semver. It exposes PLUGIN_PROTOCOL_VERSION, and its major follows the plugin protocol's major.

    9.6 Schemas and the reference plugin¶

    • Schemas for every plugin and runtime message are committed under crates/protocol/compat/ (section 7) and published with the docs.
    • crates/engine/tests/fixtures/fake_plugin.py grows into examples/plugins/python/: a dependency-free reference plugin with a tool, a hook, events, and a producer.
    • CI validates its messages against the schemas and runs it against the daemon.

    10. Client protocol¶

    10.1 Handshake and authentication¶

    { "method": "handshake", "params": {
    "protocol_version": "1.0.0",
    "client": { "kind": "web", "instance_id": "…" },
    "token": "…", "features": [] } }

    Reply:

    { "protocol_version": "1.0.0", "engine_version": "0.5.0",
  "origin": "client:web-…", "machine_id": "…", "features": [] }

    Authentication:

    • Where the token goes: the WebSocket upgrade no longer requires an Authorization header. A client authenticates either with that header at upgrade (native clients may keep it) or with token in the handshake. Browsers cannot set headers on a WebSocket, so a web client uses the handshake.
    • Before authenticating: a connection that has not authenticated may send only handshake. Anything else gets -32003.
    • Wrong token: -32003, and the connection closes.
    • Deadline: a connection not authenticated within 10 seconds is closed.

    The /runtime endpoint keeps header authentication.

    Origins. A connection whose upgrade request has no Origin header (any native client) is unaffected. One with an Origin header is accepted only if [server] allowed_origins allows it:

    [server]
allowed_origins = ["https://cookie.example", "http://localhost:5173"]
# or: allowed_origins = ["*"]
    • Default: empty, which refuses every origin, as today.
    • Entries: exact scheme://host[:port] origins, or the single entry "*". "*" combined with other entries is a configuration error.
    • With "*": any web page can open a connection, and the token is the only protection. The configuration reference says so.
    • TLS: a page served over HTTPS can only connect with wss://, so it needs the daemon's TLS settings.

    Reversed 2026-10-21 (user decision). [server] allowed_origins is removed. /ws accepts an upgrade from any Origin, or none: a reverse proxy makes browser-origin gating pointless, since the browser reports the proxy's origin, and the token is the real guard. /runtime still refuses any request that carries an Origin header (HTTP 403), since a browser is never a runtime. A config that still has allowed_origins fails as an unknown key. The handshake is unchanged, so the client protocol version is too.

    10.2 Decoding¶

    • Results and notifications are information (4.1). Open is used for:
    • EventPayload and EventSubscriptionMessage;
    • SessionsChangedNotification's change kind;
    • RuntimeChangeReason;
    • McpServerState and PluginState;
    • display blocks;
    • every other enum in results.
    • Notifications are isolated. One that does not decode is dropped. The client gets a ClientDelivery::Diagnostic, and no pending call fails. Today one bad notification fails every call in flight.
    • Replay delivers an event it cannot decode as Unknown; the page does not fail.
    • Error data decodes per data.code, and an unknown code decodes as a generic error.
    • TUI rendering: unknown events render as nothing (a dim row in the debug view), unknown states as "unknown", and unknown blocks as their text fallback (section 12.4).

    10.3 Params¶

    Params are commands (4.1). An unknown or mistyped member fails with -32602 naming the JSON path.

    Clients gate methods and params on the daemon's minor. A -32601 from a method the client believed supported shows "the daemon is too old for X".

    10.4 Payloads trimmed to client views¶

    • runtime.snapshot.get and runtime.changed carry ModelCatalogView { revision, providers, models, agents }:
    • revision is one opaque string replacing the 11 revisions and counters;
    • providers, models, and agents are client-facing descriptors without frozen bindings, recipe IDs, or compiler versions;
    • every model states input_media (section 11.2).

    RuntimeSnapshotSchemaVersion and the cap of 9 change reasons are removed. - SessionMeta keeps its revision IDs as opaque strings. - config.get and config.apply stay documents in the configuration format. That format keeps its own strict rules, and a configuration key change is a configuration change, not a protocol change.

    • Complete the methods table (session.tree_usage, mcp.auth.*, and mcp.server.* are missing).

    11. User media input¶

    11.1 Content parts¶

    "content": [
  { "type": "text", "text": "What is wrong with this layout?" },
  { "type": "file", "artifact": { "sha256": "…", "byte_length": 482113,
      "media_type": "image/png", "filename": "screenshot.png" } }
]

    UserContent is a nonempty list of UserContentPart (open): text { text } or file { artifact: ArtifactRef }. Text parts follow today's input limits.

    Where it replaces input: String:

    • the params of run.start, run.steer, and session.submit_input;
    • SessionRecallInputResult and QueuedInput;
    • the input-lane events (8.2).

    message_injected and producer bodies take UserContent but accept text parts only, for now.

    11.2 Advertised limits¶

    Each model in ModelCatalogView states:

    "input_media": [
  { "kind": "image", "mime_types": ["image/png", "image/jpeg", "image/gif", "image/webp"],
    "max_bytes": 3932160, "max_dimension": 8000, "max_pixels": 16777216, "max_count": 20 },
  { "kind": "video", "mime_types": ["video/mp4"], "max_bytes": 19608371, "max_count": 1 }
]
    • kind is an open label: image, pdf, audio, or video.
    • The limits are effective: the catalog's capability, the provider and adapter-family delivery limits (runtime_api::media), and the attachment caps (20 MiB, or 25 MiB for video), whichever is lowest.
    • Clients show attachment options only for kinds the session's selected model accepts. They filter file pickers by mime_types, and they check size and pixels before uploading.
    • Fallback models: the limits are the selected (primary) model's. A fallback model without that kind gets placeholders (11.5).

    11.3 Upload and fetch¶

    Method Params Result
    artifact.upload.begin session_id, byte_length, filename? upload_id, chunk_bytes (1 MiB)
    artifact.upload.chunk upload_id, offset, data (base64, at most chunk_bytes decoded) {}
    artifact.upload.finish upload_id, sha256 ArtifactRef, plus image: { width, height } for images
    artifact.upload.cancel upload_id {}
    artifact.read session_id, sha256, offset, length (at most 1 MiB) data (base64), total_bytes, media_type

    Uploads:

    • Storage: uploads go to the session tree's artifact store. A client that attaches before its first prompt creates the session first.
    • begin: refuses byte_length above the largest attachment cap.
    • Chunks: must arrive in order without gaps.
    • finish:
    • checks the digest;
    • sniffs the media type from the content, ignoring the filename;
    • validates the content as tool attachments are validated today;
    • stores the blob.
    • Scope: an upload in progress belongs to its connection and is dropped when the connection closes.
    • Lease: a finished upload no event references is kept for one hour, then swept.
    • Becoming durable: a submitted input's event references the blob, so revert sweeps and fork linking cover it as they cover tool attachments.

    Fetch:

    • artifact.read serves any artifact in the session's tree: user uploads, tool attachments, and the full references of display blocks.
    • Every authenticated client is trusted with the whole daemon, so no per-artifact check is added.

    Errors (data.code):

    Code Data
    media_too_large kind, byte_length, max_bytes, width?, height?, max_dimension?, max_pixels?
    media_type_unsupported media_type
    digest_mismatch –
    upload_not_found –
    artifact_not_found –

    A client may answer media_too_large by offering to downscale and attach; browsers can do this with a canvas. The TUI shows the limit.

    11.4 Admission¶

    At run.start, run.steer, and session.submit_input, each file part must:

    • name an artifact in the tree's store;
    • be of a kind the model of the run accepts (media_unsupported { kind, model });
    • fit that model's byte and pixel limits (media_too_large).

    The parts of one input of a kind must also not outnumber that kind's max_count (media_limit_exceeded { kind, count, max_count }).

    These checks back up the advertised limits (11.2); a well-behaved client never triggers them.

    11.5 Model history¶

    • User turns with file parts become oven-sdk user messages with InputPart::File, the same way tool-emitted user messages are built today (attachment_file). The existing count elision and protection of the latest message apply.
    • Media fit. A new history step runs before each request. It replaces every file part (user, tool-result, or tool-emitted) whose kind the attempt's model does not accept with a placeholder like this one:
    [image omitted: <model> does not accept images (screenshot.png, 471 KB)]

    The placeholder is deterministic, so cache prefixes stay stable. Today a model switch or a fallback to a model without that kind fails the whole request in oven-sdk. - Compaction summaries see the same placeholders.

    11.6 TUI¶

    • /attach <path> uploads a local file. The TUI may run on a different machine from the daemon, so it always uploads.
    • Pasted paths: text pasted into the composer that is exactly one existing file path (what terminals paste on drag-and-drop) offers to attach it.
    • The composer shows each attachment as 📎 name · type · size, and removes it with backspace on the chip.
    • Options shown: only kinds the selected model accepts.
    • Later, not in this spec: clipboard image paste and inline previews.

    12. Structured tool display¶

    Principle. Tools describe what happened as typed blocks, and clients choose how to render them. No client branches on a tool's name or parses a tool's arguments. Display never enters model history; the model's output is unchanged by this spec.

    12.1 Display blocks¶

    DisplayBlock is an open enum tagged by type:

    Type Fields
    text text
    markdown text (CommonMark)
    code text, language?, start_line?
    file_excerpt path, language?, start_line, lines: [string], total_lines?, full?
    diff path, old_path?, language?, change (created, modified, deleted, or renamed; open), hunks, added, removed, omitted?: { hunks, lines }, as_of (prepare or execute), full?
    terminal segments: [{ stream, text }], exit_code?, full?
    key_value entries: [{ key, value }]
    table columns: [string], rows: [[string]], omitted_rows?
    json value
    media artifact: ArtifactRef, alt?
    link url, label?
    session_ref session_id, short_id?, label?

    Field details:

    • A hunk is { old_start, old_lines, new_start, new_lines, lines: [{ op, text }] }. op is context, add, or remove.
    • Line numbers are 1-based file line numbers. A client numbers each line from the hunk's starts.
    • full is an ArtifactRef, present only on a truncated block. It names the complete content: the complete diff, stream, or excerpt. A client fetches it with artifact.read.
    • Control characters:
    • Text fields allow \n and \t only.
    • terminal segment text also allows SGR sequences (ESC [ <params> m).
    • The daemon strips every other control sequence from blocks it receives.

    Budget:

    • All display blocks of one result share 64 KiB, serialized.
    • Blocks are cut as whole units: whole hunks, rows, segments, or lines.
    • A cut block carries omitted and, where the content exists elsewhere, full.
    • full for terminal output reuses the call's retained output artifacts.

    12.2 Presentation v2¶

    tool_call_started carries:

    "presentation": {
  "title": "Edit src/main.rs",
  "hint": "file_edit",
  "tool": { "name": "edit", "published_name": "labpc_edit",
            "source": { "type": "runtime", "runtime_id": "labpc", "attachment": "labpc_repo", "capability": "coding" } },
  "primary_argument": "src/main.rs",
  "arguments": [ … DisplayBlock … ],
  "preview": [ … DisplayBlock … ]
}

    Who supplies what:

    • The runtime or plugin supplies title, hint, primary_argument, arguments, and preview from prepare.
    • The daemon fills tool. source is an open tagged value: base, runtime { runtime_id, attachment, capability }, plugin { plugin }, or mcp { server, runtime_id? }.

    Fields:

    • hint is an open label used only for icons and grouping. The documented values are shell, file_read, file_write, file_edit, fetch, search, delegate, message, skill, goal, and generic. An unknown hint renders as generic. The daemon never branches on it.
    • arguments shows the call's arguments, such as the command as a code block or a path. Clients fall back to the raw model arguments when it is absent.
    • preview shows what the call will do, such as a diff as of prepare.

    ApprovalRequest gains tool_call_id, so approval views show the call's presentation and preview directly instead of matching operation fingerprints.

    The background state is a typed background: { state } on the result, replacing metadata.background.

    12.3 Progress and results¶

    • tool_call_progress.display is a delta:
    • append { index, text } appends to the text of block index, which must be a text or terminal block. For a terminal block it appends to the last segment of the same stream, or starts a new segment.
    • replace { blocks } replaces the live list.

    The 64 KiB cumulative budget is unchanged. The TUI also shows the progress message, which it ignores today. - tool_call_terminated results carry display: [DisplayBlock]. Their final display replaces the live one. - Disk encoding: display_span is kept as an internal encoding for a text or terminal block whose text occurs verbatim in output. The daemon expands it before anything leaves the engine.

    12.4 Text fallback and version downgrade¶

    • Every block kind has a canonical text rendering, DisplayBlock::to_text, defined in the protocol crate.
    • Older clients: the daemon replaces a block whose kind is newer than the client's negotiated minor with a text block of that rendering. Every client sees something.
    • Unknown kinds from peers: a block of a kind the daemon does not know (from a newer plugin or runtime, which should not send it) is dropped, with a diagnostic.
    • Unknown kinds in logs: a block of a kind unknown to the daemon, in a log written by a newer minor, is dropped from what clients receive. The raw data stays on disk.
    • The CLI prints results with to_text.

    12.5 Built-in tools¶

    Tool Arguments Preview Result display
    edit path; the replacement as code diff as of prepare, from the file prepare already reads diff as of execute, built from the replaced ranges
    write path diff as of prepare (reads the existing file) diff: created, or modified against the text it replaced
    read path, range – file_excerpt; table for directories; media for media
    bash code (sh) – terminal with stdout and stderr segments (SGR kept) and exit_code
    webfetch link – key_value (status, type, final URL), plus text or markdown for the body excerpt

    Diff details:

    • Context: five lines on each side of every change. Hunks whose context overlaps merge.
    • edit with replaceAll: one hunk per replacement, merged where they overlap.
    • write computes a line diff of the old and new text when both are text of at most 1 MiB. Otherwise it reports change with counts and no hunks. The line diff uses the similar crate (Apache-2.0, accepted by deny.toml).
    • As of prepare vs execute: the prepare preview can differ from the execute result when the file changed in between, because execute recomputes the replacement. as_of tells clients which one a block is.

    15. Implementation notes¶

    Deviations and choices made while implementing, by phase.

    Phase B¶

    • Names. The semver type is SemVer; the exact numeric ProtocolVersion keeps its name and wire until the handshakes switch (phases E and F), which then remove it. CLIENT_PROTOCOL_VERSION (0.48.0), PLUGIN_PROTOCOL_VERSION (0.1.0), and RUNTIME_PROTOCOL_VERSION (0.5.0) are crate-root constants; the old u32 runtime_protocol::RUNTIME_PROTOCOL_VERSION lives on beside them until then. peer_protocol_version reads a handshake's version from raw JSON.
    • Open<T>. A known tag with a malformed body is a decoding error, not Unknown: Unknown means "from a newer peer". Tolerant readers (the history loader) handle the error where they know what to skip. The known tags come from the enum's own schema, so open_enum!(tagged T, tag = "…") cannot drift from its serde attributes.
    • Display blocks. Cutting needs an omitted count on every cuttable kind, not only diff and table: text, markdown, code, file_excerpt, and terminal carry omitted_lines, and key_value carries omitted_entries. terminal blocks are cut by line within their segments, so a single long segment still keeps its head. json, media, link, and session_ref cannot be cut and are dropped when they do not fit. The budget leaves room for the blocks after a cut block when they fit whole. diff.change and the terminal stream are open (unknown reads as modified and stdout); as_of and the hunk line op are closed.
    • Progress delta. append names no stream in 12.3, yet a terminal append goes to "the same stream", so append has an optional stream (default stdout; an error on a text block).
    • Strict commands with shared types. New types that also flow as information (ArtifactRef, UserContent, display blocks) do not deny unknown fields. Commands that embed them (run.start content) need their strictness from the decoder (an unknown-field check that names the JSON path) rather than from deny_unknown_fields.
    • Error registry. Today's -32011 covers both a repeated initialize and a rejected one, so both already_initialized and initialize_rejected are registered. version_mismatch stays until the runtime handshake answers unsupported_protocol. config_apply_refused carries the refusal as reason (conflict, invalid_configuration, invalid_change). idempotency_conflict is one code across run, rename, approval, fork, and provider requests, with the request's IDs as optional fields. Templates may name only required fields.
    • Checker rules beyond the table. A required field that became optional is major for information and minor for commands; a closed enum that became open is minor and the reverse major; additionalProperties going from false to allowed is major for information and minor for commands, and the reverse major for commands; any type change (nullability included) and any patternProperties change is major. Before the freeze (0.x in the baseline and the generated set) the baseline must equal the generated set exactly and findings are only reported, as phases C to G change the wire freely.
    • Surfaces. The plugin surface omits capability/tools_changed and mcp/changed, which the daemon still accepts from plugins until 9.2 removes them. The events baseline's version records the client version. ModelSnapshotManifestV1 is no longer exported (it is not on any surface), and ProviderConnectParams now is: its schema describes the credential fields' shape, never a value.

    Phase C¶

    • Runless recall. The positional user_input_recalled { input } was still written: a cancelled queued child's runless steers were withdrawn with it. The plain-named user_input_recalled { user_input_seq, input } therefore also exists runless, naming a runless admission, and readers match every recall by its admission sequence.
    • Attachments. With the "no attach events" rule gone, a session's attachment set is exactly the fold of its attach and detach events, and a session created with no attachment writes no attachment event.
    • Event storage. Without revert markers the visible branch is the whole log, so the engine keeps one event list instead of a physical and a visible one.
    • One delegation finish. delegation_finished is written where the control record was, for every delegation, and carries the teaser. It is not model history. Every background completion already accepted its steer producer message before the old delegate_finished_v2, so the old suppression rule always applied to current writes; written at the control point, the merged record would otherwise appear in a request assembled before the acceptance and the result would reach the model twice. The result reaches the model once, as the tool result or the accepted producer message, and a restart re-drives a missing acceptance as before. ParentRunFacts loses notified: a background delegation counts as notified once its producer message is accepted.
    • Approval cancellation. The pair approval_cancelled + approval_finalized the engine wrote for a system withdrawal is one approval_finalized { outcome: cancelled { reason_code } }, whose final decision is derived (expired for approval_expired, else cancelled; source system). A user's cancel stays a decided outcome, since its source is the user.
    • Open inner enums. RunOutcome, InternalAgentOutcome, DelegationStage, ApprovalStep, and ApprovalFinalization are open (Open<T>, with cheap named tags from a new open_enum! form). Unknown run and internal-agent outcomes read as interrupted, an unknown approval outcome as cancelled, and unknown stages and steps change nothing.
    • Diagnostics. diagnostic.kind is a snake-case label of at most 64 bytes; count is present only from 2; detail is at most 16 KiB. The agent-md notice is engine:agent-md / agent_md_too_large, its message the text the TUI used to compose, and the source of a plugin's notice is plugin:<name>. The Rust kind catalogs (PluginDiagnosticKind, ProducerDiagnosticKind, EngineDiagnosticKind) stay as writer helpers.
    • skippable is derived. StoredEvent has no skippable field: it is serialized from the payload's class and checked against it when read, so a value built in memory cannot disagree with its payload. A step of approval_step this build does not know accepts either value. The classes: diagnostic, skill_invocation_noted, user_input_transformed, model_request_prepared, model_tools_published, model_output_started, model_replay_evaluated, and the doom_loop approval step are audit; everything else is state (live-only events are never stored).
    • Render-only. The event log refuses every append and truncation of a render-only log (EventLogError::RequiresNewerEngine), which covers automatic compaction, titles, and recovery; run.start, session.submit_input, revert, fork, and compaction also check before they start work. Adoption skips the restart repairs. A fork is refused because it would drop the records this build cannot read. The server answers with the registry's session_requires_newer_engine (-32000), naming the event or the history_format.
    • History format. A session_created without history_format fails as the existing unsupported-era corrupt-log error; a higher one with session_requires_newer_engine; a lower one with EventLogError::UnsupportedHistoryFormat, which phase D replaces with conversion.
    • truncation. Every writer left a tool result's truncation null since retained output moved to retained_output; its readers (the model's tool-result JSON, the TUI, the compaction retry hint) served old logs only. The field and ToolOutputTruncation are gone. PersistedToolResult is also the tool/execute result, so the runtime protocol moves to 6 (0.6.0); the plugin protocol already moved to 2 in this step.
    • Adapter labels. AdaptorId is a label ([a-z][a-z0-9-]{0,31}; the kind_label! grammar with room for azure-openai-responses) with constants for the adapters this build resolves to; nothing branches on it. AdapterFamily stays an enum, since media delivery branches on it, but reads and writes the same label grammar, and a family this build does not know reads as Unknown, which delivers no media.
    • Persisted bindings. PersistedModelBinding has the shape of section 5; adapter is the binding's protocol adapter (the descriptor's, such as oven.openai.responses), and the stored identity must agree with itself (selection, provider and model, resolved) when read. decode returns the frozen binding only when it reads and names the same selection, fingerprints, and adapter. It is called where the engine runs a stored binding again: the latest run's policy for manual compaction, title regeneration, and get_history, and a frozen internal agent's model fallbacks. A failure fails that operation with unreadable_model_binding and never the open. A restart never resumes a run with its frozen bindings: runs left running are interrupted, and a new run resolves its models from the live runtime as before. A delegation reservation's bindings are never decoded on read either, since recovery does not rebuild a child from them. FrozenModelBinding and the model-snapshot manifest types are no longer on any surface, so they lose their schemas and LanguageModelDescriptorSchema is gone; no protocol type reachable from EventPayload names an oven-sdk type.
    • Selected suffix. The snapshot's existing selected_suffix_start is the fallback start index, so run_started and also delegation_reserved (which carried the same copy) drop selected_suffix. The run's model is exactly the chain entry at the start, variant included: the engine always froze the chain with the selection's own variant, so the old exception for a head of another variant never applied. Attempt and fallback validation compares resolved_model with the stored resolved of the entries.
    • Revisions. The seven revisions are one RuntimeRevisions value: session_created.revisions, and run_started.revisions and delegation_reserved.revisions present only when they differ from the latest recorded before them. RevisionFold folds them in log order. The event log drops an event's revisions when they equal its fold at append, under the append lock, so writers always pass the full value and the comparison cannot race another append. The session metadata keeps the creation revisions, as before. The only reader of a later event's revisions is the delegation store, which gets each reservation's from the fold of its parent log (the tree-load harvest and parent reconciliation fill them in); nothing reads a run's.
    • Stored data, not derived logic (8.5). Load validation no longer calls wire_resolved (the previous note) or compares with the built-in internal agent IDs: an internal_agent_usage_recorded must name the agent its run froze for the kind in run_started.internal_agents, and run_started checks only that the definitions are one per kind. With nothing recomputed there is no fingerprint mismatch left to make a delegation unrecoverable; the reservation's other checks still fail the tree load until phase D quarantines records.

PersistedToolResult.display's default is left to C3.

The input-lane events, message_injected, and producer bodies store UserContent; the client RPCs, QueuedInput's source, the recall result, plugin producer bodies, and the user_before_input hook stay text until phases E and F, so the engine wraps text as one part and hands back as_plain_text. A writer validates file parts' references, and message_injected and producer bodies refuse any part but text; the existing "not blank" rules read whitespace-only text parts and nothing else as blank, and there is no other input limit today. UserContent converts from a string and equals a string when it is exactly that one text part, which keeps the text comparisons (queue and producer idempotency, admission matching) as they were. Load validation matches a recall to its admission by a digest of the content's JSON instead of its text. The run projection's input, compared when a run.start is retried, stays the plain text the RPC carries. Artifact liveness still scans for artifact://sha256/ URIs, which a file part's ArtifactRef does not spell out; no writer produces file parts yet, so phase F adds them to the scan with uploads.
    • Display blocks in results. PersistedToolResult.display is a required list of open blocks (the schema leaves it out of required because display_span stands in for it). The span encoding applies to a whole single text block (no omitted_lines); terminal spans wait for phase G, which writes the first terminal blocks. The daemon's normalize step (fit_result_display) sanitizes blocks from every tool, drops kinds it does not know, without the diagnostic of 12.4 until phase E, and fits the list to 64 KiB serialized. Fitting cuts whole lines, so a single line longer than the budget now shows only its omitted count where it used to show its first 64 KiB; bash fits its own block, escapes counted, so its truncation marker and exit status survive. A result completed with ToolCompletion::single and no display shows its output, replacing the old "display absent" default. The TUI's rendering of a result without display (title, output, metadata, and emitted messages) served only that default and is gone; a failure with an empty display shows its error.
    • Progress deltas. An append to the index just past the live list creates the block (a text block, or a terminal block when the append names a stream), so today's writers send append { index: 0, text }. One append carries at most 1 KiB, as one display delta did. LiveDisplay is the one bounding rule for writers and readers: an append costs its text's bytes and a replacement its serialized size against one 64 KiB budget per call. Messages keep their own 64 KiB budget rather than sharing the display's. A late subscriber receives a running call's live display as one replace. The plugin SDK's progress sends no display today, so it has nothing to convert.
    • Presentation v2. hint is optional and arguments an empty-means- absent list, since today's prepare (ToolCallPresentation) reports neither; title and primary_argument keep their bounded types (SafeDisplayText, BoundedDisplayText), and PreparedPresentation follows the same shape for phase E. tool.source is absent for a call that names no tool the session offers (a call that fails before the daemon finds its tool). A provider names a plugin or MCP source through ToolProvider::tool_source: the plugin provider names its plugin, and a runtime's provider looks the tool up in the instance's last MCP report; everything else is the runtime attachment that offers it, or the base layer. Failure fallbacks keep today's title (the name the model called) and fill tool from the publication when there is one.
    • Approval requests carry a required tool_call_id, which ApprovalRequest::new takes. The TUI finds an approval's call by it instead of matching operation fingerprints.
    • Background state. PersistedToolResult.background is { state, by, job? }, state an open job | self_reporting (the two immediate results the engine commits today: a background job, or work that reports itself), and job present exactly in the job state. The immediate result's metadata is now null, so the model-visible tool result JSON no longer repeats the job and actor its output text already states.     • Clients. The TUI renders user content as today for text and a file part as its 📎 name · type · size chip (escaped in the markdown row), renders every display block through display_text (text blocks as today, other kinds by to_text), applies progress deltas through LiveDisplay, reads the tool name for its remaining name special cases from presentation.tool.name, and reads background.     Phase D¶

    • Stored events are information. No type reachable from StoredEvent denies unknown fields any more, the envelope and the loader's first line included, and the events surface reports no additionalProperties: false. ModelFinishReason reads a reason it does not know as other, and ToolEmittedContent and the required model selection ignore extra members; their schemas drop additionalProperties: false with them. The flattened tool-call start and termination, the internal-summary checkpoint, and the checkpoint commit lose it too, though the checker saw them only inlined. Client notification types (TransientEvent, EventSubscriptionMessage, output deltas) are left to phase F.
    • Strict commands. The server checks params against the method's published schema before decoding them (cookie_agent_protocol::strict): every member of an object must be a property the schema lists for it, through $ref, allOf, and the oneOf/anyOf branch a value fits (by type, required members, and const tags); an object that lists no properties is free-form. A refusal is -32602 with the registry's unknown_field data and the JSON path in field, so RunSelection, PermissionRule, OperationFingerprint, and ApprovalFeedback stay strict in run.start, session.create, approval.respond, and the rest. Unlike a deserializer wrapper (serde_ignored), it sees through internally tagged enums, which serde buffers. The goal_update tool reads its arguments the same way (parse_args_strict), and its model-facing schema stays closed (strict_schema), since GoalItem is also history. ToolOutputDeclaration in a runtime's or plugin's tool list is information per 9.1 and is not checked.
    • Locating a bad leaf. serde_path_to_error cannot see into an internally tagged enum, whose content serde buffers before decoding it, and every payload is one: it reports . for any error inside a payload. The best-effort decoder still asks it first, and otherwise reads the value serde's error names (invalid type: integer 42, unknown variant, invalid length, missing field) and tries only the leaves equal to it, at most 16, with one decode each. Degrading is therefore linear in the payload's size. A failure whose message names no value (a type's own validation) is no longer degraded by trial and error: the record is skipped with its diagnostic.
    • Quarantine. A load validates the records it decoded as before, but a record that fails a check (a cross-event one, a duplicate identity, a record-local run rule, a timestamp going back) is left out instead of failing the open: its identity is tainted exactly as a skipped line's is (ValidationTaint::mark_event; a record past the per-run phase-taint bound taints everything after it), so every record whose prerequisite it was is excused by tainted_prerequisite like a dependent of a skipped line. The failed check may have changed the validation state, so the state is rebuilt from the records kept so far with the new taint; earlier records validate as they did, since taint only reaches later ones. The log keeps the quarantine taint as its load damage, so appends (still strict), reverts, and forks see it. The first 64 quarantined records each get a quarantined: … diagnostic, and one more counts the rest; only session_created still fails the open.
    • A broken sequence. A record whose sequence does not advance ends the readable log at that line, with a diagnostic. The log is render-only by the same mechanism as an unknown state event (EventLog::is_render_only), and every change fails with EventLogError::SequenceBroken; the server answers it as an engine error until phase F gives it a code. Nothing is cut from the file.
    • Delegations. A stored delegation record the delegation store cannot verify (one the log's validation accepts, such as a reservation resuming a session other than its child) makes that delegation unrecoverable: its entry is dropped, its later records are ignored, and a diagnostic is printed; the tree loads.
    • Writer-only size caps. The engine reads a log inside cookie_agent_protocol::read_stored_history, which turns off the caps a writer keeps to that no schema states: a tool result's output (2 MiB), metadata (2 MiB), and display budget (64 KiB), a model turn's serialized size (8 MiB), native replay payloads, a diagnostic's detail (16 KiB), and the text total of a delegation's seeded context (64 KiB); the delegation store applies that one only to new reservations. Bounds a schema states (lengths, item counts) are the type's contract and stay in the decoders (7.1). The checks that served only old logs and C2 already removed (wire_resolved, fingerprint recomputation, built-in agent IDs) were confirmed gone from the load path.
    • Raw lines. A log keeps the buffer its file was read into (shared, never copied) with each sequenced line's offsets (RawLines). The memory cost is the file's size plus a few words per line for every log read from disk, for as long as the log is in memory; a log built in memory keeps none. A truncation drops the lines past the cut, so a reused sequence never answers with an old line. Rewriting a log whole (EventLog::write_whole: a fork, or a buffered session's first persistence, which never has raw lines) copies every line it read as it was read: a record read in full too, since it may hold members a newer minor added, as well as a skipped, quarantined, or degraded one. The copy is parsed as JSON and only its envelope's session_id is set to the new session's (a fork changes nothing else in the records it copies); only records appended since the read are serialized. This replaces the first version of this phase, which re-serialized records read in full and so dropped their unknown members. A fork carries its source's raw lines and load damage through the cut, and may cut after a line the source left out (the tip is the physical one).
    • Artifact liveness. One scanner over JSON values (collect_artifact_references) counts every artifact://sha256/<digest> in a string, inside longer text too, and every object with a 64-hex sha256, a byte_length, and a media_type (an ArtifactRef, such as a user file part). Revert sweeps, the deleted children of a revert, tree liveness, and fork linking scan a log through artifact_references_in_log: its raw lines as read, and the records written since as they serialize. Manifest expansion uses the same scanner.
    • Metadata caches. A root's or a filed child's metadata that does not decode, or names another session, is rebuilt by folding the session's log (read through the read-only log cache) and is rewritten only when this process owns the session; a listing, an index entry's check, and a child's adoption all go through it. A missing metadata still means a directory being published and is skipped. subagents/index.json rebuilds as before.
    • Conversion. crates/engine/src/events/convert/mod.rs holds the registry (CONVERTERS, empty in this build) and the chain: each step is a fn(Vec<Value>) -> Result<Vec<Value>, String> over a log's JSON lines, and the chain stamps history_format on session_created after each step. A line that is not JSON is left out of a converted log (its backup keeps it), as is a torn final record. The test-only step v0_to_v1.rs (format 0 is format 1 with a diagnostic's message stored as text; a line carrying convert_fails makes it fail) lives in a test-only table, so no constant needed overriding. A read-only open converts in memory, and such a log is never taken over by an owned open. SessionStore::hold_tree converts the tree on disk right after taking its lock (session::convert::convert_tree): each log of an older format is converted to events.jsonl.convert.tmp and its metadata folded from it to metadata.convert.tmp, both synced; any failure removes them all and fails the take, leaving the tree unlocked. Then each original gets a second name, events.jsonl.v<N>.bak (a hard link, or a synced copy where links fail), so events.jsonl names a complete log at every moment, and the staged files are renamed into place. subagents/index.json is removed rather than converted: it caches client summaries, not history, and the next tree load rebuilds it. An owned open of a log still in an older format fails as corrupt instead of converting one log alone. EventLogError::UnsupportedHistoryFormat is gone: a lower format without a converter (none exists) fails as the unsupported-era corrupt-log error, like a missing one.
    • cookie sessions upgrade [--all] is a new sessions command group. It converts every tree of the current directory's work dir, or of every work dir, taking each tree's lock as an owned open would (a tree another process holds is skipped and reported), prints one line per tree converted or session not converted and a summary, and exits nonzero when a session could not be converted (session::upgrade_sessions, which also reports the logs left as they are because no conversion exists).

    Phase E¶

    Step 1: handshakes, tolerance, and errors on the plugin and runtime protocols.

    • Compatibility before the freeze. SemVer::is_compatible_with requires equal majors and, while the major is 0, equal minors too (semver's 0.x convention): every pre-freeze minor may break the wire. The patch never matters. negotiate_version reads the peer's version from the raw JSON first; another major or 0.x minor, or an integer from a build before semver versions, is refused with unsupported_protocol naming both versions, and a hello without a readable version with invalid_params (data.field = protocol_version). The runtime result keeps producer_messaging as a member, as 9.1 says it keeps its members, though by 3.2 it would be a feature. The daemon sends runtimes no features: it always accepts their producer messages, so none depends on configuration. The SDK exposes the daemon as PluginContext::daemon() (DaemonInfo: version, engine_version, features, interception timeout) and refuses requests before plugin/initialize with not_initialized (a second one with already_initialized), so handlers never run without it. The fake plugin echoes the daemon's version unless a test sets one.

    • Provider hooks. provider_before_request, provider_after_response, their params and results, the SDK's builder methods, and the model manager's provider_request_payload and request_from_provider_payload (used only by them) are gone. PLUGIN_PROTOCOL_VERSION is 0.4.0.
    • Hook names. capabilities.intercept is a list of { hook, on_error }, hook a snake-case HookName (at most 64 bytes, the diagnostic.kind grammar) and on_error allow (when absent) or block. ExtensionInterceptionHook is no longer a wire type: it is the daemon's and the SDK's list of the hooks this build dispatches (ALL, name, method, from_name, from_method). The daemon drops, before decoding the initialize result, an entry it cannot read, one naming a hook it does not dispatch, and one repeating a hook (the first wins), each with a note in the plugin's status. on_error is open, and a value this build does not know reads as block, the stricter one. PluginInfo.hooks is the list of hook names, so the client protocol is 50 (0.50.0); the status does not show on_error.
    • What block blocks. A failure is a timeout, a plugin that is not connected or exits, an error answer, or an answer that does not decode (an unknown action included). An answer that decodes but cannot be applied (an invalid replacement, an added file) is not a failure: it is skipped with an invalid_modification diagnostic whatever on_error says, as before, and the hooks that already refused such answers (tool_before_call argument changes) still do. A blocking failure stops later plugins, like a block. Per hook: tool_before_call fails the call before it runs ("Tool call blocked: …"); tool_after_result fails the call after it ran and withholds its output ("Tool result withheld: …"); agent_before_start, user_before_input, and a run's model_before_select refuse the request before anything of the run is recorded; a fallback's model_before_select ends the run without falling back, with the failure as the run's error; model_before_request and message_end record attempt_abandoned without a model_error, release the attempt's producer claim, and fail the run (no retry and no fallback: the failure is not the model's); session_before_compact refuses session.compact, and an automatic compaction treats it like a plugin's cancel (the request goes on uncompacted); session_before_fork and session_before_revert refuse the operation. A refusal is EngineError::PluginHookFailed(PluginHookFailure { plugin, hook, reason }), which the server answers with the registry's plugin_hook_failed (plugin, hook, and the failure as detail). The message names no field, because the client protocol's faults still carry a static message until phase F. The diagnostic keeps its failure kind (interception_timeout, interception_crash, interception_rejected) and its message leads with the outcome ("the <hook> hook failed, so the operation was blocked (on_error = block): it timed out"), since a long reason is cut at 200 characters. The SDK's on_hook_error(hook, on_error) sets the policy; the build fails when it names a hook without a handler.
    • Hook views. crates/engine/src/plugin/hook_views.rs holds every conversion. model_before_request sends HookHistoryMessage { role, content: [Open<HookContentPart>] } and model: HookModel { provider_id, model_id, adapter } (adapter the AdaptorId label, as tool turn contexts carry it, not the oven adapter of PersistedModelBinding). A file's ArtifactRef is computed from the bytes the request holds (its SHA-256 and length); a URL or provider-reference file, reasoning, system and user extension parts, sources, and approvals are left out of the view, and a provider-run tool result in an assistant message shows as a tool_result. A tool result's text joins its text and JSON values with newlines, and its files follow it as file parts, which a rebuilt tool message attaches to the result before them. A replacement message equal to the view of an original turn is that turn, unchanged (the first unused match, so a plugin may drop or reorder messages without losing replay state); any other is rebuilt from its parts, a rebuilt assistant turn with empty usage, no replay, and tool_calls or stop as its finish reason, and a file part must name a file of the request by digest. message_end sends [Open<HookAssistantPart>]: text, reasoning, tool_call, and file (artifact-backed files only). A replacement part equal to an original part's view is that part with its metadata (provider_item_id, raw_input, signatures), and the parts the view leaves out follow the visible part they followed, or end the message when that part was not returned. Unknown parts are refused in both.
    • User input. user_before_input sends content: UserContent and a transform answers content (was new_text). Every file part of the answer must equal one of the input's (ArtifactRef equality: a renamed file is another file), the answer must not be blank, and an unknown part is refused. The engine's input is still text until phase F: it wraps the text as one part and takes the result's as_plain_text.
    • Prompt context. ExtensionPromptContext { input, system_prompt, injected_messages } replaces the json! object, whose session_id repeated the params' own. input is null for a run a producer's message starts (it has no user input).
    • Event patterns. capabilities.subscribe_events and PluginInfo.subscribe_events are lists of EventPattern (a type, a prefix ending in *, or *; empty for none). The daemon skips a pattern it cannot read with a note, as it does intercept entries. A payload is serialized once when any connected plugin subscribes to anything, and its type is read back from that JSON for matching; the serialized payload is what plugin/event carries, so a plugin that subscribes narrowly costs one serialization per event, as a subscriber always did. Live-only events (text_delta, reasoning_delta, internal_agent_text_delta, tool_call_progress, native_compaction_started/_finished) were delivered before and still are: patterns select them by type like stored events, so * includes them and run_* does not. Their seq is the sequence of the durable event they follow. The SDK's on_event subscribes to * unless event_patterns([...]) narrows it.
    • Tests. fake_plugin.py gained FIXTURE_FAIL_WHEN (a call fails only when its params have the given members, so a fallback's model_before_select can fail while the run's own succeeds) and FIXTURE_ECHO_REPLACEMENT (answers model_before_request and message_end with what they were sent). runtime/tests/hook_failures.rs runs every hook with each failure under block and allow.

    • Prepared calls.     • Approval identity. The daemon builds it (engine::permissions::identity::declared_operation) for every call its provider only declares (PreparedTool::declared): runtime tools, the coding runtime's own included, plugin tools, and MCP tools, in runtimes and in the global runtime. The daemon's base tools still state theirs (PreparedTool::new), since the daemon owns them. apply_permission_resource sets it, from the tool's resolved ToolIdentity and its origin, for a call and for a tool_before_call modification alike. The recipe: the digest of the normalized arguments' canonical JSON; one capability, the permission action (tool for a tool that needs none) with operation <source's tool name>:call (lowercased, other characters as _); one resource, <action>:<SHA-256 of the resource> (<action>:unscoped without one), bound to the tool's identity (its resolved source and source name, never what the peer reports) and the resource; and an execution context of the tool's identity and the origin's context bytes. A peer's operation member is ignored as information, so no peer can state another tool's identity (identity_tests.rs; the plugin tool test sends a forged one). The approval semantics of the built-in tools are kept with one rule the daemon now applies by action: a command's (PermissionAction::is_command, bash) and a path action's binding is process-local, a command approves by command prefix, and every other binding is restart-stable and exact, so read, write, edit, and bash are still never granted for a tree and webfetch and MCP tools still may be. What differs: fingerprints changed bytes (grants recorded by earlier builds no longer match); the binding no longer covers a file's or the shell's identity, which revalidation still checks before a call runs, so a repeated call on a path whose file was replaced counts as the same operation; bash's normalized arguments gained timeout, so its identity still tells timeouts apart; webfetch's context is now its instance, not every runtime's webfetch, which narrows its tree grants; a plugin's tool of any other action is now restart-stable and so may be granted for a tree (the SDK and the fixture used process-local bindings); and the approval reviewer's prior decisions read <tool>:call where they read bash:execute or read:read.
    • Execute results. ExecuteOutcome::Completed(ToolResult) flattens the result under status: completed: output, and optional title, display, metadata, attachments, additional_messages, and failed. The daemon builds the stored result (ToolResultExt::into_completion): a result without a title is titled with the tool's source name, and a single output without display shows its text, as ToolCompletion::single does. The coding runtime sends ToolResultExt::of(completion). background and retained_output stay the daemon's.
    • Unknown display blocks are dropped with a diagnostic whose source is plugin:<name> or runtime:<id> (an MCP tool of a runtime names the runtime; anything else engine:tools), kind unknown_display_block (PeerDiagnosticKind), and detail { tool, part, kinds }: from a presentation, from a result (taken from the executor's completion before capture, so detached calls are covered), and from progress, once per call and part. tool/progress is a command, which E1's strict check refuses an unknown tag in; the daemon instead removes a replace's unknown blocks before the check (runtime_protocol::take_unknown_progress_blocks), since a display block is only shown. There is no since table: every kind exists in 0.x, a peer's newer kind is dropped as unknown, and phase F downgrades per client.
    • SDK. ToolOutput is a #[non_exhaustive] builder (success, error, text, title, display, displays, metadata, attachment, failed, read back with output_text and is_failed, as the builder methods take the field names). An attachment's bytes travel in media (the SDK depends on base64). prepare_presentation(tool, f) takes a PrepareCall { name, arguments, resource } and returns a Presentation builder (title, hint, primary argument, arguments, preview); the default is the tool's name and its resource, and the build fails for a tool not registered.     • Schemas. Every plugin and runtime method was already in the generated set; the new types are reached from their roots. scripts/build-docs.sh copies crates/protocol/compat/{plugin,runtime} to docs/site/schemas/ (ignored by git), and reference/schemas.md links them.
    • Reference plugin. examples/plugins/python/ holds cookie_plugin.py, a single-threaded helper (it keeps what arrives while a handler waits for an answer), reference_plugin.py, and check_reference_plugin.py, which plays the daemon through a scripted conversation and validates every message both ways against the published schemas with a standard-library validator (types, properties, required, additionalProperties, $ref, oneOf, anyOf, allOf, enum, const, item and length bounds, numeric bounds, patterns with \p{Cc} and \p{Cf}, and x-open).     Phase F¶

    Step 1: the client protocol (section 10, without media). CLIENT_PROTOCOL_VERSION is 0.51.0; the exact numeric ProtocolVersion, PROTOCOL_VERSION, RuntimeSnapshotSchemaVersion, RUNTIME_SNAPSHOT_SCHEMA_VERSION, and exact_numeric_wire_type! are gone.

    • Handshake. ClientHello { protocol_version, client, token?, features } is a command (strict); ServerHello { protocol_version, engine_version, origin, machine_id?, features } is information. The daemon reads the version with negotiate_version before decoding the rest; a refused version leaves the connection open for another handshake, within the authentication deadline. engine_version comes from ServerProtocol::engine_version. The client also checks the reply's version and keeps it (Client::daemon_version); before the freeze the minors are equal, so no method or member is gated yet. No feature is defined on either side.
    • Authentication. protocol::serve takes an Authentication: Authenticated (an in-process connection, or an upgrade whose Authorization header carried the token) or Token(token). Before a Token connection's handshake carries the token, only handshake is answered (-32003 otherwise); a wrong or missing token is answered with -32003 and closes the connection; AUTHENTICATION_DEADLINE (10 s) closes one that has not authenticated, and being answered does not extend it. An authenticated connection that has not handshaken gets -32001. A token in the handshake of a connection the header authenticated is ignored. A wrong Authorization header is still refused at the upgrade with HTTP 401, since it is a claim the daemon can check before upgrading. /runtime keeps header authentication and refuses any Origin.
    • Origins. [server] allowed_origins entries must equal their URL's ASCII origin serialization, so an entry is spelled as a browser sends it (lowercase, no default port, no path or trailing slash); * inside an entry is refused, as patterns are not supported.     Step 2: user media input (11.1 to 11.5). CLIENT_PROTOCOL_VERSION is 0.52.0.

    • Content in the params. run.start, run.steer, and session.submit_input take content: UserContent, and a recalled session.recall_input returns content; QueuedInput already carried it. The params stay strict through their parts: a member an ArtifactRef does not list is unknown_field at its path (content[1].artifact.width).     • Advertised limits. Every AvailableModelDescriptor carries a required input_media (at most 16 entries, one per kind) from runtime_api::media::user_input_media(family, capabilities). It shares one table with tool_input_media (deliverable_media over family_delivery): a kind counts for a user turn whenever the family delivers it at all, in a tool result or a user message. mime_types are the model's types (exact, or a prefix ending in *, with the video aliases folded) that an upload can be recognized as, so a type the daemon cannot recognize is never offered; Matroska is left out, since telling it from WebM needs a file extension and uploads ignore names. max_bytes is the lowest of the model's, the family's, and the attachment cap; images carry max_dimension 16384 and max_pixels 16 Mi, the validation caps.     • Uploads. artifact.upload.finish returns { artifact: ArtifactRef, image? } rather than the reference's members with image beside them: a client puts artifact into a file part as it is, where image would be a member commands refuse. UploadId is upl_<uuid>. begin publishes a session still buffered in memory, because its tree's store lives in the session directory, which exists only from then; a byte_length above 25 MiB is media_too_large with kind: file. Chunks stream into .upload-<uuid>.tmp in the tree's store and are hashed as they arrive; finish reads the file once (at most 25 MiB) to validate it with validate_upload, which recognizes the type from the content alone, applies the attachment caps and container checks of validate_attachment, and reports an image's size; an image over the dimension or pixel caps is media_too_large with its width and height, unrecognized content media_type_unsupported with application/octet-stream, and a malformed container media_type_unsupported with the type it started like. Three codes were added: upload_offset_mismatch { expected_offset } (a gap or a repeat), upload_size_mismatch { byte_length, received } (a chunk past the end, or a finish before the end), and too_many_uploads { max_uploads }. A refused chunk and an early finish keep the upload; a digest or content refusal drops it. A connection has at most 8 uploads in progress (MAX_UPLOADS_PER_CONNECTION), each a temporary file and no memory; the server's connected hook drops them when the connection's shutdown token fires. Requests run concurrently, so chunks a client pipelines can arrive out of order: the reference says to send each after the previous one's answer. Uploads in progress are in memory, so a restart forgets them and their temporary files stay behind.
    • Leases, pins, and why a sweep cannot race a submit. One lock (UploadState::leases) holds the leases (tree and digest to expiry), the pins admission takes, and every deletion that could remove an input's artifact. finish publishes the blob and leases it for an hour under that lock. Admission pins each artifact an input names and checks that the store holds it, under the lock, then keeps the pins (PinnedArtifacts) until the event naming them is written. The lease sweep (each janitor tick, on a blocking thread) takes the lock, picks leases past their expiry with no pin, skips everything while a capture is publishing or a session of the tree is running, and deletes only digests no log of the tree references (D's raw scanner, which counts ArtifactRef objects); each such lease ends whether its blob was deleted or is now referenced. A revert's sweep takes the same lock and keeps every leased or pinned digest. So a sweep either ran first, and admission finds the blob gone (artifact_not_found), or it runs later and finds it pinned or referenced. Leases are in memory, so a restart forgets them: an upload no event referenced then stays in the store, as an orphan of a failed revert sweep does. A reverted reference leaves the blob to its lease; a fork links it into the new tree like any referenced artifact.
    • Reading. artifact.read verifies a blob's digest when it first opens it and keeps the handle in its own verified-handle cache, so a large artifact read range by range is hashed once; a removal evicts it. media_type is the type recognized from the content, else text/plain when the first 16 KiB are UTF-8 (a character cut at the end allowed), else application/octet-stream. An offset past the end is invalid_params; one at the end returns no data.
    • Admission. The model of the run is the frozen chain's first entry: at run.start after the fallback continuation is applied, for a steer the running run's (a later fallback gets placeholders), and for a queued input the model of the selection it carries, looked up in the current catalog; the run the queue later starts is admitted again with what it actually runs, and a refusal then voids the queue like any failed start. The accepted media are that model's catalog input_media; a model the catalog does not list accepts none. Kind, type, byte, and count checks come first, then the pins, then each blob is read (through the verified attachment cache model history uses next) and validated: content that is not the type its reference states is artifact_not_found, content that is no media at all media_type_unsupported, and an image over max_dimension or max_pixels media_too_large with its size. A type the model does not list is media_type_unsupported (the kind is accepted, so media_unsupported would mislead). Admission runs after user_before_input, on the content that will be recorded, and before anything of the run is.
    • Media fit. media::fit_media runs on every model request before both elision passes (and again after model_before_request, like elision) and in native compaction's request. A user or emitted user message's file and an assistant file fit when the model's user_input_media takes their kind and type within the byte limit; a tool result's file fits only when its tool_input_media entry delivers the kind in a tool result, since a family that carries it in user messages cannot carry it there. The placeholder is [<kind> omitted: <reason> (<filename>, <size>)] with <kind> image, PDF, audio, or video and the reason <model> does not accept <kind plural>, <model> does not accept <media type>, larger than the <limit> <model> accepts, or <model> does not accept <kind plural> in tool results; a missing filename or size is left out. Files that are no media kind are left alone. The compaction summarizer is an internal agent, whose requests already replace every file with ⟦elided media attachment: <type>⟧, so it keeps that wording rather than the fit's.
    • Liveness. Nothing new was needed: D's scanner already counts every ArtifactRef object, the input-lane events' file parts included. The engine test uploads, submits to a fake provider that receives the image, forks (the fork's tree has the blob), reverts past the submit (the lease keeps the blob), and sweeps after the lease (the root's copy goes, the fork's stays).

    Phase G¶

    Step 1: every built-in tool emits typed presentation and display (12.5). No wire shape changed, so no protocol version moved; no block kind was added.

    • Prepare-time presentation. A provider that knows how to show a call only once it prepared it (a diff of the file it read) attaches the presentation to the call (PreparedTool::with_presentation). The host takes a PreparedDeclaration's presentation first, then the prepared one, then ToolProvider::presentation; the coding runtime's server sends the prepared one as PreparedCall.presentation. A call that fails to prepare is shown by ToolProvider::presentation, which every built-in tool now overrides with its hint, human title, and arguments. Helpers: DisplayBlock::{markdown, code, key_value, is_cut, set_full}, PreparedPresentation::{with_hint, with_arguments, with_preview}, ToolAttachment::artifact_ref, and runtime_api::text_head (the first lines of a long text within a byte bound, so a fit measures little).
    • Titles. Presentation titles are human (Edit <path>, Write <path>, Read <path>, Run `<command>` cut to 60 characters, Fetch <url>, Delegate to <agent>, Read subagent <session>, Load skill <name>, Read goal, Update goal checklist, Message <to>, Read artifact <12 hex>, Stop <job>; an MCP tool keeps its published name). primary_argument is unchanged. Result titles are not: the model reads them with the metadata, so they, the output, and the metadata are exactly what they were.
    • edit's diff is built from the replaced byte ranges at prepare (on the text preparation read, which in a same-file batch is the text the previous edit leaves) and again at execute. Each range is widened to the whole lines from the line holding its start to the end of the line holding its end (so an oldString ending in a newline also takes the next line, and removing a line break shows the two joined lines); ranges whose widened lines overlap are one change, and lines the old and new text share at either end become context. write diffs its own line slices with similar::capture_diff_slices_deadline (Myers, one-second deadline), since similar's line tokenizer also splits on a lone \r. Both feed one hunk builder: five lines of context, and two changes share a hunk when at most ten unchanged lines separate them (their context overlaps or touches, so no line between two hunks is skipped). A side with no lines in a hunk starts at the line before it, 0 at the top of the file (a created file's hunk is -0,0 +1,N), as unified diffs number it. similar 2.7.0 was already locked through insta; the coding runtime takes it without default features.
    • write's sides. Preparation now reads the file there (a file it cannot read counts no lines), and execution reads it again right before writing, so the result diffs against what the write replaced. A target that was absent at preparation is created at execution too; a file that appeared there in between is replaced without a diff of it. A side over 1 MiB or not UTF-8 gives a diff without hunks whose counts are each side's newline-separated lines (a large old file is counted while streamed, not held).
    • full. A block is cut to the budget less 1 KiB, the room its full needs. An executed edit or write whose diff was cut retains the uncut diff's to_text (unified-diff text) as text/plain named <file>.diff; the coding runtime sends its bytes with the reply like an attachment's. A preview has no store to retain it in, so a cut preview carries only omitted. A cut terminal block gets full from the daemon when it commits the call's retained output: the first declared stream kept as an artifact (stdout, then stderr), text/plain, named after the stream, and only when the display still fits its budget with it. There is no merged artifact to name, and when no stream outgrew its preview the model's output holds everything, so full is absent. A read excerpt has no full: its page is not retained (read opts out of retention) and the file itself is the complete content.
    • bash. The display is one terminal block of segments in read order with exit_code, replacing the text block with its Exit status: N line and [display truncated] marker. Output is sanitized with sanitize_terminal_text as it is read; an escape sequence a read ends inside of (at most 256 bytes) is held for the next read, for the output as well as the display, so a colour split across two reads reaches both whole. Progress appends each chunk to block 0 with its stream, cut between SGR sequences. The block keeps at most 64 KiB of output, counting the lines after it in omitted_lines (a line the cap splits counts once), and the budget fit cuts by whole lines from there, keeping the head.
    • read. The excerpt holds the page's lines as the output numbers them, without the numbers, up to 64 KiB of text; a directory page is a table of name and type (file or directory); a media read shows media with the file name as alt, whether the attachment rides on the result or in the following user message.
    • webfetch. The body excerpt is its first lines within 24 KiB (the start of the first line when it is longer), so even a body of quotes fits beside the response block once escaped; text/markdown bodies are markdown. The response block also says truncated: yes for an over-cap body.
    • MCP. structured_content the text does not already hold is shown as json and also stays in metadata.mcp.structured_content: the model reads metadata, so moving it out would change what the model sees. metadata.mcp.is_error stays too (the executor reads it). Consecutive text parts are one text block joined as the output joins them, so a text-only result is still stored as a display_span.
    • Base tools. Arguments are key_value blocks. delegate_subagent's include the prompt as an entry (a multi-line value). A delegation's markdown is the subagent's whole final message (up to 48 KiB, then the budget), not the model's bounded preview; a cancelled or failed delegation shows its session_ref, when it has a session, and its output as text; the immediate result of a delegation moved to the background shows its output as before. skill shows the loaded skill and the goal tools a checklist as markdown; send_message, read_artifact, and stop_background keep their output as text. read_artifact's hint is file_read and stop_background's generic.
    • Disk encoding. display_span still covers a whole single text block and was not extended to terminal blocks: the span would need the segment's stream and the exit code beside it in the stored result, a shape change of PersistedToolResult on the client surface for a saving limited to a bash call with output on one stream. Results whose display is no longer their output's text (bash, read, webfetch, edit, write, skill, the goal and delegation tools) now store it beside the output, at most 64 KiB each. Phase H can revisit a terminal span before the freeze.

    Step 2: the TUI renders by block kind and hint (12.6) and attaches files (11.6); cookie run prints tool calls as text. No wire shape changed.

    • Removed special cases. tool_icon's name table and external_tool_icon (icons come from hint_icon: one per documented hint, the hammer for generic, an unknown hint, or none), abbreviate_tool_argument (every argument cuts at the right edge), ParsedToolArguments, display_tool_arguments, the bash title expansion, parse_read_output and render_read_output, tool_diff with its pseudo-diffs, is_unified_diff, approval_operation_preview with its $ command rows, the bash hero-line rule, the delegate_subagent check in the reducer (a start whose hint is delegate counts as agent activity, so get_subagent_result now counts too), and the permission panel's action icons keyed by tool names (an action maps to the hint its built-in tools carry). IndexedToolCall lost the tool's name. The only built-in tool name left in crates/tui/src outside tests is "bash" as the syntax name normalized_language maps sh to. Background state was already typed (C3).
    • Call state. ToolCallState holds the result's display, a failure line, the running call's progress message, the LiveDisplay, and loaded full content, replacing detail, has_output_chunks, and operation_fingerprint. A call that did not complete shows its result's display when it has one, else what it streamed, else its result's output as text; the old rule that put a failed call's model output ahead of its display is gone. The model call: … line a running call showed is gone.
    • Header. The title, then primary_argument unless the title already shows it, whole or cut before a … (at least 8 characters of it), since 12.5's titles name their argument (Run `ls`, Edit src/main.rs). A running call's progress message follows the title in the collapsed row and is the first output row when expanded.
    • Panel. The presentation's argument blocks show under the arguments label at every event level (48 rows, 4 KiB); the raw arguments stay a info/debug fallback for a call without argument blocks. Blocks follow, one blank row apart, from one budget (64 rows/8 KiB collapsed, 1024/128 KiB expanded): text as is; markdown through the transcript's renderer; code, file_excerpt, and json as numbered or plain code rows highlighted by language (an excerpt or diff without one by its path's extension; json always), an excerpt under a path · lines a–b of N header; diff under created|modified|deleted|renamed path · +A -R (· preview as of prepare), each hunk under its @@ header with the file line number (the new one for context rows) and a +/- marker in the gutter on the diff tints, a hunk-less diff as the header alone, and … N more hunks (M lines) not shown; terminal with SGR mapped to styles (basic, bright, 256-colour, and RGB colours fitted to the theme's colour level, none in mono; bold, dim, italic, underline, reverse, strike; each stream keeps its own rendition across lines; stderr in the warning tone under its own colours; any other escape dropped) and exit code N (failure tone when not zero) as a row the budget always keeps; key_value with keys aligned (at most 24 columns) and multi-line values hanging; table with columns aligned (cells at most 40 columns); media as its chip and alt; link as label and <url>; session_ref as a ↗ session … row whose click opens the session (watch_session); an unknown block as nothing. Every cut block counts its omitted_* units.
    • Full content. A cut block with full adds click to load the full output (size). The click reads one artifact.read chunk (at most 1 MiB, so a longer artifact shows its start and says so), expands the call's output for the larger budget, and keeps the text on the call (FullContent) until the click on ▴ full output · click to show the cut display puts it away or the call's result replaces it. The text replaces the block's cut rows: a diff's is parsed as the unified diff 12.5 retains, a terminal's is drawn as stdout with its SGR, an excerpt's numbered from its start_line. A failed read says why and offers a retry. Loaded content is view state, so a rebuild from history drops it.
    • Approvals. The panel's hero is the hint icon, the title, and the header argument, then the presentation's argument blocks and its preview, drawn by the same block renderer and wrapped to the panel; the request's resources show when the presentation has neither, as before.
    • Attachments. Commands run only from the palette, so /attach (aliases file, image) is a palette entry with a path step, listed only while the selected (draft) model's input_media is nonempty; the step's placeholder names the kinds. Before reading, a path that is no file, a model that takes nothing, and a file larger than the largest max_bytes are refused. The file is then read and checked with runtime_api::media::validate_upload (the daemon's own recognizer, so the TUI now depends on cookie_agent_runtime_api) against the entry of its kind: refused kinds name the accepted ones, and byte, side, and pixel limits are named. Chunks go one after another (artifact.upload.cancel on a refused chunk), and a media_too_large from the daemon shows its limit; nothing is downscaled. A new-session draft creates its session first. An upload that finishes after the view moved to another session is not attached, since its blob is in the first session's tree. Chips sit on the composer's bottom border (as many as fit, then +N); Backspace with the cursor at the start of the draft removes the newest. A draft of attachments alone is sent. A paste that is exactly one existing absolute, ~/, or file:// path (quoted, or with backslash escapes) opens a confirm; Cancel types the paste. Owed input is a ComposerInput { text, files } everywhere text was (VoidedInput, PendingInput, the submit and recall updates), so recalled, voided, and failed-to-send input restores its files as chips, deduplicated by digest. A revert still restores the message's text only, as the menu captured it.
    • Job control. Ctrl+Z (Unix) sets pending_suspend; the event loop drops its event stream, restores the terminal like suspend_terminal, stops the process group with SIGTSTP (as vim and neovim do), and on return re-enters the modes like resume_terminal, clears, and redraws. A SIGCONT listener re-enters the same way (leaving the modes first, so the keyboard enhancement stack is never pushed twice) for a stop the TUI did not ask for; JobControl skips the one SIGCONT that follows its own Ctrl+Z. The cursor-position tolerance in emoji_backend.rs is unchanged. Elsewhere than Unix, Ctrl+Z does nothing.
    • CLI. --verbose in text and none modes writes, per finished call, cookie run: tool <title> (with the outcome when it did not complete) and the first eight lines of its display's display_text, indented, to standard error; standard output, the failure diagnostics, and JSON mode are unchanged.
    • Coding runtime. BuiltinTools did not forward ToolProvider::presentation, so a bash, read, or webfetch call (and an edit or write that failed to prepare) reached clients as its bare name with no hint or argument blocks; it now forwards to each tool.
    • Docs. The TUI's behavior is documented in clients/tui.md (composer, attachments, Ctrl+Z, palette, transcript details, approvals, live output) and sessions/media.md; the docs/site/tui/ pages cover tui.toml only and gained nothing.
    • For phase H. The TUI tests build display blocks, presentations, and attachment flows from protocol types (tests/display_blocks.rs, tests/diffs.rs, tests/attachments.rs with answering_client, which scripts the daemon's answers); their request and event JSON could seed the client corpus. The golden logs should include a terminal block with SGR, a cut block with full, a session_ref, and a user input with a file part.

    Phase H¶

    The freeze: storage encoding, 1.0.0, the enforced checker, golden logs, corpora, and the compatibility policy.

    • Storage before the freeze. A session of eight tool calls against the coding runtime (four reads, one a 2000-line page of a 3630-line file, and five bash calls) stored 258,745 bytes of events.jsonl, 85,803 of them (33.2%) display that repeated the results' output: since phase G, read and bash display blocks are no longer single text blocks, which were the only ones display_span covered. The encoding is extended, and it is now what 12.3 says it is, a pure disk encoding: values serialize in it only inside cookie_agent_protocol::write_stored_history, which the event log's append and whole-file writes use, and decoding expands it, so clients, plugins, and runtimes always receive whole blocks (display is required on the wire, and display_span is gone from the client, plugin, and events schemas; until then the client received spans too). Besides the single whole text block's display_span, a block of display may store the text of a text, markdown, or code block, or of a terminal segment, as text_span: [start, end), and a file_excerpt's lines as lines_span: a range of output holding the lines one per line, each after its file line number and ": ", as read numbers them. The writer uses a span only for a text of at least 32 bytes found verbatim in the output (a terminal stream searches on from its previous segment), never inside a block of an unknown kind, and never for excerpt lines holding a newline, so expanding always gives the same text back. The same session then stored 173,810 bytes (33% less); its display took 862 (0.5%). A bash display cut to its budget is not in the output preview and stays inline. crate::stored_display holds the encoding; converters read logs with it (events::convert says so).
    • Versions. CLIENT_PROTOCOL_VERSION, PLUGIN_PROTOCOL_VERSION, and RUNTIME_PROTOCOL_VERSION are 1.0.0; HISTORY_FORMAT stays 1. SemVer::is_compatible_with compares majors only: the 0.x same-minor rule of E1 is gone, since no 0.x peer connects to a 1.x one anyway. The handshake tests of the server, the coding runtime, the remote runtime client, the plugin SDK, and the plugin host now connect peers of a newer minor and patch and refuse the next major, a 0.x build, and an integer version. The Python reference plugin speaks 1.0.0 with the same rule; the fake plugin echoes the daemon's version. The changelog's 1.0.0 entry summarizes the frozen contract and says that 0.x builds never interoperate with 1.x ones.
    • Checker. With the generated set at 1.0.0 against the 0.52.0 baselines, every rule enforced, the check found nothing to reject: no information type is closed any more, and a major bump covers every change. The regenerated baselines changed only their version files. The pre-freeze mode (exact-equality baselines, unenforced findings) is removed from check-compat.py, whose every surface is 1.x now; the mutation test's pre-freeze case became a check that a 0.x set is refused against a 1.x baseline, and the update is checked to leave a corpus/ directory beside the surfaces alone. The named fixture roots were unchanged. Experiments (reverted): an optional member added to ContextResult without a bump fails (runtime: the changes need a minor bump from 1.0.0); with RUNTIME_PROTOCOL_VERSION at 1.1.0 it passes; ContextResult.skipped removed with only that minor bump fails (needs a major bump ... field 'skipped' removed or renamed).
    • Golden logs. crates/engine/tests/fixtures/history/1/ holds six scenarios (about 800 KB), recorded by the ignored test record_golden_history (COOKIE_GOLDEN_HISTORY_OUT=<new dir>; it refuses a directory that exists) against fake OpenAI-compatible, Anthropic, and OpenAI Responses endpoints, the in-process coding runtime over the runtime protocol, the fake plugin, and the Python reference plugin: coding (reads of a file, a directory, an image, and a missing file; bash with SGR on both streams, a non-zero exit, a background job and its report, and output cut to the budget with full; a plugin tool's json, link, code, and key_value blocks; an edit approved once, a write rejected, a webfetch granted for the tree and then allowed by the grant, a skill; user input with an image and a video upload; the approval reviewer; a summary compaction and a run after it), delegation (foreground, background, and resumed delegation, get_subagent_result, send_message queued and steered, subagent reports, a goal whose pending reminder is discarded when the checklist completes, the reference plugin's tool, a call its hook blocks, its queued producer message, and user input steered into a running run and queued behind it), replay (signed Anthropic thinking replayed natively), native-compaction and native-compaction-fallback (OpenAI's compaction window, and the summary when it fails), and revert-fork (a fork, then a revert of the source). Every display-block kind occurs in a stored result. Each scenario is the session store's root directories as written (artifacts, children, caches; no lock files) and snapshot.json: per session the metadata, usage, model history (full and assembled), and the events as a client of this version receives them, recorded only where they differ from the stored record (a stored display range), so the snapshot does not repeat the log. Indented down to the sessions' members, one line per event. golden_history_reads_as_recorded opens a copy of every scenario of every format directory read-only (the tree's lock held elsewhere; the copy must stay byte-identical) and owned (Engine::resume), and compares: every member the snapshot records must read the same, members a newer build adds are allowed, and arrays keep their lengths. It writes nothing; a failure names the JSON paths and says the logs are frozen. golden_history_tolerates_what_a_newer_build_adds rewrites copies of coding and delegation as a newer build of format 1 could have written them (unknown envelope, payload, and result members, a display block of an unknown kind, and a final record of an unknown type): they read as recorded, the unknown block is not sent to clients, a skippable unknown record is skipped, a fork copies every unknown member and the unknown record, and an unknown state record opens the logs render-only (run.start refused) with one skipped event reported. The recorder's COOKIE_GOLDEN_HISTORY_ONLY names one scenario while a recorder is being written.
    • Not covered by the golden logs. Quarantine needs records a writer never produces, so phase D's synthetic tests keep covering it; raw preservation is covered by the future-data test. The goal tools are not called by the model: on the base layer, goal_get and goal_update declare path actions (read, write) on the relative resource goal:current, which no rule can match without a workspace, so policy denied them whatever the agent allowed; the recorder completes the goal through the API.     • A fork of a session that delegated is refused as a corrupt log ("delegation reservation ownership is invalid"): the fork copies the delegation_reserved records, whose parent_session_id names the source, and validates them against the fork's own ID.     • Approval records read tolerantly.

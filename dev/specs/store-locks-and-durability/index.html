    Session store locks and durability¶

    Status: approved (2026-10-31), with the user's decisions of 2026-10-31 in section 8. The measurement step shipped and its findings are in section 5.1. 4.1, 4.2, 4.4's heavy work before locks, and 4.5 are implemented (2026-10-31; notes in section 9), and so is 4.3 (client protocol 1.60.0, plugin protocol 1.32.0; notes at the end of 4.3); the rest of 4.4 is shelved. Follows responsive session loading, whose phase 1 removed the tree load from a replay's history pages but left the locks below in every session command's path.

    1. Problem¶

    Every command a session's actor runs goes through Engine::send_command (crates/engine/src/runtime/messaging/mailbox.rs): a replay's final page, but also a running agent's every append, tool result, and steer. It:

    1. takes residency_mutation, one tokio::sync::Mutex for the whole engine;
    2. under it, calls ensure_session_owned → SessionStore::begin_write, which completes the session's tree (ensure_tree_for) and then takes the store's mutation lock exclusively (lock_mutation) before begin_write_locked finds the session already owned and resident, as it nearly always is;
    3. only then spawns or finds the actor and sends.

    Appends hold the same mutation lock shared, with the session's slot, while they write and fdatasync the record (EventLogWriter::append). So:

    • Every command waits for every append in flight to sync, in every session, holding the engine-wide lock while it waits, so every other session's commands queue behind it. A waiting exclusive locker also makes new shared lockers wait, so appends stall too. On a busy disk a sync takes hundreds of milliseconds, and this convoys.
    • A cold open stops every writer. Opening a session that is not resident (begin_write_locked → open_owned_log) parses its whole log under the exclusive lock (0.2 s idle, over 1 s busy, for a 17 MB log), and loading its tree (every subagent's log) runs under the engine-wide lock. Meanwhile no agent anywhere appends.
    • The idle janitor holds the engine-wide lock while it drains a tree's actors before evicting it (evict_idle_roots_with, evict_idle_subagents_with).

    The number of syncs is not what hurts: their latency under those locks is. Measured on 2026-10-31, by strace -f -e trace=fsync,fdatasync on a scratch daemon and from the timestamps of the user's real logs (one sync per synced record):

    What Syncs
    A scripted turn (edit a file, run a check, reply; 37 events) 15 of the session log, about 18 more: the new session's directory and metadata, unread.json, memory's read bookkeeping, the model catalog's metadata, the edited file and its directory
    A real Claude Code (ACP) session, per run (31 runs) 262 of the session log; 56% are acp_session_updated
    The same session over time 0.11 a second while running on average, 6.7 a second in its busiest minute, 45 in its busiest second
    The whole store 12,000 to 23,000 a day; at most 92 in one second

    Most of a Claude Code session's records are the agent's live state rather than its history. Of its 9,813 records, 4,584 are acp_session_updated (29% of the log's bytes): 2,328 carry a tool call's refined presentation (3.1 MB; every one between the call's start and its end) and 2,223 the agent's context use (up to 468 in one run, none outside runs). The other fields (commands, options, notices, steering, and the rest) arrive about 35 times in all.

    Elsewhere, crons.json is synced with its directory on every cron fire, unread.json on every read or unread change, and the coding runtime's write and edit tools sync each file they write and its directory.

    2. Goals¶

    • No lock is held across a disk sync, a log parse, or a tree load.
    • A command to a session that is already open takes no engine-wide or store-wide lock.
    • One tree's cold open, tree load, or eviction never delays another tree.
    • Syncs only where recovery needs them (section 3).
    • The agent's live state stays out of the log (section 4.3).

    Not goals: the single-writer ownership model (owner.lock), or what recovery repairs. The history format changes only additively: an optional field on tool_call_terminated (section 4.3).

    3. What a crash may lose¶

    A sync matters only when the machine crashes or loses power: a record the daemon wrote survives the daemon's own crash, from the kernel's page cache. Today every record but six bookkeeping kinds is synced before it is published. The rule instead:

    1. The log stays a prefix. Everything up to the last sync is durable. Of the records after it, the kernel may write back any subset in any order; opening a log already cuts it at its first damaged line, so what survives is everything up to some point.
    2. Commit points sync before they take effect. A record that something outside the log acts on is synced before that action, and every record before it with it:
    3. tool_call_started, before the tool runs (and with it the model_turn_committed holding the call): a crash that lost them would let a resumed run ask the model again and repeat the side effect;
    4. tool_call_terminated, before the next model request: a crash that lost it would have recovery record a finished call as Interrupted, and the model, told "Tool interrupted; retained output is incomplete.", could run it again;
    5. user_input_submitted, and every other record a request's reply confirms, before that reply;
    6. permission grants and approval decisions, before the call they allow;
    7. delegation records, before the child they start;
    8. session_created, forks, reverts, deletion;
    9. run_finished, so a run always ends durable;
    10. every kind that is rare: syncing it costs nothing.
    11. Everything else rides along. The six bookkeeping kinds, model_turn_committed, and the stored acp_session_updated fields are not synced themselves. The next commit point covers them, or closing the log does (eviction, shutdown, release, as the writer's drop does today). Within a run the next commit point is seconds away; between runs only rare ACP fields can wait for the log to close.

    Recovery already treats the log's end as possibly short: open runs end as Interrupted, pending tool calls are terminated Interrupted, and nothing is re-run on its own.

    4. Design¶

    4.1 Syncs outside every lock¶

    EventLogWriter::append writes the record under the session's slot and the shared mutation lock, as now, so readers in this process see it at once. A commit point's sync runs after both are released, on a duplicate of the file's descriptor (fdatasync covers everything written to the file so far, whoever wrote it), and the record is published after it.

    A session publishes its records in order: a record appended while a commit point ahead of it is still syncing is published after that commit point. The append that records tool_call_started returns after its sync, so the tool starts only then. When a turn starts several tools at once, all their tool_call_started records are written first and one sync covers them.

    4.2 Which records sync¶

    syncs_on_append becomes an exhaustive match over the event kinds, with no catch-all, so a new kind does not build until someone decides whether it is a commit point. The classes are section 3's.

    Expected effect, from the counts in section 1: the Claude Code session syncs about once per tool call start and once per tool call end, plus a few records per run (inputs, run_finished): about 80 syncs per run instead of 262, none under a lock. A short turn changes less: the scripted one goes from 15 log syncs to about 12, since most of its records are once-per-run ones (the input, the run's start and end, memory, the title), which stay commit points.

    4.3 The agent's live state is not history¶

    ACP tool presentations and context use become live-only, like text deltas and tool progress:

    • A new transient event, acp_live_update, carries a tool_presentation, a context, or both. The ACP runner publishes it through publish_transient instead of appending acp_session_updated for those two fields, and the store's in_flight keeps the newest context and the newest presentation of each open call, so a client that joins mid-run gets them.
    • The final presentation is stored with the call's end. tool_call_terminated gains an optional presentation, set when it differs from the one tool_call_started stored. Replaying a log shows the start's presentation, then the final one.
    • Context is stored once per run. Before run_finished, the runner appends one acp_session_updated with context when it changed since the last stored value, so a reload shows the last use.
    • Everything else in acp_session_updated stays stored as it is: commands, options, notices, steering, the plan, the fork point, compactions, messages between sessions, background ends, the prompt context. They are rare and they are history.

    Older clients drop a transient event they do not know (the client protocol's rule for live-only output), so they see a call's final presentation when it ends and the context once per run. Client protocol: a minor bump. Effect on the session in section 1: 4,584 ACP records become about 65, and the log about 19% smaller (the final presentations still travel in the end records). This replaces the ACP item of history format 2 in session storage v3 (its section 4.2).

    Implementation notes (2026-10-31)¶

    Implemented as client protocol 1.60.0 and plugin protocol 1.32.0 (plugins receive live-only events too). History format 1 gains only the optional presentation of tool_call_terminated; logs earlier builds wrote, with their stored presentations and context use, read as before.

    • acp_live_update is live-only (EventPayload::is_transient), so StoredEvent::validate refuses it and it is never appended: an exhaustive syncs_on_append (4.2) puts it with the other live-only kinds, where it cannot occur.
    • The store's in_flight keeps an ACP session's newest context use until its run's end, and each open call's newest presentation until the call's tool_call_terminated or the run's end. Being whole values, they also go to a subscription that resumes from a cursor, which gets no other in-flight output.
    • The runner stores the context use, when it changed since the last value the log holds (read from the log as the run starts), before each round's end request (PromotePendingOrComplete, which ends the run unless input waits), before a cancel's run_finished, and before a failed run's, and never once the run has ended (a cancel from outside). A run whose waiting input starts another round may store it once per round.
    • tool_call_terminated.presentation is set from the presentation the clients last got, when it differs from the start's; a call that ends with the turn (end_open_calls) carries it too. The display audience converts its blocks, and those of acp_live_update, as it converts a start's.
    • The client reducer applies acp_live_update as it applied those two members of acp_session_updated, and a termination's presentation before its result; held history keeps only the newest live value of each.

    Measured on a copy of the session in section 1, the new writer simulated over its records: 9,813 records become 5,293, its 4,584 acp_session_updated become 64 (31 context records, one per run; 1,105 of its tool ends carry a final presentation), and 16.9 MB become 14.0 MB (17.6% smaller). Folded by the client reducer, both logs give the same presentation and status for all 1,112 calls, the same context, and the same transcript rows. A scripted fixture session (four turns: three late presentations of two calls, three context changes in two runs, an edit, and two commands) stores 65 records instead of 69.

    4.4 Commands without engine-wide locks¶

    The measurement (section 5.1) found no contention on these locks, so only the last item, heavy work before locks, is built now. The other three are shelved until the timing shows waits for them to remove.

    • Shelved: fast path. If the session is owned, resident, and has an actor, send_command sends to it directly. begin_write checks owned and resident before it takes the mutation lock, and returns AlreadyOwned without it.
    • Shelved: retired actors. Eviction marks an actor retired, under its tree's residency lock, before draining it. A retired actor answers every command it receives with Retired, and the sender retries through the locked path, which reopens the session. So a command can never run on an evicted session.
    • Shelved: one residency lock per tree. residency_mutation becomes a lock per root, taken by the four places that take it today (send_command's slow path, delegate recovery, and the two janitor passes), each of which knows the session's root. Eviction is already per tree: a tree goes whole or not at all, and one tree never evicts another's subagents.
    • Heavy work first, locks after. The slow path completes the tree (off the async workers) before it takes any lock. A cold reopen parses the log without the mutation lock and takes it only to install the projection, re-checking that nothing installed one meanwhile.

    4.5 Other files¶

    File Today Proposed
    crons.json synced with its directory on every write unchanged: a fire's run state is what keeps a job from firing twice
    unread.json synced on every change written atomically without sync: a crash may mark a session read again
    memory's read bookkeeping (..reads.json) synced on every turn that reads memory atomic without sync
    model catalog metadata synced atomic without sync: a cache
    grant journal synced per grant unchanged: a commit point
    files the write and edit tools write file and directory synced unchanged: about 350 syncs in five weeks of the user's sessions, and none for Claude Code's own edits

    5. Measurement first¶

    Before 4.1 and 4.4, the daemon records how long commands wait for residency_mutation and the mutation lock, and how long each log sync takes, and logs any wait or sync over 250 ms with the session and the lock. A run of the user's daemon on a busy machine then shows how much of the stall each lock causes, and the same counters prove the change after.

    5.1 What the measurement found (2026-10-31)¶

    Four hours of the user's daemon (16:39 to 20:49, 25 summaries, the build of 5a44ac557, before session storage v3's phases 2 and 3):

    Meter Per 10 minutes Typical Worst
    residency lock wait 14 to 738 0 ms 3 ms in all; never slow
    store lock wait, shared, and session slot wait 11 to 708 0 ms 2 ms
    store lock wait, exclusive 17 to 747 0 to 16 ms 192 ms, once
    residency lock hold as the waits under 1 ms 275 ms and 525 ms, once each: commands that opened a cold session under the lock
    log sync 10 to 545 15 to 45 ms on average about 65 over 250 ms, up to 1,699 ms; up to 7.9 s of syncs in 10 minutes

    The locks are not where the time goes: in four hours no command waited for the residency lock or a session slot. The disk is. On a busy disk one fdatasync takes 250 ms to 1.7 s, and the slow ones come in bursts on the session that is working (nine of 270 to 495 ms in two minutes on one log), each holding that agent's next record back. Hence the order of work in section 7: fewer syncs and syncs outside the locks first; of 4.4 only the heavy work before locks, for the two slow holds.

    6. Tests¶

    • Sync counts (EVENT_LOG_SYNCS): a turn's syncs are its commit points; a burst of model turns and stored ACP fields between two of them adds none.
    • Commit ordering: a tool starts only after its tool_call_started is synced (a sync hook that holds the sync proves the tool waits); a record appended during a commit point's sync is published after it.
    • Crash tests: a log cut at any byte after a commit point reopens with every record up to that commit point, and recovery ends the run as Interrupted.
    • Live state: a client that joins mid-call gets the call's newest presentation and the newest context from in_flight; a replay from the log shows the final presentation from tool_call_terminated and the context stored before run_finished; no acp_session_updated is stored for presentations or for context mid-run.
    • Locks: a cold reopen parses its log and completes its tree before it takes the residency lock and the mutation lock, and does not delay another session's appends. (The shelved items of 4.4 bring their own tests: a command to tree B completing while tree A's lock is held, and a command racing an eviction answered Retired and retried.)

    7. Order of work¶

    1. Measurement (section 5): shipped as 5a44ac557; findings in 5.1.
    2. Syncs outside locks (4.1) and the commit-point classes (4.2).
    3. ACP live state (4.3).
    4. Heavy work before locks (the last item of 4.4).
    5. Other files (4.5).

    The rest of 4.4 is shelved (section 5.1).

    8. Decisions¶

    User decisions of 2026-10-31:

    1. No sync window and no background syncer: syncs move outside the locks, only commit points sync, and everything else rides on the next sync. The measured rate is low; the stall is sync latency under the locks.
    2. tool_call_terminated is a commit point, so a finished tool is never recorded as interrupted and repeated.
    3. ACP tool presentations and context use are live-only (acp_live_update); the final presentation is stored in tool_call_terminated and the context once per run.
    4. crons.json keeps syncing every write, a fire's run state included, so a job never fires twice after a power loss; unread.json stops syncing.
    5. The files the write and edit tools write keep their syncs: they are rare (section 4.5).
    6. Measurement first: the lock and sync timing (section 5) ships alone and runs on the user's machine for a few days before the rest is built.
    7. This spec comes before phase 2 of session storage v3.
    8. (2026-10-31, after the measurement in 5.1) Build 4.1, 4.2, 4.3, the heavy work before locks of 4.4, and 4.5; shelve 4.4's fast path, retired actors, and per-tree residency locks.

    9. Implementation notes¶

    4.1, 4.2, the last item of 4.4, and 4.5, as built on 2026-10-31:

    • Syncs. EventLog::write_owned writes a record unsynced and returns a Commit for a commit point; EventLog::sync_through waits until a sync covers it. The sync state of a log (events/durability.rs) counts records written and the count each finished sync started at, and keeps a duplicate of the writer's descriptor to sync on. A caller whose commit is not covered runs the sync when none is in flight and otherwise waits for the one in flight and then runs the next, so commit points written before a sync starts share it. Closing the writer syncs what no sync covered; a revert's cut, synced whole, counts as a sync of everything written. The log sync meter times each sync as before.
    • Appends. SessionStore::append writes and folds the record under the session's slot, queues its publication there (session/publication.rs), releases the slot, then syncs a commit point and publishes what its sync settled. A record publishes, to the live tails and as the session list's and approvals' notifications, when it rides along or its sync ended, and only after every earlier record of its session. A failed sync is reported to the append that ran it and still releases the queue. A tail registered while a commit point syncs already has it in its first page and is not sent it again.
    • Tool starts. The model loop appends a turn's tool_call_started records with Engine::append_deferring_sync and syncs them once (Engine::sync_appended, which also streams them to plugins) before any permission decision or tool runs. The ACP runner's starts each sync on their own: they report calls the agent already runs.
    • Classes. syncs_on_append is an exhaustive match. Ride along: the six bookkeeping kinds, model_turn_committed, acp_session_updated. Live-only kinds are listed too (never written). Every other kind is a commit point, tool_round_started and the per-run prompt, memory, and internal-agent records among them, as rare kinds.
    • Reopens. A command's slow path calls SessionStore::prepare_write off the async workers before the residency lock: it completes the tree, reopens a session this process owns but evicted, and otherwise parses the log read-only for the adoption to take over. reopen_owned parses and folds without any store lock, one reopen of a session at a time (a per-session gate, so nothing appends to the file while it is parsed and a torn tail is cut safely), and takes the slot only to install, re-checking for a projection installed meanwhile and for deletion. begin_write reopens that way before its exclusive lock and loops if the session was evicted again before the lock.
    • Other files. unread.json, memory/.reads.json, and the catalog's models-dev-v2.meta.json are renamed into place without syncing the file or its folder (SecureDirectoryLock::replace_unsynced for the catalog); the catalog body keeps its sync.

    Deviations:

    • An adoption (the first write to a tree this process does not own yet) still takes the tree's owner.lock, converts the tree, and folds the log under the exclusive lock; only the parse moves before it, taken over when the file is unchanged. Taking the owner lock outside the store lock would let two acquisitions in this process race on it.
    • A command queued behind the residency lock while the janitor evicts its session finds it evicted under the lock and reopens it there (outside the store's mutation lock); retired actors, shelved, would remove that.
    • Forks, reverts, and a buffered session's first write still sync under the locks that make them: they are rare structural changes.

    Measured with strace -f -y -e trace=fdatasync,fsync on cookie run in a scratch home with scripts/web-e2e/showcase-model.py (the same edit, check, reply turn, 36 events), the store warmed by one earlier run:

    Session log All syncs
    Before (b59ba7c14) 15 29
    After 12 21

    Of the eight syncs fewer, three are the log's: the turn's three model_turn_committed now ride along. The other five are unread.json, memory's read times and their folder, and the catalog metadata and the folder sync after it. The rest are the new session's directory and metadata, the runtime revision index, the catalog body (fetched in this run), and the file the edit tool wrote with its directory.

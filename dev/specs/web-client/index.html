    Web Client and Local Daemon Use¶

    Status: implemented (2026-10-20), in phases L and W0 to W5; what landed and where it differs from the plan is in section 17, with a summary of the deviations at its end. The decisions in section 1 come from the planning discussion of 2026-10-19, and no questions are open (section 15). The spec builds on the compatibility spec, which froze the client protocol and added browser authentication, and on the runtime capabilities spec, which added the listening daemon. The addendum of 2026-10-21 (section 16) adds web layout v2 and session deletion, implemented on 2026-10-21. On 2026-10-21 the user also reversed the "no service worker" decision of section 9: the page installs as an app, with a network-only service worker.

    1. Goal and scope¶

    Before this spec the TUI was the only interactive client. This spec adds a browser client that does everything the TUI does that a browser can do. It works on a phone and on a desktop, against a daemon on the same machine or on another one.

    It also makes plain cookie use a daemon already running on the machine instead of starting a private one beside it (section 13). Once a persistent daemon holds the machine's sessions, every client should see the same ones.

    Decided 2026-10-19:

    • Use. One client serves the desktop browser on the daemon's machine and remote access from a laptop or phone. The layout is responsive, and every action works by touch.
    • Stack. The client is Rust compiled to WebAssembly with Leptos, using client-side rendering. It reuses the Rust protocol client and a reducer shared with the TUI. No TypeScript client and no generated TypeScript types are written.
    • Hosting: both.
    • The daemon serves the built page.
    • The same bundle also works from any static host, connecting to a daemon whose allowed_origins lists that host.
    • Who serves the page. cookie daemon always serves it. Plain cookie never does: it either connects to a running daemon (section 13) or runs one in-process with no port. There is no configuration key or flag for this.
    • Highlighting. Code is highlighted by highlight.js shipped inside the bundle, not by syntect compiled to WebAssembly and not by Shiki (several times larger). The web and TUI colours may therefore differ slightly.
    • Editors. /config and /memory edit in a plain text area in version 1. A code editor can come later.
    • No project-site hosting. The bundle is not published on cookie-agent.github.io. Releases attach it as an archive.
    • MSRV. If the chosen Leptos release needs a Rust newer than 1.88, the workspace MSRV rises to match.
    • Origins: no special case. Every browser connection, the embedded page's included, must come from an origin [server] allowed_origins lists. Whoever sets up the daemon decides which addresses reach it.
    • One listener. The page and /ws share the daemon's one TCP listener. Forwarding that one port (with cloudflared, Tailscale, an SSH tunnel) forwards both, and the connect screen fills in the daemon URL from the page's own address.
    • Styling. The page uses standard tooling: Tailwind CSS through Trunk's built-in Tailwind support, as the Leptos documentation describes. No hand-written stylesheet framework.
    • No conformance client. No Python or Node smoke client is added. The compatibility checker and the frozen corpora stay the guard for third-party clients.
    • Milestone. The milestone is full TUI parity, phases W0 to W5. Two exclusions stay with the TUI and CLI:
    • MCP OAuth, whose redirect must reach a loopback listener;
    • offering this machine as a runtime, as cookie attach does when the daemon is remote.
    • Plain cookie and a running daemon (section 13):
    • When a daemon is running on this machine, plain cookie connects to it.
    • It then checks whether the daemon has a coding runtime on this machine. If so, sessions use the daemon's runtime. If not, plain cookie provides its own local coding runtime.
    • When no daemon is running on this machine, plain cookie behaves as today: it runs the daemon in-process.
    • cookie attach and cookie --standalone override the automatic choice.
    • There is no discovery file. Plain cookie finds the daemon at the address [server] configures (section 13.1).
    • cookie run stays in-process.
    • A daemon running as another OS user on the same machine is not detected. It reports the same machine ID, so its local runtime is used, with that user's file permissions. Users who run the daemon under a service account use --standalone or a dial-in runtime.

    Out of scope: - protocol changes, beyond any small additions phase W0 finds it needs (section 11); - a TypeScript SDK; - hosting the bundle on the project's Pages site; - offline use; - push notifications.

    2. Vocabulary¶

    • Bundle. The built web client: index.html, the WebAssembly module, its JavaScript glue, the highlighter, styles, and icons.
    • Embedded page. The bundle served by cookie daemon from its own listener.
    • Hosted page. The same bundle served by any other web server.
    • Shared client. The Rust code the TUI and the web client both use: the protocol client in cookie_agent_protocol and the state crate of section 5.

    3. Architecture¶

    crates/protocol            wire types + Client (now also wasm32)
crates/client_state        NEW: reducer and view state, shared by TUI and web
crates/tui                 ratatui rendering over client_state
crates/web                 NEW: Leptos CSR app over client_state (wasm32)
crates/web_assets          NEW: the prebuilt bundle as bytes, for the server
crates/server              serves /ws, /runtime, and now the bundle
    • crates/web is a workspace member.
    • It builds for wasm32-unknown-unknown with trunk.
    • It also compiles natively, so cargo build --workspace and the unit tests keep working without the wasm target.
    • Natively, only its pure logic is tested. Browser APIs are not called in native tests.
    • crates/web_assets includes the bundle at compile time.
    • When no bundle has been built (a fresh checkout, or the regular CI jobs), it includes a placeholder page: "the web client was not built; run scripts/build-web.sh".
    • So cargo build --locked --workspace never needs trunk or the wasm target.
    • Dependency direction. web and tui depend on client_state. client_state depends only on cookie_agent_protocol and plain crates. Nothing in it renders.

    4. Protocol client on WebAssembly¶

    cookie_agent_protocol builds for wasm32-unknown-unknown with the client side only.

    • Features. The native-only parts are gated by target:
    • the server (session/server*);
    • the stdio transport and codecs;
    • oauth-callback;
    • StopSignals;
    • process helpers.

    On wasm, tokio is limited to sync (and macros where needed). uuid and jiff enable their browser features for randomness and the clock. The core oven-sdk crate already has no tokio or HTTP dependency. - Executor shim. Client calls tokio::spawn, tokio::time::timeout, sleep, and interval today. A small internal module provides spawn, timeout, sleep, and interval: - native: tokio, unchanged; - wasm: wasm_bindgen_futures::spawn_local and browser timers.

    The client's logic, its limits (2,000-event replay pages, the 5 s page timeout, 6 recovery attempts) and its tests stay one copy. - Browser WebSocket transport. - The web_sys::WebSocket is not Send. It lives in one local task that exchanges frames with the client over channels, so the client's own futures keep their bounds. - The transport sends no Authorization header (browsers cannot set one). The token goes in ClientHello.token, as the protocol reference describes. - A close before the handshake reply is reported like a refused native upgrade. A browser exposes no HTTP status for a refused upgrade (Firefox reports close code 1006), so an origin refusal cannot be told from others: the page shows every refusal before the handshake with the allowed_origins hint naming its own origin. - Reconnect uses the same backoff (500 ms rising to 10 s) and the same ClientIdentity across reconnects, so this tab's origin stays stable. The instance id lives in sessionStorage, so each tab is its own client, the same as each TUI process. - CI. A job runs cargo check --target wasm32-unknown-unknown for cookie_agent_protocol (client features) and cookie_agent_client_state, and clippy over them; the web job runs the browser tests (section 12).

    5. Shared client state¶

    The reducer and view state move from crates/tui/src/state/ into crates/client_state, and the TUI uses them from there. Their tests move with them (state/tests.rs).

    • Moves:
    • StateStore, SessionState, and reduce_event/reduce_transient (event attribution, pending and queued lanes, approvals, goal, live tool display deltas);
    • the runtime snapshot revision chain (state/runtime.rs);
    • model display names (state/model_names.rs).
    • Markdown.
    • Today the state stores a MarkdownDocument already styled with ratatui.
    • The state will keep only markdown that any client can use: the source text plus a pulldown-cmark event list, or the source alone if parsing in each client proves cheap enough.
    • The ratatui styling moves to crates/tui/src/markdown.rs, and the web client renders the same markdown to HTML.
    • Phase W0 picks the representation by measuring the TUI's redraw cost on a long session.
    • Moves too, where it separates cleanly:
    • the subscription policy (keep the 8 most recently viewed trees subscribed, release settled ones, retry a failed recovery after 2 s);
    • treating a session.resume "owned by another process" error as a read-only snapshot;
    • the model-selection draft: publish after 300 ms, and yield to a session_model_selected from another origin;
    • upload chunking.

    These are client behaviour, not rendering. Pieces too tangled with App stay in the TUI, and the web client reimplements them. Phase W0 records which. - Stays in the TUI: - rendering, pointer targets, hover; - tui.toml and the theme; - $EDITOR editing; - the OSC 52 clipboard; - the terminal-only debounces (approval hotkey grace).

    6. The web client¶

    • Shape.
    • Wide screens: a session sidebar (list and subagent tree), the transcript, and a composer docked at the bottom. Panels (approvals, /runtime, /mcp, /config, …) open as side sheets.
    • Narrow screens: the sidebar and panels become full-screen sheets, and the transcript fills the screen.
    • Commands. The composer accepts the same slash commands as the TUI, with the same names and aliases. Every command is also reachable from a menu, because phones lack a convenient /.
    • Keys and touch.
    • Keys: Enter steers, Alt+Enter queues, Shift+Enter and Ctrl+J insert a newline, Escape cancels, Up recalls.
    • Touch: Send steers, and long-pressing Send (or its menu) queues.
    • Every clickable element has a visible hover on pointer devices and a visible pressed state on touch, mirroring the TUI's rule that every click target hovers.
    • Transcript rendering.
    • Markdown: rendered to sanitized HTML. Raw HTML in model output is escaped, never rendered.
    • Display blocks: every kind gets its own renderer: text, markdown, code, file_excerpt, diff, terminal, key_value, table, json, media, link, session_ref.
    • Diffs show real file line numbers and their five context lines.
    • Terminal blocks turn SGR sequences into styled spans.
    • Tool names: no renderer branches on a tool's name.
    • Unknown blocks use their text fallback, and unknown events render as nothing.
    • Media.
    • Attachments come from the file picker, drag and drop, paste, and the camera on phones.
    • They are offered only for the media kinds the selected model's input_media accepts.
    • On a too-large rejection, the client offers "downscale and attach?". Images are re-encoded through a canvas; video is not downscaled.
    • media blocks and attachments are shown inline from artifact.read through Blob URLs.
    • Highlighting.
    • A JavaScript highlighter is shipped in the bundle (no CDN, since a daemon may run with no internet) and called through wasm-bindgen.
    • It is loaded lazily on the first code block.
    • The highlighter is highlight.js.
    • Editors. /config and /memory edit in the page.
    • They keep the TUI's revision and conflict handling: config.apply reports configuration errors, and a memory edit that conflicts with a newer revision asks what to do.
    • Version 1 uses a monospace text area.
    • Clipboard.
    • Copy uses navigator.clipboard. Browsers offer that only in a secure context (HTTPS or localhost).
    • Elsewhere the client falls back to selecting the text and asking the user to copy it.
    • Preferences.
    • Theme (light, dark, or system) and the /events level filter live in localStorage.
    • There is no server-side preference store.
    • Styling.
    • Tailwind CSS, wired in through Trunk's rel="tailwind-css" asset. Trunk runs the standalone Tailwind CLI at a version pinned in Trunk.toml, so the build needs no npm or node_modules.
    • Components use Tailwind utility classes in their view! markup. Tailwind finds them by scanning crates/web/src/**/*.rs (an @source entry), so class names are always complete string literals, never assembled from pieces at runtime.
    • The palette is defined once as Tailwind theme tokens (CSS variables): the landing site's colours, which are the TUI colours from crates/tui/src/theme.rs. Light and dark variants use Tailwind's dark: variant, following the system setting or the user's override.
    • Other web assets come in through Trunk's standard asset pipeline too: the highlighter script, fonts, icons, and the manifest are copied by Trunk, not by hand. Copied files keep their names (the manifest names its icons by path), so they are revalidated rather than cached forever (section 7.1).
    • JetBrains Mono for code. Fonts are bundled, not loaded from Google.
    • Icons are Font Awesome Free (CC BY 4.0, credited on the connect screen and in the connection panel) from the icondata crate, rendered by leptos_icons as inline SVG that takes the text colour. Only the icons the page names are in the bundle; there is no icon font. Icon-only buttons have an aria-label and a tooltip.

    7. Hosting and authentication¶

    7.1 Embedded page¶

    • cookie daemon serves the bundle on its listener, over TLS when TLS is configured.
    • GET / returns index.html.
    • The bundle's files are served at their paths.
    • /ws and /runtime keep their meaning, and any other path is a 404.
    • Files whose names carry Trunk's content hash (the WebAssembly module, its glue, the stylesheet) are sent with Cache-Control: immutable. index.html and the files Trunk copies under their own names (fonts, highlighter, manifest, icons, screenshots, the service worker) are sent with no-cache and an ETag, so a restarted daemon's page always matches its own build.
    • A compressible file is sent gzip-compressed to a browser that takes gzip; there is no Brotli.
    • Serving the page needs no token. The page holds no secret. Every connection it opens still authenticates in the handshake.
    • One listener for both. The page and /ws share the daemon's TCP listener. Anything that forwards that one port forwards both, and the page finds the daemon at its own address (7.2).
    • Origins have no special case.
    • The page's /ws connection is a browser connection like any other. It carries the page's Origin, and the daemon accepts it only if [server] allowed_origins lists that origin or is ["*"].
    • The default list is empty, so the embedded page cannot connect until the user lists the origins they open it from. Examples: http://127.0.0.1:7419, http://192.168.1.5:7419, or a tunnel's https://cookie.example.com.
    • The daemon trusts no headers to work out where it is reachable from.
    • Telling the user what to add.
    • A refused connection gives the page no reason to show. When the handshake never happens, the connect screen names the likely cause: "add "<location.origin>" to [server] allowed_origins in the daemon's config.toml and restart it". It quotes its own origin exactly.
    • When allowed_origins is empty, the daemon says, in a log line after its ready line, that the web page needs an entry before it can connect.
    • Plain cookie opens no port and serves nothing.

    7.2 The connect screen¶

    The same page runs embedded in the daemon or from any other static host, and both open on one connect screen.

    • The daemon URL is filled in from the page's own address.
    • The scheme changes from http to ws, or from https to wss.
    • Host and port stay the same.
    • ws is appended to the page's directory: https://abc.efg/ gives wss://abc.efg/ws, and https://abc.efg/cookie/ gives wss://abc.efg/cookie/ws.
    • What the fill covers.
    • The embedded page, reached directly or through any forward of the daemon's port, always gets the right URL.
    • A page on a static host without a daemon gets a URL to edit. The edited URL is remembered in localStorage.
    • When the page connects by itself. It connects without a click when it has both a URL (filled in or remembered) and a token (from #token= or localStorage, section 7.3). Otherwise the screen waits for input.
    • Relative paths. The bundle uses relative paths only, so it works from any path on any static host.
    • HTTPS pages. A page served over HTTPS can only reach wss:// daemons. The web clients section already says so, and the fill keeps the page's scheme.
    • Version skew between page and daemon is handled by the handshake: same major required, and the page gates methods on the daemon's minor.
    • Archive. The release attaches the bundle as an archive, so it can be hosted anywhere.

    7.3 Getting the token to the page¶

    • cookie web is a new CLI command. It prints the page URL with the token in the fragment: http://<host>:<port>/#token=<token>, or https when the daemon uses TLS.
    • URL and token resolve like cookie attach: --url and --token flags first, then [server] url and [server] token in this machine's configuration.
    • --open opens the system browser.
    • The URL is derived from the client URL: ws→http, wss→https, and the /ws path dropped.
    • The fragment never reaches a server or its logs. On load, the page reads #token=, stores the token in localStorage under the daemon URL, and removes the fragment from the address bar.
    • Fallback: a paste box on the connect screen.
    • The daemon's ready line is unchanged, since supervisors parse it. The page URL, without the token, follows it as a log line.
    • Forget: a "Forget this daemon" action deletes the stored token.

    9. Phones¶

    • Layout. Layouts work from 360 px wide. Touch targets are at least 44 px, nothing scrolls sideways, and long lines in code, diff, and terminal blocks scroll inside their block.
    • Home screen.
    • The bundle has a web app manifest and icons (any and maskable, 192 and 512 px, an SVG, and an Apple touch icon), display: standalone, and a theme colour for light and dark, so it can be added to the home screen.
    • The spec first left a service worker out: it would need a secure context and adds caching the daemon's version matching does not want. The user reversed this on 2026-10-21: the page advertises itself as an installable app, with a service worker that caches nothing (below).
    • Installable app (user decision, 2026-10-21). Users opening the page in a browser, typically over tailscale serve HTTPS (https://<host>.<tailnet>.ts.net/ in front of the loopback daemon), can install it to a phone or desktop.
    • Manifest. name, short_name, and id, start_url, and scope of ./ (relative, so the page installs from any path), display: standalone, background and theme colours, the icons above, and a narrow and a wide screenshot for Chromium's richer install dialog.
    • Service worker, network-only. sw.js beside index.html, so its scope is the page's directory without Service-Worker-Allowed. It caches nothing: no Cache Storage, and its fetch handler passes the page's own GET requests to the network (respondWith(fetch(request))) and leaves every other request, and /ws and /runtime, to the browser. The page must always match its daemon's build, which is why caching stays out. It calls skipWaiting and clients.claim, and scripts/build-web.sh stamps the build on its last line, so a new build replaces it on the next load. The page registers it only in a secure context, with updateViaCache: "none".
    • Serving. sw.js keeps its name, so it is sent with no-cache and an ETag like index.html, as text/javascript. The Content-Security-Policy adds worker-src 'self' and manifest-src 'self'.
    • Advertising it. An inline script keeps Chromium's beforeinstallprompt (it may fire before the WebAssembly runs) and prevents the mini-infobar. Settings › This browser, the connect screen, and a phone's one-time dismissible banner offer Install app, which opens the prompt; appinstalled or running standalone (display-mode: standalone, iOS's navigator.standalone) hides it. iOS and iPadOS have no prompt, so they get the steps instead: Share, then Add to Home Screen. A page that is not a secure context cannot be installed, and Settings says it needs HTTPS. The decision is pure logic in crates/web/src/install.rs.
    • Launching. The app opens at start_url, which has no token, and connects with the stored one. iOS keeps a home-screen app's storage apart from Safari's, so there the token field takes a pasted cookie web link once. The theme-color follows the page's theme, the user's override included.
    • On-screen keyboard. The page's frame and sheets take the visual viewport's height, which the keyboard shrinks, so the composer and an open sheet stay above it; the frame keeps clear of safe-area insets.
    • Background tabs.
    • A phone suspends background tabs. On visibilitychange to visible, the client checks its connection and reconnects through the shared client's resync.
    • Lost events are recovered by cursor, as after any reconnect.
    • Remote access. Reaching a remote daemon from a phone means cookie daemon --listen on a private network or VPN, or TLS. The guide page says the token crosses the network in the clear without TLS, as the daemon's --listen help already does.

    10. Build, CI, and packaging¶

    • scripts/build-web.sh
    • runs trunk build --release for crates/web, with wasm-opt for size;
    • copies the result to crates/web_assets/bundle/, which git ignores;

    13. Plain cookie and a local daemon¶

    Before this change, plain cookie always started a private daemon inside its own process, even when cookie daemon was already running on the machine. That private daemon could not open a session the other one owned: it showed the session as a read-only snapshot. Its own sessions were invisible to the web client and to every other client of the running daemon.

    From this change, plain cookie follows the decisions in section 1:

    1. find a daemon running on this machine and connect to it (13.1);
    2. pick the coding runtime for its sessions (13.2);
    3. with no daemon found, run in-process exactly as today.

    13.1 Finding the daemon¶

    • The token comes first. The probe happens only when this machine's config.toml has [server] token. cookie daemon writes that key on its first start and keeps it across restarts. With no token, no daemon has run with this configuration, so plain cookie starts in-process without touching the network.
    • The probe address is ws://<[server] host>:<[server] port>/ws, the address a plain cookie daemon listens on.
    • It is not [server] url. That key may name a daemon on another machine (a laptop configured for labpc), and plain cookie must never go remote on its own. Reaching another machine stays explicit: cookie attach.
    • Plain cookie authenticates with the Authorization header and the configured token, as cookie attach does.
    • Deadlines. A refused connection falls through to in-process at once. The connect and the handshake each have a short deadline (500 ms and 2 s), so a stuck listener delays startup by seconds at most.
    • What each outcome does:
    Outcome Result
    Nothing listens (refused, or the connect deadline passes) In-process, silently
    Handshake succeeds Connected to the daemon (13.2, 13.3)
    Something answered but the handshake failed: wrong token, another protocol major, a TLS listener, not a cookie daemon In-process, with a notice (below)

    The notice appears in the TUI's status area when it starts. It names the address and the reason, and suggests cookie attach to require the daemon or --standalone to stop probing. Failing outright would lock the user out when, for example, a daemon from an older major keeps running after an upgrade. - Daemons this does not find: - one started with --port or --listen on an address the probe does not reach; - one serving TLS only.

    For those the user runs cookie attach, or sets [server] host and port to match. - Token exposure. Plain cookie sends the token to whatever listens on that loopback port. cookie attach with default settings does the same today. config.toml is owner-only, and the probe only happens when a token exists.

    13.2 Choosing the coding runtime¶

    After the handshake and before the first session is created, plain cookie picks the runtime its sessions use for the current directory. The steps go in order, and the first match wins:

    1. The daemon is on this machine. If ServerHello.machine_id equals this machine's ID, the daemon's local runtime serves the directory. session.create names the directory as cwd and no runtime, as cookie attach does today. If either side has no machine ID, this counts as a match, again as cookie attach does today.
    2. A runtime of the daemon runs on this machine. Otherwise, plain cookie looks for a connected runtime that:
    3. runtimes.list places on a machine whose ids (from machines.list) include this machine's ID; and
    4. offers a capability that takes a workspace.

    Sessions attach that capability at the directory. Example: the daemon runs in a container or behind a forwarded port, with cookie runtime serve --daemon running here. When several runtimes match, the lowest runtime ID wins, and /runtime shows the choice. The choice uses only reported facts (machine, takes_workspace), never a runtime's kind label. 3. Nothing on this machine. Plain cookie dials in its own runtime, client_<host>, limited to the directory and living as long as the TUI. cookie attach already does this for a daemon on another machine.

    cookie attach switches to the same three steps, replacing its current machine-ID check. That way the two never pick differently.

    13.3 Once connected¶

    • Behaviour matches cookie attach.
    • The session list is filtered by the directory.
    • A dropped connection is retried with the same backoff. Plain cookie never falls back to in-process mid-session, because the sessions belong to the daemon.
    • Quitting the TUI leaves the daemon running.
    • The TUI shows where it runs. The status bar shows the daemon's address when connected, and standalone when in-process. Today the two look the same.
    • Version notice. When the daemon's engine_version differs from this binary's version, the TUI notes it once: "the daemon runs 0.5.0, this is 0.6.0; restart the daemon to upgrade". This happens after an upgrade while a service daemon keeps running. The protocol versions still decide whether the two connect.

    13.4 Overrides¶

    • cookie --standalone always runs in-process and never probes. It applies to plain cookie only. Combined with a subcommand, it is a usage error.
    • cookie attach stays explicit:
    • its target comes from --url, --token (or COOKIE_DAEMON_TOKEN), then [server] url and [server] token, and may be another machine;
    • a failure is an error, never a fallback;
    • it chooses its runtime by 13.2.
    • cookie run stays in-process and never probes. Headless runs are often scripted, and a script attaching to a long-lived daemon by surprise is riskier than a TUI doing so.
    • In-process alongside a running daemon behaves as today: a session the daemon owns opens as a read-only snapshot.

    13.5 Testing¶

    • The decision logic is a pure function. It takes the probe outcome, ServerHello, runtimes.list, machines.list, and the local machine ID, and returns one of: in-process, in-process with a notice, local, an existing runtime, or a dial-in. It is tested over every row of 13.1 and every step of 13.2.
    • Integration tests use a scratch home whose [server] port points at a test daemon:
    • plain cookie connects and creates its session through the daemon;
    • with nothing listening, it starts in-process silently;
    • with a wrong token, plain cookie starts in-process with the notice;
    • --standalone and cookie run never connect;
    • a daemon reporting another machine ID gets a dial-in runtime.

    16.2 Session deletion¶

    Decided 2026-10-21:

    • Users delete sessions from the TUI and from the web client.
    • Deleting is a hard delete of the whole session tree from disk: the root session and every delegated subagent session under it, with their events, metadata, and artifacts. Nothing is kept for undo.
    • A client sends the delete only after the user confirms it.
    • The daemon refuses while any session of the tree has an active run, and while another process holds the tree's owner.lock.
    • A delete that succeeds sends the existing sessions.changed removed change to every connection.
    • TUI. In the session picker (/sessions), Ctrl+D, Delete while the list has focus, or the picker's Delete button asks to delete the highlighted session, in a confirmation over the picker; y or Enter (or Confirm) deletes and n or Esc (or Cancel) keeps it. Ctrl+A, or the picker's directory button, switches the list between this directory's sessions and every directory's, whose rows then name their directory. The picker's action row names both keys.
    • Web client. Section 16.1's trash icon and confirmation.

    The method¶

    session.delete deletes one root session's tree.

    { "jsonrpc": "2.0", "id": 7, "method": "session.delete", "params": {
    "session_id": "<root session ID>", "expected_last_seq": 42 } }
    • session_id names a root session. A delegated session is refused: its tree is deleted through its root.
    • expected_last_seq is required, at least 1. It is the root's last_event_seq from the SessionMeta the client showed the user (session.list, session.get, or a sessions.changed upserted). A root whose last event is now another one is refused, so a delete never removes a turn the user has not seen, such as one another client just added. Only the root's log is compared. A change elsewhere in the tree happens during a run, and a running tree is refused anyway.
    • Params are strict like every command: an unknown member is unknown_field.

    The result names every session that was deleted, the root first:

    { "deleted": ["<root session ID>", "<subagent ID>", "…"] }

    Errors¶

    All are -32000 registry errors with message, hint, and detail. Three codes exist already, and three are new in 1.5.0:

    data.code Fields When
    session_not_found session_id No such session, or it was already deleted
    not_a_root_session (new) session_id, root_session_id The session is a delegated subagent. The hint says to delete its root
    session_tree_running (new) session_id, optional running_session_id A session of the tree has an active run, a compaction, or a subagent waiting for a slot. The hint says to wait for it or cancel it
    session_owned_elsewhere session_id Another cookie process holds the tree's owner.lock
    session_changed (new) session_id, current_last_seq expected_last_seq is no longer the root's last event. The hint says to look at the session again
    engine_error none The tree could not be moved aside on disk. Nothing was deleted, and detail says why

    session_running is not reused: its message and hint speak of starting a run, which a delete does not do.

    What the daemon does¶

    1. Checks. It resolves session_id: an unknown session is session_not_found, a delegated one not_a_root_session.
    2. Ownership. A tree this daemon holds is deleted on the root's session actor, which orders the delete after every request already queued for the root. A tree it does not hold is not adopted: adoption would repair the tree and append events first. The daemon takes the tree's owner.lock for the deletion itself, which fails with session_owned_elsewhere when another process holds it. Neither path writes an event.
    3. Busy and stale checks. In a held tree it refuses with session_tree_running when:
    4. a run of any of the tree's sessions is active;
    5. a compaction holds one of them;
    6. a delegated child waits in the delegation queue;
    7. or a resident session's status is running.

    A tree whose lock was free has no live run. A running status there is what a crashed process left, so it does not refuse. Then expected_last_seq is compared with the root's last event: session_changed. 4. Quiescing. The tree's background calls are stopped without a report. Its uploads in progress are dropped. Every resident log of the tree closes its append handle, so no handle stays open in the directory (Windows cannot rename a directory with an open file). 5. Commit. Under the session store's exclusive mutation lock, the root directory sessions/<workdirkey>/<root>/ is renamed in place to a tombstone, sessions/<workdirkey>/.deleted-<root>-<uuid>, and the work directory is synced. The rename is the commit point: from then on no listing, lookup, or tree load finds the tree. A rename that fails changes nothing and is engine_error. On Windows it is retried while another program briefly holds a file open. 6. Forgetting. The daemon drops what it holds for each session of the tree. In the session store: - locations; - the lazy tree-load state and queued load products; - resident projections, evicted summaries, and deferred metadata tips; - ownership (the tree's entry, which drops its lock and write authority, and each session's writable or adopting entry); - live tails; - cached read-only logs; - per-tree gates.

    In the engine: - session actors, whose queued requests then fail with session_not_found; - producers and the goal and producer projections; - skill grants and pending skill invocations; - compaction state; - delegation records and queue entries; - delegation recovery claims; - pending approvals; - the tree's permission mode; - the tree's grant journal, after which the visible tree grants are rebuilt; - the tree's artifact store handle; - upload leases; - fork idempotency keys whose source or fork was deleted; - steer ordering.

    Queued inputs and the goal live in the log, so they go with it. 7. Unlocking. The tree lock is released. On Unix it is inside the tombstone. On Windows it is the sidecar <root>.owner.lock beside the tree, which is then removed. 8. Telling clients. A sessions.changed removed change goes to every connection for each deleted session, the root first. 9. Removal. The tombstone is removed with everything in it. A failure is logged and leaves only the tombstone. SessionStore::open removes every .deleted-* entry of its work directory, so a daemon that crashed between the rename and the removal cleans up at its next start.

    What is removed on disk is the root directory and everything in it:

    • events.jsonl and metadata;
    • owner.lock on Unix;
    • grant-invalidations.jsonl;
    • artifacts/: uploads, retained tool output, and attachments;
    • subagents/index.json;
    • subagents/<child>/ with each child's events.jsonl and metadata;
    • any temporary files.

    On Windows the <root>.owner.lock sidecar goes too. The work directory's own files (cwd, layout.json, and the runtime revision index) are shared by every session and stay. A fork made earlier is not touched: it hard-linked its artifacts into its own tree.

    Subscribers¶

    sessions.changed removed is the only signal. No events.subscription message is added. When a tree is deleted:

    • the daemon drops the live tails of its sessions;
    • each connection forgets its subscriptions to them, so it sends nothing further for them, and events.unsubscribe answers false;
    • a client viewing a deleted session treats removed as "this session is gone": it leaves the view and drops the session's state.

    A connection that fell behind gets resync as before, and the deleted sessions are then absent from session.list.

    Clients¶

    • Only from 1.5. A client sends session.delete only to a daemon whose handshake protocol_version has minor 5 or later. To an older daemon it shows "The daemon is too old to delete sessions." without sending anything. A -32601 it gets anyway reads the same way.
    • Shared helpers. cookie_agent_client_state provides:
    • whether the daemon's version supports deleting;
    • the call that builds the params from the SessionMeta the user confirmed;
    • the outcome the TUI and the web client show.
    • TUI. The confirmation names the session's title and says how many subagents go with it. Refusals show their registry message and hint.

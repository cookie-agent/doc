    Sessions that run forever: recent events in memory, opening without a full parse¶

    Status: approved by the user on 2026-11-06. Built on the forever-sessions branch, all eight phases (section 12, with what remains open at its end); not on main. See section 11.

    1. Problem¶

    The goal is a session that can run forever (the user, 2026-11-06): it is not a memory shortage today, but nothing a long-lived agent does should cost more because its log is longer. So a term that is small now but grows with the log counts against this.

    A resident session holds every event of its log in memory. A long ACP session's old events serve no model request, as the agent holds its own context, and compaction is the agent's own command, so the log never gets a checkpoint. They are kept only because the code reads the whole list.

    What this settles:

    • The events are nearly all of it today. The line index, raw lines, and validation maps add 0 to 3.2 MB, and the projection, with its per-run agent copies, 0.4 to 1.5 MB. But those grow with the log too: at 100 times this length they would be hundreds of MB. Section 6 deals with them.
    • A session needs almost none of them. Under 0.1 MB at rest, and about one turn's events during a run (section 3.2). The largest run holds up to 17 MB in memory, which a window per turn does not keep.
    • Opening costs more than holding. Parsing peaks at about 1.7 times what stays. Section 4 removes the parse.
    • The tree load keeps little. It parses and drops children: with 20 subagents its peak was 15.3 MB against 8.1 MB without. But it parses the root too, which is probably why viewing a session parses its log at all (not measured apart).

    These are the storage crate's numbers. The daemon's RSS rose about 61.5 MB on opening the largest of these, so the rest is the parse's peak, which the allocator keeps until malloc_trim, and whatever the engine adds.

    Why not cap idle sessions instead? A cap frees this at the cost of a parse when the session comes back, which is what a forever agent does on every wake: a session evicted after 30 idle minutes parses its whole log each time a cron job or a message wakes it. So a cap makes it worse, and it is left out.

    2. The API¶

    EventLog::event_snapshot() goes. Its 125 production uses each move to one of:

    Call Gives Audit's count Where they landed (section 12)
    recent() The events since the log's window start 36 1
    state() A small fold kept up to date on append (section 3.1) 51 76
    history() An iterator over events read from disk, one at a time, unless the log holds them all 30 43
    model_context_events() Pinned records and the window, for a native model's context 8 7

    The compiler finds every use, so none is missed, and each states what it needs. Until a log is windowed, it holds every event and these cost nothing. ACP sessions are windowed first (section 3), then native ones (section 5).

    3. ACP sessions¶

    3.1 state()¶

    Each is a fold over one event at a time, in the log's order, so opening a log computes it once, an append updates it, and a revert computes it again.

    Fold What reads it today
    Per agent: the latest acp_session_started, the detach markers since it lifecycle::plan, each turn; acp_host_hints
    The ACP settings: option values, starting options, commands, context, prompt context options.rs, acp/compaction.rs, stored_acp_context, recorded_prompt_context
    Inputs not yet taken, with their bodies input_since, recall_input, drain_queued_input
    Producer messages, with the bodies of unsettled ones only input_since, woke_since, producer_input_waiting, goal_tools_offered
    Pending approvals, each response's id, and each approval's latest user decision approval/projection.rs, resolve_interrupted_direct, cancel_run, user_answer
    Latest values: SessionModelState, memory snapshot, published tools, permission overlay epoch start_run, acp_prompt_context, latest_model_tool_names
    "Once" facts: a seed, a title, a skill body, a link, a delegation's completion admission.rs, install_prepared_skill, delegation.rs, producers.rs

    A "once" fact is a set of keys, which grows with the log but stays small: a key per delegation or skill. recorded_option_values has the most subtle rule: it stops at an earlier session of another agent or declaration.

    3.2 The window¶

    After each committed turn, a windowed log's window start moves to that turn's record. So a run of any length holds about one turn's events, and a run that never ends is bounded too (the user's choice, 2026-11-06). This first said "the earlier of that turn's record and its input_through_seq", which section 12 explains is a whole run.

    Measured on the store's 12 largest logs, on disk, without what blobs hold (11,222 turns):

    Median 99th percentile Largest
    Between two committed turns 7.9 KB 23 KB 60 KB
    A whole run, for comparison 8 MB

    Reads that a run-long window would have served move to state(), as they look further back than one turn:

    Fold What reads it today
    The current run's run_started, with its prompt run_agent_prompt, acp_machines_note
    Open tool calls: the started record of each tool_call_owner, signal_approval_needs_you. Up to 6 were open at once, and one stayed open across 28 turns
    Inputs of the current run not yet applied pending_inputs, hold_inputs_to_steer, promote_steered_inputs, void_runless_pending_inputs
    Whether this run was cancelled or failed, and its last attempt run_cancelled_recorded, run_failure_event
    Attached context since the last run ended add_attached_context

    The loop guard reads a run's last calls, but only for native sessions (section 5.1). The doom-loop check reads them for ACP sessions too, so it is a fold (section 12). Phase 1 confirms each of these against the code, and any other that a turn-long window breaks shows in section 7's tests as a fold that differs.

    A log is windowed while its session's agent is an ACP agent: from the first turn such an agent commits, until a run starts with a native one. It also takes a file that holds what it lets go of, and since phase 4 that goes for a read-only log too (section 12). A held snapshot keeps what it holds until it goes, as the list is behind an Arc.

    3.3 history()¶

    It streams the file a record at a time and keeps nothing but up to 64 KiB of lines read ahead, so its memory does not depend on the log's length. Its time does: a read of old events is a pass over the log. A caller keeps only what it needs, as an older page keeps its window and folds the header as it goes, which also gives the page's state for free. That serves pages, event.read, revert, fork, delete, and rare lookups such as attachment_record.

    The parsed read-only cache was the first choice, being the least new code, but its newest log stays whatever its size, and a forever agent's reaches hundreds of MB. It stays for sessions that are not windowed.

    3.4 Frozen context¶

    An ACP session's context is frozen for the life of that ACP session (the user, 2026-11-06), and never refreshed: it has no checkpoint, and the agent holds its own context. Code at b339c902e already does most of this:

    • acp_prompt_context composes it once, when a new ACP session starts: the agent document's body, attachments block, tool instructions, skill listing, and memory snapshot. It goes as the appended system prompt or ahead of the first prompt, and prompt_context records it.
    • A resume sends what was recorded, so a daemon restart or a reinstall does not change it. AGENTS.md is the harness's own.
    • A new ACP session is the only thing that composes again: a lost session, or a change of agent or declaration, as a new session has been told nothing.
    • A skill the agent loads over the bridge goes to it as a tool result, which the agent then holds. So nothing is read again at the agent's own /compact.

    For this spec, that means state() holds the latest prompt_context per agent, a bounded text, and a skill's duplicate check is a set of (name, digest of body), as old SkillLoaded records leave the window. No record is pinned. Phase 1 confirms that a branch after a revert or fork keeps what was recorded.

    3.5 Revert¶

    Wherever its cut falls, as a fold cannot be taken back, a revert reads what stays as a pass, recomputes state() and validation over it, and holds the events since the new latest boundary. It does this before it cuts the file, so a failed read changes nothing. It ends a pass still reading what it cuts with EventLogError::HistoryCut.

    4. Opening without parsing the whole log¶

    Nothing about opening needs the old records as such: it needs what they fold to. So a windowed log saves that beside it, and an open parses only what comes after. This reopens the resume from a checkpoint rejected on 2026-10-14, at the user's request of 2026-11-06: the reason then was that readers needed the whole list, which section 2 removes for ACP sessions.

    4.1 state.json¶

    Written next to events.jsonl, private, as a temporary file renamed over the old one and never synced, as view.json is. It holds, as of a record at a turn's boundary, and names where the window starts, which is at or before that record:

    Part From Today's source
    Where: the record's seq, timestamp, and byte offset; history_format; STATE_VERSION As view.json
    ValidationState, its taint, diagnostics, render_only validate_loaded Whole list
    EventIndex and the prompt block and deferral folds EventStorage Whole list
    LineIndex, and the raw lines no record reproduces, which a line naming blobs no longer counts as (section 12) load_event_jsonl, RawLines Whole file
    The sequences validation refused, which a pass leaves out too EventStorage::refused Whole list
    Where a view cache starts, with the headers it can move to EventStorage::view_start Window
    The projection: meta, usage, runs, fold state projection_fold_with Whole list
    state()'s folds Section 3.1
    The tree load's harvest: grants, delegation records, producer state, a parent's facts state(), as a fold of its own (section 12) Whole list

    None of these types serialized, and some maps have tuple keys, so each has serde derives and its maps written as sorted lists, in JSON, with no new dependency, which also makes two equal states the same bytes. These are internal types, not history: this file is a cache, and it stands outside the compatibility rules.

    Measured by phase 4: 1.9 to 3.2 MB on the logs of section 12, about a quarter of the log.

    4.2 Writing it¶

    After a committed turn, when over 1 MiB of log came since the last write, so a long run is covered and a turn does not pay for a write, and when a session leaves memory, which the store's release counts as. Only the process that owns the log writes it, and only a log with a window has one, a native log once a checkpoint moved its window (section 5.6). The session's slot and the log's locks are held to copy what it holds; serializing and writing take no lock. A crash loses nothing: the log stays the only source of truth. A log shorter than 1 MiB has none (STATE_MIN_LOG_BYTES, the user's choice of 2026-11-08): folding it from its start takes a few milliseconds, and on yunhao-labserver's store the 79 windowed logs under 1 MiB had 16.5 MB of files against 29.6 MB of log, the smallest larger than their logs.

    4.3 Opening¶

    1. Read state.json, and check it as view.json is checked: its history_format, and that the line at its offset is the record it names, whole.
    2. Read the log from the window's start. Records up to the snapshot's join the window as they are; each after it also goes through the same steps a live append takes: validation, index, projection, folds.

    Any mismatch means folding the whole log from its start. That covers a missing or unreadable file, a revert, a converted or rewritten log, and a line the loader would repair. A revert also removes the file. A torn final record is handled by step 2. A file behind its log that still matches is no mismatch: what came after it is the tail, whatever its length.

    That fallback streams too, through the same steps, dropping each record once it has been folded, so it costs time and not memory. Reading the whole file into a buffer, as the loader does today, would not do at this scale. Two kinds of log still read that way, at the peak of section 1 (section 12): one with damage the file does not already answer for, and one of an older history format, which converts in memory.

    Line by line, the tail is read as the loader reads it, including blobs. The log's first record comes from its first line, not from the file.

    4.4 Across builds¶

    A file stays valid across builds, as the store's formats do, so a reinstall costs nothing (the user's question, 2026-11-06). It names a STATE_VERSION, and a different one means folding from the start and writing the file again. There is no converter and no store-wide step, as this is a cache: the log is what is kept.

    The difference from history_format is what can go wrong. A log's meaning is fixed when it is written, while this file holds what a fold computed. A fold whose logic changes leaves the file's shape alone and its contents wrong, quietly, so a version someone must remember to raise is too weak by itself. A test raises the alarm instead: a committed digest of what every fold gives at every turn boundary of the golden logs. A change to a fold or a field that alters any of it fails that test until STATE_VERSION rises and the digest is recorded again. A change the golden logs do not reach is not caught, which is why the golden ACP scenario is built to reach every fold (section 7).

    4.5 What this does elsewhere¶

    • The tree load reads state.json for the root and for each child that has one, and so parses none of them. Native children parse as today.
    • Viewing then parses nothing until the user reads older pages. Skipping the tree load for viewing is no longer needed for ACP trees.
    • Damage in old records is found later (section 11): an open no longer validates records before the offset. A damaged one shows when history() reads it.
    • A read-only open uses the file too, and writes none. It holds only its window, through the file or through the fallback, so a pass of it checks at its end that the owner has not cut the file under it.

    5. Native sessions¶

    A native session really does read its log: each model request is built from it. So its window cannot move per turn. It moves when a checkpoint commits, and memory follows the model's context, not the log: a native forever agent stays bounded because compaction keeps its context bounded. A session with compaction off stays whole.

    5.1 What a model request needs¶

    assemble_model_context reads the latest checkpoint and selects from the whole list. Read at b339c902e, it needs:

    Needed Why it can be old In the design
    Events from the summary's recent_from_seq, or after a provider window's source_through_seq Both start before the checkpoint record The window starts at the earlier of them, so a switch to a model that cannot use the window still has the summary's range
    Every SkillLoaded before the boundary Of any age today, with its full body Not carried (section 5.2): the skill tool reads fresh when called
    The latest AGENTS.md and memory records Latest of their kind, from the run's start Read fresh at each checkpoint (section 5.2)
    Producer admissions not yet consumed Of any age Pinned records, chosen by the fold of section 3.1, with each one's acceptance, and the acceptance of a message admitted in the window (section 12)
    What close_event_dependencies pulls in: an applied input's submission, a started call's turn, a terminated call's start "Late tool completions can refer to events before the retained range" At a checkpoint, pin the closure. Afterwards, open calls' records and inputs not yet applied are pinned, so any later reference resolves
    Latest NativeReplayCut, ToolCallLinked, ToolOutputElided, whether any producer message exists assemble_history_with_replay's forward pass over everything The cut that reaches furthest is pinned, and so are the latest run_started and its latest system_prompt_composed (section 12). Links and elisions matter only for calls in view, which the window and pins hold
    The loop guard's last 64 calls, the doom-loop count Read back to a run's start, which can precede the window Folds, as a ring of digests

    So model_context_events() returns pinned records and the window, in order, and assembly keeps working on a slice. state() chooses what is pinned: open calls, inputs not yet applied, messages not yet consumed. Only producer admissions and back-references are ever pinned, with the few records assembly reads beside them (section 12).

    5.2 Fresh at each checkpoint, and skills when called¶

    A native session's whole context refreshes at a checkpoint, and nothing is pinned for it (the user, 2026-11-06; ACP sessions are the opposite, section 3.4).

    Part When it is read Today
    System prompt, with its skill listing At the checkpoint, inside a run; between runs, at the next run (section 12) At the next run, so a run that never ends keeps the prompt it started with
    Tool round At the checkpoint, for the request right after it At the request after that one
    AGENTS.md, from every coding attachment At the checkpoint At the next run, so a compaction mid-run keeps the old one until then
    Memory snapshot At the checkpoint The same as AGENTS.md
    A skill's body Only when /skill or the skill tool is called Read when called, then pinned forever

    A loaded skill is a regular turn. invoke_skill already reads the skill afresh on every call. A body in the summary's kept range stays verbatim like any other turn; an older one is summarized like any other, and nothing is injected again (the user, 2026-11-06). After a checkpoint, the listing says what is available, and a model that still needs a skill loads it again, which gets its current version. A forever agent would otherwise hold every skill it ever loaded.

    How other harnesses do this, read on 2026-11-06:

    Harness After compaction
    Codex Not injected again, in the code read. The <skill> body is a contextual fragment left out of the kept user messages, and the listing returns with the initial context
    opencode A regular message. A /skill's text goes with its user message and the skill tool's as a tool result, and recentUserMessages strips skills from what it keeps
    DeepSeek harness A regular message, as far as read: its compaction code and design doc name no skills
    Claude Code Injected again, per its docs: each skill's latest invocation, first 5,000 tokens each, 25,000 in all, newest first. Its docs also list "the conversation was compacted" as why a model stops following a skill

    The cost is that a model following a long skill may lose detail in the summary, and must load it again to get it back. That is accepted.

    What follows from that:

    • The duplicate check looks since the latest checkpoint. It now looks at the whole log and records skill_invocation_noted instead of a body, so a load after compaction would show the model nothing.
    • The summarizer's prompt changes. It stops being told to omit loaded skills, and is still told to omit AGENTS.md.
    • What a load granted stays. A skill's permission overlay and model, in memory by session (skills_runtime), survive a refresh point (the user, 2026-11-06), so no approval prompt appears mid-task because of compaction.

    The system prompt is composed again right after a checkpoint inside a run commits, as the run's admission composes it: the agent's body as its document reads now, the runtimes, attachments, tool instructions, and skills blocks, and the plugins' system-prompt hooks. When it differs from the prompt in force it is recorded as system_prompt_composed, and the run's later requests carry it (section 12). The run's agent otherwise stays as it was admitted: its permissions, models, and limits come from the run's frozen policy, which only the next run freezes again.

    AGENTS.md and memory are read as compaction starts, as their size counts in its budgets, and held in memory. They are written just before the commit, so a compaction that fails leaves no trace. If one cannot be read, the latest record is written again, from state(), so a machine that is away does not lose its instructions, as a refresh already does for memory.

    Existing logs. A commit gains an optional context_fresh, which is additive. Selection pins older records only under a commit without it, so existing logs read as they did, and hold those records until their next checkpoint. No format bump is needed.

    In-stream compaction (ChatGPT sign-ins) commits no checkpoint, as built: the server's compaction items stay in their turn's native replay. Its backstop is an ordinary checkpoint, which reads these first like any other (section 12).

    5.3 The check that matters most¶

    A wrong selection changes what the model is sent, and quietly. So the assembled request from pinned records and the window must equal the one from the whole log, at every turn boundary: ModelContext whole (history, native window, replay decisions, assistant prefixes), project_summary_context, compaction_tail_candidates, checkpoint_retained_history, and get_history. In tests, every request also assembles from the whole log and asserts the two match, as the per-append reference fold does. That also protects prompt caching and reasoning bound to its prefix, as an unchanged request cannot break either.

    The golden logs cover compaction with and without a provider window, replay, delegation, revert and fork. A new long scenario adds several compactions, skills loaded before them, a call finishing after a checkpoint, a producer message pending across one, and a model switch (as built, section 12).

    5.4 Switching agents¶

    • ACP to native. Its first model_context_events() after the native run's start reads the log whole, and the log then holds what the model's context needs: with no checkpoint, the whole log, until the next checkpoint or an ACP agent's next committed turn; after an earlier checkpoint, the context since that one at once (as built, section 12). Nothing is lost, and it is no worse than today. Asked of a session whose agent is still ACP, as get_history can, it reads whole and the log keeps its window.
    • Native to ACP. The window narrows at the next committed turn.

    5.5 The approval reviewer gets its own log¶

    The reviewer applies only to native sessions (ACP permissions spec). Today it has no context of its own: its conversation is rendered from the session's log on every escalated approval, "nothing about it is stored separately", and gather passes over the whole log each time, holding what it gathers. Its one reset is an epoch: when the next turn would not fit the window, it starts over from a fresh render within its budgets.

    It gets its own context and durable log, and the same refresh flow (the user, 2026-11-06):

    • A hidden child session holds its conversation: a user turn per review, an assistant turn per verdict, as they were sent. So window, state(), and state.json apply unchanged, and its prompt's bytes survive a restart by being stored rather than by being rendered again.
    • Each review adds only its delta: it reads the session's events since the last review's cut, from the nearest run boundary, so its time follows the gap between reviews and not the log.
    • An epoch is its refresh point. Its system prompt and AGENTS.md are read fresh, and its fresh turn is rendered from its own log's kept entries within today's budgets. It makes no model call to summarize (decision 1).
    • A delegated session's opening (root_messages_until, a pass over the root's log) is written to its log once, when the log is created.
    • Existing sessions have none. The first review creates it with a fresh turn, from one pass over the session's log, and misses the provider's cache once. No conversion is needed.
    • Usage stays recorded on the parent as internal_agent_usage_recorded, and clients keep hiding the child from the session tree.

    As built (section 12, phase 8): the child is reviewer/events.jsonl in the reviewed session's own folder, where nothing that lists or walks sessions looks, and its records are reviewer_turn_recorded. A review reads the session's log after the previous turn's cut, the nearest point a pass can start, not a run boundary. The epoch's first turn holds what the log kept and is where its window starts, as a checkpoint is a native model's. A revert drops the turns whose verdicts it cuts, and a fork copies those it keeps.

    5.6 state.json¶

    The same file, adding the pinned records, written after a checkpoint commits and per 1 MiB of log, and as the session leaves memory. A session with no checkpoint yet has a whole window, so opening reads the log, which its context limit bounds. As built (section 12): the file holds the pinned records themselves and says the window is a model's context, and an open reads the window from the file as an ACP agent's does and puts the pinned records before it.

    6. What else grows with the log¶

    Trimming events leaves these, each small today and each linear in the log. state.json holds them, so they cost twice: in memory, and in writing the file.

    11. Decisions¶

    From the user, 2026-11-06:

    1. Damage in old records is found when they are read.
    2. history() streams from disk and keeps nothing.
    3. state.json is kept across builds by a version (section 4.4), rather than tied to the exact build.
    4. An append naming something older than the validation floor is refused (section 6).
    5. An ACP session's window moves per committed turn, not per run.
    6. Native sessions are in this spec.
    7. A native session's context is read fresh at each checkpoint, with nothing pinned for it. An ACP session's stays frozen for the life of that ACP session.
    8. A loaded skill is a regular turn: read when called, summarized like any other, and not injected again. What a load granted stays across refresh points.
    9. The approval reviewer gets its own context and durable log, and the refresh flow.
    10. A reviewer's refresh makes no model call to summarize: it renders from its own entries.
    11. The reviewer's log is a hidden child session.
    12. The order is ACP, then native, then the reviewer.

    • Attempts: each lifecycle record names an unfinished attempt, an abandon follows its commit at once, and a replay's base names an earlier attempt of its own run, which only native runs record. Unfinished attempts of the runs kept stay, and the latest 16 that ended.
    • Calls: an ACP call can stay open across many turns, and a background job's call ends after its run does, so a call stays until it ends, whatever its age. The latest 16 ended stay.

    How a fold and a whole read are compared. A whole read (validate_loaded, rebuild_validation) keeps every map as it validates, since a record may name anything before it, and lets go of what settled at its end (finish_whole). A record-at-a-time validation lets go after every record that could let something go, not only at a committed turn: letting go at turns only kept, at a log's tip, what had settled since, and a fork's prefix ending mid-run differed from its parse. What it lets go of depends only on what it holds, and no later valid record brings it back, so the two keep the same. assert_agrees_with_whole checks that what a fold holds, a whole read holds the same, and that once each lets go of all that settled they are equal, which a log that went native at its end needs (a native log does not let go). A state file and its tail are compared with a fold of the whole file exactly, as before. The producer fold is compared with its scan by agrees_with_whole, and the decisions and cancelled runs by what the fold keeps of the scan's.

    • A record a fold refuses goes to the whole read. A log written before this phase may hold a record naming what a fold now lets go of.     Closing note: what the branch did, and what remains open. Phases 1 to 8 made a session's memory follow what it uses rather than its log: an ACP session holds about one turn and its state() folds, a native one the model's context since its last checkpoint and what that pins, and the reviewer the turns since its last epoch; each opens from state.json without a full parse, the bounds of section 6 keep the folds and the file flat to 100 times today's largest log, and an ordinary turn, a compaction, and an escalated approval read no pass over the whole log. Measured: an ACP session's live heap fell by 74 to 81 percent and its open's peak by 85 to 90; a synthetic log at 100 times holds under 2 MB without delegations; a native log that compacts holds 1.0 to 2.7 MB from 1 to 100 times; a review reads the delta between reviews. Open:

    • The harvest's delegation records still grow with the log (phase 5): about 26 MB of heap at 100 times the stress rate. Bounding them is the delegation registry's change.
    • A damaged log reads whole, at the old peak (phase 4), and so does a log of an older history format on a read-only open; so does a native log that went from ACP to native at its first model context.
    • Native children with no checkpoint parse at each tree load, as they have no state.json, and so does any child this process never owned (phases 4 and 7).
    • The long native scenario of phase 6 does not go through a real log (phase 7): its through-disk counterpart is the synthetic native log.
    • Daemon RSS was not measured for native sessions, nor for phase 5's bounds or the reviewer's log; the ACP numbers are phase 3's and 4's.
    • The log's size on disk grows forever (section 9), and with it older pages and a fold from the start; only sealed chunks would bound it.
    • The reviewer's log: a future history format bump starts reviewer logs over instead of converting them; a session whose reviewer keeps failing passes over its log once more after each restart; the cursor's bounds are chosen, not measured.
    • Real logs were checked at their tips, not at every turn boundary, after phase 4; the store's native forever agents, once one runs, should be measured as section 8 asks for phase 7.

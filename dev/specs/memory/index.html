    Memory¶

    Status: implemented (2026-10-19); approved the same day. Decisions are listed in section 1 and the sections that follow; none are open (section 15). How each phase settled, with its deviations, is in section 16; later decisions are dated addenda there (section 16.6, section 16.7, section 16.8, section 16.9, section 16.10). This spec builds on the runtimes spec and the runtime capabilities spec, and adds the term machine to their vocabulary.

    1. Goal and scope¶

    Agents forget everything between sessions. This spec gives the daemon a memory: Markdown notes the agent and the user write, which later sessions see or find again. Memory is gathered context. Reading or writing it never changes a session's attachments, runtimes, or workspaces.

    Decided 2026-10-19:

    • Memory is part of the global runtime. A session with global attached has memory; detaching global turns it off for that session.
    • Each memory is one Markdown file with frontmatter, as in Claude Code and Hermes. There is no database and no embedding index.
    • Memory has four layers: user, agent, machine, and project.
    • The user layer is a fixed set of category files, ~/.cookie-agent/memory/user/<category>.md. The user adds a category by creating a file. When the daemon starts and ~/.cookie-agent/memory does not exist, it creates a default set.
    • Machine is a new daemon concept: the computer a runtime runs on. The daemon groups runtimes into machines automatically, and the user regroups, renames, and merges them from any client. Groupings live only in the daemon's machine registry, not in configuration.
    • A project is just a folder under ~/.cookie-agent/memory/projects/. It is not configuration and is not bound to workspaces: the agent finds the project a task relates to by searching memory keywords.
    • Each memory declares keywords, case-insensitive strings that search matches against.
    • Memory tools follow permission rules under two actions: memory for searching and reading, memory_write for writing, editing, and deleting. The resource is the memory URL.
    • Agent memory is one file per agent ID, memory/agents/<agent_id>.md: what an agent has learned about doing its own job, such as what the user cares about in reviews. A run sees its own agent's file in full in the snapshot, like a user category.
    • Delegated subagents see only their own agent's memory in their snapshot and may write only their own agent's memory. Every other layer is read-only for them through search and read.
    • Which agents' memory an agent may search, read, or write is left to permission rules on agent:// URLs; there is no built-in restriction besides the delegated-write rule above. agent://self in a rule means the run's own agent.
    • Agents that declare no memory rules get defaults by mode: primary and all agents may read and write all memory, subagent agents may read all memory and write only their own agent file (section 9.2). (Replaced 2026-10-22: the defaults now depend on whether the run is delegated; see the note in section 9.2 and section 16.9.11.)
    • A snapshot changes only at the points in section 7.2; the user's own edits from a client do not refresh open sessions.
    • Machine memory folders and URLs use machine names; renaming a machine moves its folder in the same step.
    • The user files, the run's agent's memories, and an index of the session's machine memories reach the model as a snapshot taken once and kept stable, so the prompt cache survives writes. Project memory is never injected; the agent searches for it.

    Out of scope: search over past sessions, embedding or semantic recall, OpenClaw-style intents and triggers, scanning memory for prompt injection, recording which session wrote a memory, and automatic recall or saving: the model searches and saves on its own judgement. Adding matched memories to a user message whose text hits their keywords, and a silent save pass before compaction, are candidates for a later spec.

    2. Vocabulary¶

    The first five terms come from the runtimes specs and are unchanged; this spec adds the rest.

    Term Meaning
    Daemon The gateway: configuration, sessions, the model loop, permissions. It holds all memory.
    Runtime A tool provider connected to the daemon, identified by its runtime ID. The built-in global and local runtimes run inside the daemon process; spawned, dial-in, and client runtimes connect over the runtime protocol.
    Capability Something a runtime offers that sessions attach separately, such as global or coding.
    Capability instance A capability opened for one workspace or none: (runtime ID, capability, canonical workspace).
    Attachment A durable session fact binding the session to a capability instance.
    Machine A computer that runtimes run on, with a machine name. Every runtime belongs to exactly one machine. The daemon's own machine hosts global and local. See section 3.
    Memory One Markdown file with description and keywords frontmatter, addressed by a memory URL.
    Memory layer What a memory is about: user (the user, everywhere), agent (one agent's way of doing its job), machine (one machine), or project (one body of work).
    Category A file of the user layer, such as preferences. Categories are fixed by the files that exist.
    Project A named group of memories about one body of work. It exists as long as its folder does.
    Agent An agent definition from the agent registry, identified by its agent ID, such as default or reviewer. A run has one agent.
    Memory URL user://<category>, agent://<agent>, machine://<machine>/<name>, or project://<project>/<name>. Tools, permission rules, and clients all use it.
    Snapshot The memory a session's model sees without searching, recorded once as a memory_loaded event.

    Model-facing text says "project", never "folder"; "folder" appears only where this spec describes the files on disk.

    3. Machines¶

    3.1 Identity¶

    A machine is identified by a machine ID: the opaque digest that cookie_agent_protocol::paths::machine_id() already computes for clients, from /etc/machine-id or /var/lib/dbus/machine-id, or from a random ID kept in ~/.cookie-agent/machine-id when the OS has none.

    Runtime protocol 1.1.0 adds an optional machine object to InitializeResult:

    "machine": { "id": "3f9c…", "host_name": "labpc" }

    cookie runtime serve fills it from paths::machine_id() and the host name. The built-in global and local runtimes use the daemon's own values. The field is optional: a runtime that cannot tell, such as a third-party one, leaves it out.

    3.2 Machine registry¶

    The daemon keeps every machine in one registry, <data_root>/machines.json. It is daemon state, not configuration: there is no [machines] table. Clients change it only through the machines.* RPCs (section 3.3), and the user never needs to edit the file.

    machines.json {
  version: 1,
  machines: [ { name, ids: [ machine ID ], runtimes: [ runtime ID ] } ]
}

    ids are the machine IDs the machine stands for; runtimes are runtime IDs pinned to it whatever they report. A machine ID or a runtime ID appears on at most one machine.

    The daemon assigns each runtime to a machine when it connects, in this order:

    1. The machine whose runtimes pins the runtime ID.
    2. The machine whose ids contains the reported machine ID.
    3. With a reported ID: a new machine with that ID, named after the sanitized host name, with -2, -3, … added on a clash.
    4. With no reported ID: a new machine pinning that runtime ID, named after the runtime ID.

    New machines are written to the registry at once, so a machine keeps its name and its memory across restarts and host renames.

    Machine names follow the runtime ID rule: a lowercase ASCII letter, then up to 31 lowercase letters, digits, _, or -.

    Typical reasons to regroup by hand: a container reports its own machine ID, two OS users share a host that has no /etc/machine-id, a third-party runtime reports nothing, or an automatic name is unhelpful.

    3.3 Managing machines¶

    Clients manage the registry through these RPCs. They are user actions: no model tool changes machines.

    RPC Effect
    machines.list Every machine: name, IDs, pinned runtimes, the connected runtimes assigned to it and why (pinned or by ID), platform, and its number of memories
    machines.rename { machine, name } Renames the machine and moves memory/machines/<old>/ to <new>/. Fails, changing nothing, if the name is taken or the folder cannot be moved.
    machines.assign { runtime, machine } Pins a runtime ID to a machine, creating the machine when the name is new, and removes the pin from any other machine
    machines.unassign { runtime } Removes a runtime's pin, so it falls back to its reported machine ID
    machines.merge { from, into } Moves from's IDs and pins to into, moves its memories into into's folder, and removes from. Fails, changing nothing, if a memory name exists in both.
    machines.forget { machine } Removes a machine with no connected runtimes and no memories

    Each change takes the memory lock (section 4.4) while it rewrites the registry and moves folders, so a memory write never races a rename or merge. A change moves the affected connected runtimes at once and sends a machines.changed notification to every client. Sessions pick it up like any attachment change: their system prompt names the new machine from their next run, and their next root run takes a new memory snapshot because their set of machines changed (section 7.2).

    Machines also show up here:

    • runtimes.list entries gain machine (the name).
    • The TUI /runtime panel groups runtimes by machine and offers rename, move runtime to machine, merge, and forget, each target with its hover.
    • cookie machine list|rename|assign|unassign|merge|forget calls the same RPCs, so it works against a remote daemon.
    • The system prompt and tool descriptions name machines (section 3.4).
    • Machines key the machine memory layer (section 4).

    Permission selectors (action@runtime_id) are unchanged; action@machine is not part of this spec.

    3.4 What the model is told¶

    Today the system prompt's runtimes block (system prompt reference) and the tool-description notes call each attachment a "runtime" and give a platform per runtime. This spec changes both to the vocabulary of section 2: the model is told about attachments, nested in the runtime that serves them and the machine that runtime runs on. What the model most needs from this is which tools share files: attachments on one machine see the same filesystem, attachments on different machines do not.

    global is still never mentioned: its tools are not tied to a workspace. The platform belongs to the machine; when runtimes grouped into one machine report different platforms (a container, WSL), each <runtime> carries its own platform instead. An attachment carries its capability's kind and its workspace.

    One attachment besides global: unchanged except for the machine line.

    Working directory: /home/me/web
Machine: laptop (linux)

    The machine line is left out when the daemon cannot name the machine; the platform in parentheses is left out when the runtime reports none. An attachment without a workspace still adds nothing.

    Several attachments besides global: machines in the order the session's attachments first name them, runtimes within a machine and attachments within a runtime in the same order.

    This session has several attachments. An attachment is a set of tools bound
to a workspace, served by a runtime running on a machine. Each tool's
description names the attachment it belongs to, and file tools and bash
resolve relative paths against that attachment's workspace. Attachments on
the same machine share its files; a path on one machine means nothing on
another. A tool several attachments offer is named `<attachment>_<tool>`.
<machines>
<machine name="laptop" platform="linux">
<runtime name="local">
<attachment name="local_web" kind="coding" workspace="/home/me/web"/>
<attachment name="local_api" kind="coding" workspace="/home/me/api"/>
</runtime>
</machine>
<machine name="labpc" platform="linux">
<runtime name="labpc">
<attachment name="labpc_api" kind="coding" workspace="/srv/api"/>
</runtime>
</machine>
</machines>

    With several attachments, each tool of an attachment ends its description with Belongs to attachment `labpc_api` (runtime `labpc` on machine `labpc`). instead of today's Runs on runtime `labpc_api`..

    Machine names are part of the composed prompt, so renaming a machine changes the system prompt of sessions on it from their next run, like attaching or detaching a runtime does today.

    4. Memory layers and files¶

    4.1 Layout¶

    ~/.cookie-agent/memory/            (<data_root>/memory)
  user/
    profile.md  preferences.md  feedback.md  references.md
  agents/<agent>.md
  machines/<machine>/<name>.md
  projects/<project>/<name>.md
    Layer About Who creates files Who deletes files
    user The user, in every task The user only The user only; the agent's delete clears the body (section 16.6)
    agent One agent's way of doing its job: what the user wants from this role, lessons, checklists The daemon, one for every agent that is not internal (section 16.7) The user; the daemon removes an empty file it made when the agent goes (section 16.7); the agent's delete clears the body (section 16.6)
    machine One machine: OS quirks, toolchains, paths, hardware, rules such as "read-only unless asked" The agent or the user The agent or the user
    project One body of work: conventions, decisions, gotchas, where things are The agent or the user; writing the first memory creates the project (superseded: projects are created from a client, projects spec) The agent or the user; the project disappears with its last memory (superseded: the folder goes with its project)

    The agent may edit any existing user category but cannot add or remove one. When it deletes a user category or an agent file, the file stays with its frontmatter and only the body is cleared.

    An agent's file outlives the agent: when an agent document is removed or renamed, its memory stays on disk, and memory.list and /memory show the file as belonging to no current agent; only an empty file the daemon made and nobody touched goes with it (section 16.7). Internal agents, such as compaction and titling, never get memory.

    4.2 Names¶

    Categories, memory names, and project names are a lowercase ASCII letter or digit followed by up to 63 lowercase letters, digits, or -. Agent IDs already fit this rule. Files whose names break the rule, files without the .md extension, and anything nested deeper than the layout are ignored and listed as invalid in memory.list.

    4.3 File format¶

    ---
description: Build and test conventions for cookie-agent
keywords: [cargo, clippy, msrv, no-fail-fast, cookie-agent]
---
- Run `cargo test --no-fail-fast`; plain `cargo test` stops at the first
  failing crate.
    Key Type Rule
    description string Required. One line, 1 to 200 characters; shown in indexes and search results.
    keywords list of strings Optional, at most 32 entries of 1 to 64 characters each, no line breaks. Matched case-insensitively (section 8.1).

    The body is Markdown and may be empty. A whole file is at most [memory] max_file_bytes.

    A file with frontmatter that does not parse, an unknown key, a wrong type, or an oversized body is invalid: search and the snapshot skip it, and memory.list and /memory report it with the reason. One invalid file never hides the others.

    4.4 Revisions and writes¶

    Every read returns a revision, the first 16 hex digits of the SHA-256 of the file's bytes. A write or delete of an existing file must send the revision it last read; if the file changed since, the call fails and returns the current revision. This stops two sessions, or a session and the user's editor, from silently overwriting each other.

    A write goes to a temporary file in the same folder, is flushed, and is renamed over the target. Writes take an advisory lock on <data_root>/memory/.lock, because two plain cookie processes are two daemons sharing one data root.

    4.5 First start¶

    When the daemon starts and <data_root>/memory does not exist, it creates user/, agents/, machines/, and projects/, and these category files with empty bodies:

    File description keywords
    profile.md Who the user is: role, expertise, languages, and the machines and accounts they use [user, role, background, expertise]
    preferences.md How the user wants work done: style, tools, formats, tone, and things to always or never do [prefer, style, always, never, format]
    feedback.md Corrections and confirmed approaches from the user, each with why it matters [feedback, correction, mistake, approach]
    references.md Where to find things: URLs, dashboards, documentation, related repositories [link, url, docs, dashboard, repo]

    If the folder exists, the daemon never adds, changes, or recreates anything in it, even when user/ is empty.

    5. Memory URLs¶

    URL File
    user://<category> memory/user/<category>.md
    agent://<agent> memory/agents/<agent>.md
    machine://<machine>/<name> memory/machines/<machine>/<name>.md
    project://<project>/<name> memory/projects/<project>/<name>.md

    Each segment follows the name rules of section 4.2, so a URL maps to exactly one path inside memory/ and can never escape it. The daemon parses URLs strictly: other schemes, extra segments, .md suffixes, and upper-case letters are errors, not normalized.

    6. Which memories a session reaches¶

    Memory is available to a run when all of these hold:

    1. The session has global attached.
    2. The run's agent can see the memory tools: its permissions or the session overlay hold an allow or ask rule for memory (section 9); every non-internal agent has one by default (section 9.2). No separate frontmatter switch exists: memory: deny in an agent document turns memory off.

    Without a memory rule the agent gets no snapshot, no memory prompt, and no memory tools at all, even if it has memory_write rules: writing without reading is not offered.

    A root run gets the full snapshot, memory_search, and memory_read, plus the write tools when it can see memory_write.

    A delegated run gets a snapshot of its own agent's memory only, memory_search, and memory_read, plus the write tools when it can see memory_write. Its writes are refused for any URL but agent://<its agent>, whatever its rules say. An explorer subagent can gather context from every layer, and a reviewer subagent keeps its own lessons, while only the root agent decides what to keep about the user, machines, and projects.

    The session's machines are the machines of the session's attachments other than global, matching the machines the system prompt names (section 3.4). A session with only global has the daemon's machine, since that is where its tools run.

    Layer Root run's snapshot Delegated run's snapshot Search and read reach
    user Every valid category file in full No All categories, as memory rules allow
    agent The run's agent's file in full The run's agent's file in full Every agent's file, as memory rules allow
    machine Index of the session's machines' memories No Every machine's, as memory rules allow
    project No No Every project's, as memory rules allow

    Search and read are always filtered by the memory rules (section 9); the last column is what they reach before those rules.

    7. Snapshot¶

    7.1 Content¶

    At the admission of a run that needs one (section 7.2), the daemon reads memory and appends one durable event:

    memory_loaded {
  delegated: bool,
  writable: bool,
  user: [ { category, description, keywords, body } ],
  user_omitted: [ category ],
  agent: { agent, memory: { description, keywords, body }? },
  machines: [ {
    machine, attachments: [ attachment name ],
    memories: [ { url, description, keywords } ],
    omitted: <count>
  } ]
}
    • delegated and writable record whether the run was delegated and whether it could see the write tools, so a replay renders the same instructions the model saw. A delegated event has no user and no machines.
    • user holds every valid category file, in name order, including empty ones. A file is included whole or not at all: when the next file would push the rendered user section past [memory] snapshot_user_bytes, it and every later one go to user_omitted, which keeps only their names.
    • agent names the run's agent and holds its file whole, or no memory when the file does not exist or is invalid. A file is at most [memory] max_file_bytes, so it always fits; it is present whenever memory is available.
    • machines holds one entry per machine of the session, in the order the session's attachments first name them, with the attachment names of the session that run there. A machine with no memories still has an entry. Its memories are listed newest file first; when the rendered index reaches [memory] snapshot_index_bytes (summed over all machines), the rest are only counted in omitted.
    • An empty event, with no user, agent, or machines, records that memory is no longer available (section 7.2).

    Both snapshot limits and the agent file's size are measured on the rendered text and stay, with the fixed text, under the 64 KiB event bound.

    7.2 When a snapshot is taken¶

    The memory prompt follows the memory tools. A run shows the memory snapshot exactly when it is offered the memory tools: never when global is detached, or when the agent and session overlay have no memory rule. Its save paragraph appears exactly when the run is offered memory_write.

    Root and delegated runs follow the same rules, each in its own session's log. A run appends a new memory_loaded when any of these holds:

    • memory is available and the session has no non-empty memory_loaded yet;
    • memory is available and a compaction finished after the latest one;
    • the set of the session's machines changed since the latest one;
    • the run's agent differs from the latest one's;
    • whether memory is available changed since the latest one: global was attached or detached, or the session overlay gained or lost its memory rule;
    • whether the run can see memory_write changed since the latest one.

    When memory is not available, the new event is empty, so the prompt disappears from that run on and a replay shows exactly what the model saw. Turning memory off this way changes the history the model sees, so it costs one prompt-cache miss, just as detaching a runtime already does.

    Writes in the middle of a session change the files, never the current snapshot. Edits the user makes through /memory or the CLI do not refresh open sessions either; new sessions and the next compaction see them. Only the points above ever change the snapshot.

    7.3 Place in history¶

    History assembly renders the latest memory_loaded as one user turn and pins it through compaction like AGENTS.md. A run's history starts:

    Position Role Content Changes when

    Rules the examples follow:

    1. Fixed text. The opening paragraphs are constant, with one version for root runs and one for delegated runs. Without writable the save paragraph is left out. The fixed text is part of this spec and changes only with a history format change, so equal events always render equal text.
    2. User section. One <memory> element per category file with a body, in name order. Categories with an empty body are listed on one Empty: line, so the model knows where to save. Categories in user_omitted are listed on a Not shown (too long): user://… line; the model reads them with memory_read.
    3. Agent section. Headed with the agent ID. One <memory> element for the agent's file. A file with an empty body, or none, leaves the section out (section 16.7; this replaced a No memory yet. line).
    4. Machines section. One <machine> element per machine, naming the session's attachments on it, which match the <attachment> names in the system prompt's machines block and the tool prefixes. One line per memory: url: description [keywords: …]. A machine without memories says No memories yet. A machine with omitted memories ends with - N more; search with layer "machine".
    5. Empty layers. The heading of a section with nothing to show is kept, followed by None., so the model always sees all of the structure. The whole turn is left out only when the latest event is empty, which is the case whenever the agent has no memory rule (section 6).
    6. Escaping. Attribute values escape &, <, >, and ". Bodies stay readable Markdown: only a < that starts one of this turn's own tag names (memory, machine, system-reminder, with or without /, in any case) is written as &lt;, so Vec<T> stays as it is but a body cannot close or open an element.
    7. Bytes. snapshot_user_bytes covers the user section from its heading to its last line and snapshot_index_bytes the machines section. The agent section is bounded by max_file_bytes. The fixed text is not counted against any of them.

    8. Tools¶

    The global runtime provides five tools. All arguments are strict (unknown fields fail).

    Tool Arguments Result
    memory_search query (1 to 200 characters), layer? (user, agent, machine, project), limit? (1 to 25, default 10) Ranked matches the rules let the agent see (section 9.3): URL, description, keywords, and up to three matching body lines each. layer only narrows the results; it is not a permission resource.
    memory_read url Frontmatter, body, and revision
    memory_write url, description?, keywords?, body, revision? Creates or replaces one file; returns the new revision. Without revision the file must not exist; with it, it must exist at that revision. Creating a user:// file is refused; an agent:// file may be created only for an agent ID in the registry. description is required except for agent://, whose description the daemon sets (section 16.7); keywords defaults to none.
    memory_edit url, old, new, revision Replaces the one occurrence of old in the body; fails when old occurs zero or several times
    memory_delete url, revision Deletes a machine:// or project:// file. A user:// or agent:// file cannot be deleted: its body is cleared, its frontmatter kept as written, and the result says so with the new revision (section 16.6)

    8.1 memory_search¶

    The query is split into terms on whitespace. A memory's score is, in order of weight:

    1. each keyword that occurs in the query, case-insensitively;
    2. each query term that occurs in the memory's name, its project or machine name, or its description (an agent file's name is its agent ID);
    3. each query term that occurs in the body.

    Memories with score zero are left out; ties go to the more recently modified file. Searching reads the files each time; there is no index on disk. With a project layer of hundreds of small files this stays in the low milliseconds, and an in-memory cache keyed by file modification time can come later.

    The tool description tells the model to give projects keywords that identify them across machines: repository names, remote URLs, and <machine>:<path> strings for each place the work lives.

    9. Permissions¶

    Memory tools use two permission actions, both added to PermissionAction::BUILT_IN:

    Action Tools Resource label
    memory memory_search, memory_read memory_read: the memory URL. memory_search: none; each result is checked instead (section 9.3)
    memory_write memory_write, memory_edit, memory_delete The memory URL

    Rules then match by layer, agent, machine, or project:

    permissions:
  memory:
    "agent://reviewer": deny
    "*": allow
  memory_write:
    "user://*": ask
    "agent://default": allow
    "project://*": allow
    "machine://labpc/*": deny

    Rules are part of each agent's own document, so agent:// rules are how an agent is given, or denied, access to other agents' memories. A delegated run's writes to any URL but its own agent://<agent> are refused before rules are consulted.

    Both actions take selectors like any other (memory_write@global).

    9.1 agent://self¶

    In a rule pattern, agent://self stands for the run's own agent: the daemon replaces it with agent://<agent ID> before matching, so "agent://self": allow works in any agent document and in the defaults below. self becomes a reserved agent ID: an authored self.md is rejected like the other reserved IDs. A memory URL itself never contains self; tools and clients always use the real agent ID.

    9.2 Default rules¶

    Today an agent document that names no rule for an action gets none, so the action's tools stay hidden. The two memory actions are the exception: when an agent document, the built-in default agent included, has no key for memory or for memory_write, the daemon supplies that action's rules by the agent's mode:

    Mode memory memory_write
    primary, all allow allow
    subagent allow "agent://self": allow
    internal none none

    A document that declares the key replaces the default for that action entirely, so memory: deny turns memory off for an agent, and memory_write: ask makes every write ask. Session overlays apply on top as for any action.

    With these defaults every non-internal agent has memory, and therefore the snapshot, whenever its session has global attached (section 6). An all-mode agent running delegated is still limited to writing its own agent:// file by the delegated-write rule above.

    Note 2026-10-22: the memory defaults are removed. memory and memory_write are now denied by default like any other action: no mode, and not the built-in default agent, gets rules for them, so an agent document with no memory key has no memory tools, no memory_search, and no snapshot. Memory is opt-in, with memory: allow (or per-URL rules) and memory_write: … in the agent document, or a session overlay rule. The table above records the defaults as they were from 2026-10-19 to 2026-10-22. Delegated runs regain one default, their own agent file (section 16.9.11). list_runtimes keeps its default, and mcp gained one (runtimes spec section 7.1). Later the same day root runs regained a default too, chosen by delegation rather than by mode: read everything, write what is related to the session (section 16.9.11, decided 2026-10-22). Memory is opt-in no longer; memory: deny turns it off, as under the table above.

    9.3 Search results¶

    memory_search always searches every memory and is never checked as a whole: there is no approval prompt for a search. Instead, each match is checked against the memory rules with its URL as the resource, as if it were read:

    Rule for the match's URL In the results
    allow URL, description, keywords, and matching body lines
    ask URL and description only; reading it goes through the approval prompt
    deny, or no matching rule Left out, and not counted

    So a rule set like memory: { "project://*": allow } searches freely and only ever sees project memories, and "agent://reviewer": deny hides that agent's file from every search. limit applies after filtering.

    Deviations and readings of the spec:

    • The lock creates no memory folder. While <data_root>/memory does not exist, MemoryRoot::lock holds no file and creates nothing, so that phase 2's first start (section 4.5), which keys off the folder's absence, still runs for a data root phase 1 has used. Registry changes are then serialized within the daemon only; two daemons sharing a data root without a memory folder can race a registry write (each change rereads the file first, so the window is the write itself). Once phase 2 creates the folder at start, the lock always holds a file.
    • Host names become machine names by their first label (labpc.lan is labpc), lowercased, with each run of other characters replaced by -, edges trimmed, host- in front of a name that does not start with a letter, machine when nothing is left, and at most 32 bytes; a clash shortens the base to keep -2, -3, … within 32 bytes.
    • host_name is optional in InitializeResult.machine; a machine ID without it gets the name machine. A machine whose ID is empty, longer than 128 bytes, or not printable ASCII, or whose host name is longer than 255 bytes or holds control characters, is read as not reported.
    • A runtime's machine is never stored with the runtime. It is computed from the registry when asked for, so a registry change "moves" connected runtimes by being the new answer. The daemon places connected runtimes at start and after every runtime registry change, so a new machine is written as soon as a runtime it belongs to connects.
    • Assigned-by. A runtime placed by rule 4 reports assigned_by: pinned, since its new machine pins it; one placed by rule 3 reports machine_id.
    • Every machines.* change answers with MachinesListResult, the machines afterwards, and machines.changed is an empty object; it is also sent when a connecting runtime creates a machine. Params use the spec's member names (runtime, machine, name, from, into).
    • Refusals are registry errors: machine_not_found, machine_name_taken (another machine, or a memory folder that belongs to none, has the name), machine_in_use, machine_memory_conflict, machine_merge_self, runtime_not_pinned (unassigning a runtime no machine pins), and machine_store_failed.
    • Forget refuses a machine whose memory folder holds anything at all, not only memories, so it never deletes a file; an empty folder goes with the machine. memories in machines.list counts *.md files.
    • machines.json is strict like configuration: an unknown member, another version, a malformed name or machine ID, or an ID or runtime on two machines fails the daemon's start with the file's path.
    • Assigning a new name creates the machine without checking for a memory folder of that name; a stray folder becomes the new machine's.
    • Prompt text. The several-attachments paragraph is one line, as the previous runtimes paragraph was; the spec's line breaks are wrapping. An attachment whose machine the daemon cannot name gets a <machine> of its own without a name, since nothing says it shares files with another; a tool note then reads Belongs to attachment `x` (runtime `r`).. The platform goes on the machine only when every attachment on it reports the same one.
    • The TUI shows machines in a second view of the /runtime panel (m or its tab) rather than regrouping the attachment list; the attachment rows name their runtime's machine.
    • Corpora. No runtime/1.1.0 or client/1.2.0 corpus directory was recorded, as none was for client/1.1.0: the recorder's session does not exercise the new methods, and its runtime handshake would record the recording machine's host name.     Landed 2026-10-19: memory URLs, the file format and revisions, the store's reads, listings, writes, edits, and deletes, search, the first start, and [memory] with its configuration reference page (Memory). Nothing calls the store yet besides the first start; no protocol changed.

    Where things are, for the later phases (all in crate::memory, crates/engine/src/memory.rs and memory/):

    • URLs (memory/url.rs): MemoryUrl::parse(&str) and its Display; MemoryLayer (parse, as_str), MemoryName, url.layer(), url.name(), url.group() (the machine or project), and relative_path().
    • Files (memory/file.rs): MemoryDocument::new(description, keywords, body) validates a tool write's arguments, MemoryDocument::parse(bytes, max_file_bytes) a file or a client's whole text, and render() gives the file text. Failures are InvalidMemory(reason). MemoryRevision::of hashes bytes; MemoryRevision::parse checks a revision a caller sent.
    • Store (memory/store.rs, methods of MemoryRoot): read(url, max_file_bytes), list(&ListScope, max_file_bytes) (scopes All, Layer, Agent, Machine, Project; entries carry URL, revision, size, modification time, and the parsed memory or why it is invalid; ignored lists what breaks the layout), write(url, text, expected_revision, origin, agent_exists, max_file_bytes), edit(url, old, new, revision, max_file_bytes), and delete(url, revision, origin). Origin::Model or Origin::User carries who asks; the caller passes agent_exists, a predicate over the agent registry. Errors are StoreError: NotFound, Exists and RevisionMismatch (both with the current revision), Invalid, Refused, NoOccurrence, SeveralOccurrences, and Memory for lock and I/O failures.
    • Search (memory/search.rs): MemoryRoot::search(query, layer, limit, max_file_bytes, visibility), where visibility maps each candidate's URL to Visibility::Full, Summary, or Hidden from the memory rules. Hits are SearchHit { url, description, detail }, with detail (keywords and matching lines) only for Full.

MemoryConfig::EVENT_MAX_BYTES and RENDER_OVERHEAD_BYTES in cookie_agent_config are the bound phase 3's memory_loaded validation uses.
    • Blocking. Every store call is synchronous file I/O, and changes wait up to 5 s for the memory lock, so async callers run them on a blocking thread.

    Deviations and readings of the spec:

    • Segment rules. The machine segment of machine:// follows the machine name rule of section 3.2 (a letter first, _ allowed, at most 32 bytes), not section 4.2, because machine folders carry machine names. The agent segment of agent:// follows the agent ID rule, slightly stricter than section 4.2 (no trailing or doubled -), and self is refused.
    • Parsing. The frontmatter is parsed with serde_yaml, as agent documents are, into a strict struct, so a duplicate key is also invalid. Lengths are counted in Unicode characters. \r\n reads as \n; any other control character but newline and tab makes a file on disk invalid, not only a write, so the snapshot never carries one. A file that is not UTF-8, or a path that is not a regular file (a symbolic link included), is invalid.
    • Rendering. A tool write's file is rendered as description: …, then keywords: [a, b] (left out when empty), then the body unchanged. Each value is written plain when it reads back the same, double-quoted otherwise. A write from whole text (the client's memory.write) keeps the text as given once it validates. An edit re-renders the file, so YAML comments or quoting the user wrote in the frontmatter do not survive an edit; an empty old counts as not occurring.
    • Who may create. The user:// creation refusal applies to Origin::Model only, since the user adds categories (section 4.1). The agent registry check for a new agent:// file applies to both origins.
    • Folders. A write creates any missing folder on its way, the memory folder included if the user removed it. Deleting a project's last memory removes its folder only when nothing else is left in it; a machine's folder stays, since it belongs to the machine registry and machines.forget removes an empty one.
    • Listing. Ignored entries carry a reason: not a .md file, a name that breaks the rule, a name that is not an agent ID (self.md included), a folder name that is not a machine name, nested deeper than the layout, a file where a folder belongs, not a regular file, or something in the memory folder outside the four layers (.lock excepted). A file over max_file_bytes is not read whole by a listing or search; its revision is hashed while streaming it.
    • Search. Scores compare by keyword hits, then name and description hits, then body hits, each count beating any amount of the next, rather than adding weighted counts. A keyword hits when it occurs anywhere in the lower-cased query, each distinct keyword once; repeated query terms count once. Matching lines are body lines holding any query term, trailing whitespace trimmed. Ties go to the newer file, then to the URL. visibility is asked in rank order and only until limit hits are found; a Summary hit keeps the rank its full score gives it. Checking the query (1 to 200 characters) and limit (1 to 25) is left to the tool.
    • First start. Engine open runs it right after the session store opens and before the machine registry, so nothing has taken the memory lock or moved a machine folder first; phase 1's lock and folder moves create no memory folder. The folder is built as <data_root>/.memory.<id>.tmp and renamed into place, so a crash leaves no half-made folder that later starts would keep, and a second daemon starting at once keeps the first one's. A failure fails the start with EngineError::Memory.
    • [memory] bound. Each limit must be positive, and their sum at most 57344 bytes: the 64 KiB event bound less an 8 KiB reserve for the fixed text, headings, tags, and escaping. Escaping can lengthen a body (<memory becomes &lt;memory), so phase 3 must measure the agent section, too, on its rendered text and keep the reserve's promise.

    • Versions. Phase 1 had already made the client protocol 1.2.0, so memory_loaded makes it 1.3.0; the plugin protocol goes from 1.1.0 to 1.2.0 as section 12 says. History format is unchanged; the event is a state event, so a build that does not know it opens such a log render-only. No client/1.3.0 or plugin/1.2.0 corpus directory was recorded, as for 1.2.0.
    • Event shape. Every member is left out when empty or false, so an empty snapshot is the bare {"type": "memory_loaded"}. agent gains omitted (below). Writers refuse a snapshot that holds anything but its agent when delegated, anything at all when empty, blank names or descriptions, or more than 128 KiB of JSON: the 64 KiB bound is kept on the rendered text, and JSON escaping can lengthen text with many line breaks or quotes.
    • Byte accounting. Each user category and each machine memory is added only while the whole section, rendered as it would end with that entry the last one shown (the Not shown names and N more counts included), fits its limit; so the section that is kept was measured whole. The agent file is measured on its escaped description and body against max_file_bytes, the heading and tags coming out of the 8 KiB reserve; when escaping makes it longer, the file is left out with agent.omitted, rendered Not shown (too long): agent://<agent>.
    • Rendered text. Each fixed paragraph is one line; the spec's line breaks are wrapping. Empty: and Not shown (too long): are consecutive lines of one block. A body is shown without leading blank lines and trailing whitespace, and a body of only whitespace counts as empty. Machine index lines escape like bodies. A <machine> lists its attachments comma-separated and has no attachments attribute when there are none (the daemon's machine of a session with only global). Keywords of user categories and of the agent file are stored but not rendered.
    • Session machines. An attachment whose machine the daemon cannot name adds no machine. "The set of the session's machines changed" compares machine names: a new attachment on a machine already listed does not refresh the snapshot, which keeps naming the attachments it was taken with. A delegated snapshot has no machines and never refreshes for them. A change of delegated would refresh too, though a session never changes it.
    • Defaults. A key for a memory action with any runtime selector (memory_write@global) declares the action. The defaults are appended after the document's own rules in the frozen agent snapshot, so run_started and the permission views show them.
    • agent://self is substituted only for the exact pattern agent://self, in agent documents and session overlays alike, when matching; it then ranks like the literal URL.
    • memory_search declares no permission. It needs no rule of its own and is never approved as a whole; composition publishes it only with memory_read, and each hit is checked against the run's memory rules and session overlay for its URL. Matching body lines longer than 200 characters are cut and end with ….
    • Refusals before rules. A delegated run's write to anything but its own agent file, and a delete of a user:// or agent:// memory (superseded by section 16.6: such a delete now clears the body), are refused while the call is prepared, so no approval is asked for a call that cannot succeed. Creating a user:// file and creating an agent:// file for an unknown agent are refused by the store when the call runs.
    • Errors. Tool failures reach the model as failed tool results with the store's message (current revisions included); registry error codes belong to RPCs, so the memory.* codes come with phase 4.
    • Arguments. memory_write requires keywords and body (each may be empty). memory_read returns a url: and revision: header and the whole file text, and says when the file is invalid so the model can fix it with memory_write. Reads run in parallel; writes are exclusive.
    • A snapshot that cannot be read (a memory folder that fails to list) is reported on standard error and not recorded; the latest snapshot stays.
    • The TUI shows memory_loaded as a debug row only; the /memory panel is phase 4.

    16.6 Addendum 2026-10-21: agents clear what they cannot delete¶

    Decided 2026-10-21. A model's memory_delete of a user:// or agent:// memory is no longer refused. It supersedes the refusal of sections 4.1 and 8 and of the "Refusals before rules" note in section 16.3. machine:// and project:// deletes are unchanged: the file is removed, and a project goes with its last memory.

    • What a clear does. The body is removed; the frontmatter stays byte for byte as it was (YAML comments, quoting, and line endings included), and so does the file, so a user:// category or an agent:// file keeps existing. An empty body is valid (section 4.3), so the cleared file loads as a valid memory: listings show it with its description and keywords, the snapshot includes it with an empty body (a user category then renders in the Empty: line, an agent file as an empty element), and search still matches its keywords, name, and description.
    • Same rules as other writes. The call is a memory_write on the memory URL, so the permission rules and the delegated-write rule apply as before; the revision must be current, and a stale one is refused with the current revision. The clear runs under the memory lock, writes the file through a temporary file renamed over it, signals memory.changed, and returns the new revision. A file that is invalid is refused, as an edit is; the agent can fix it with memory_write first.
    • Results. A clear answers <url> cannot be deleted, so its content was cleared; its description and keywords stay. New revision: <revision>. A body that is already empty (no bytes after the closing --- line) is left alone, nothing is written or signalled, and the call answers <url> cannot be deleted, and its content is already empty, so nothing changed. Its revision is still <revision>.
    • Where it is. MemoryRoot::clear_body in memory/store.rs, which returns ClearedBody::Cleared or AlreadyEmpty with the revision, and MemoryDocument::frontmatter_len in memory/file.rs, which finds where the frontmatter ends in the file as written. The store's delete still refuses Origin::Model for these layers; the tool calls clear_body instead.
    • Unchanged. The client RPC memory.delete (/memory, the web page, cookie memory rm) still deletes any file, user:// and agent:// included, since it acts for the user. No protocol, schema, or history format changed; only the memory_delete tool's description and results did.

    16.7 Addendum 2026-10-21: the daemon keeps one memory file per agent¶

    Decided 2026-10-21. The daemon manages one memory file for each agent. This supersedes "the agent, by its first write" as the creator of agent files (section 4.1) and the No memory yet. line of section 7.4.

    • A file for every agent. At start, and after every runtime publication (configuration reload, config.apply, provider and catalog changes, which can add or remove the built-in default agent), the daemon makes sure agents/<id>.md exists for every agent ID of the shared registry and of every preset registry. Internal agents get none (section 4.1). A new file has an empty body.
    • The daemon owns the description. It is Memory of the `<id>` agent: <description>, from the agent document's description with every run of whitespace and control characters made one space, cut to 200 characters (the last one … when cut); Memory of the `<id>` agent when the document's is blank. An ID in the shared registry takes the shared document; one only in presets takes the alphabetically first preset's. A changed description rewrites the file's at the next sync.
    • Keywords. The daemon's two keywords are <id> and the mode (primary, subagent, or all), one when the ID is the mode's name. They come first; every other keyword a writer added is kept in order, except repeats and other mode names (compared case-insensitively), up to the 32 allowed. memory_write's keywords is now optional, as the file format always had it.
    • Writes keep what the daemon owns. memory_write and memory_edit on a managed agent:// file keep the daemon's description and keywords, in place of what the call gave; memory_write may leave description out for agent:// and says in its result what it kept when the call gave something else. An agent:// file the daemon does not manage (an orphan's, or an internal agent's) keeps the description it has.
    • The user's memory.write follows the same rule, at the write itself rather than at the next sync: deferring would let a description the user typed reach snapshots until a sync that may be days away. The frontmatter is replaced only when it differs, the body kept byte for byte, and MemoryWriteResult gains an optional notice saying what was kept (client protocol 1.6.0), which /memory and cookie memory edit show.
    • Empty memory stays out of the prompt. An agent file with an empty body (whitespace only counts as empty, as for user categories) renders no agent section at all. The memory_loaded event still carries the agent and its empty memory, so section 7.2 is unchanged: a snapshot whose agent memory is empty is kept like any other, and a first body the agent writes shows from the next refresh (a compaction, a new session, and the rest of section 7.2), like every other write.
    • Removal. When an agent leaves every registry, its file is deleted only when the daemon made it and nobody touched it, with no marker on disk: the body is empty, the description starts Memory of the `<id>` agent, the keywords are exactly the daemon's two for some mode, and the bytes are exactly what the daemon writes. Any other file stays and is orphaned, as before.
    • Concurrency. A sync takes the memory lock, reads the registries published at that moment (so of two racing syncs the later state wins), writes each file through a temporary file renamed over it, and signals memory.changed only when it changed something; with nothing to do it writes nothing. It skips a file that is invalid or not a regular file, and a rewrite that would pass [memory] max_file_bytes. While the memory folder does not exist it does nothing, so the next start's first start (section 4.5) still runs. A config.apply or reload awaits a sync before it answers; other publications sync in the background. A run admitted while a sync is pending snapshots the files as they are: a missing file and an empty one render alike, so only a description change can be one snapshot late. Renaming over an existing file replaces it atomically on Windows as on Unix, and the daemon's own readers open files with delete sharing, so a sync does not fail for one of them; an editor holding the file open without that sharing can make one sync fail, which is reported on standard error and retried at the next sync.
    • Where it is. crate::memory::agents (AgentMemorySpec, AgentMemory, MemoryRoot::sync_agents) and crates/engine/src/runtime/agent_memory.rs (desired_agent_memory, Engine::agent_memory, and the sync at start and after publications).
    • Deviation: replay of older logs. The rendered text depends on the event alone, but the agent-section rule changed without a history format change. A log written before this build renders its latest snapshot by the new rule: a No memory yet. line, or an empty agent element, is no longer shown. That costs a session one prompt-cache miss at its next run, and a replay of such a log does not show that line. Keeping the old text for old events would need a new event member that every snapshot carries, which this change did not take on.

    Approved 2026-10-21, and queued as the first step of phase 1 of delegating to runtimes.

    Until now a runtime's machine came only from a pin or from what the runtime reported while connected (section 3.2). An ssh template that had connected before therefore fell back to "on no machine yet" as soon as it disconnected. Its badges, its ~/… paths, and its place in the Machines view were all lost while it was offline.

    • What is remembered. When a runtime connects, machines.json records under its runtime ID:
    • the machine ID it reported;
    • its platform and its home directory;
    • when it was last seen.

    The record is rewritten whenever a reconnect reports something different. Writes go through the same lock as every registry change. The registry format version goes up by one, and an older file reads with no records. - Placement. A runtime's machine is decided in this order: 1. its pin; 2. the machine its live report resolves to; 3. the machine its record resolves to, as a new reason, "last seen".

    A disconnected runtime with a record stays on that machine, shown as offline. "On no machine yet" is left for runtimes that have never connected. Merging or renaming machines moves remembered runtimes as it moves connected ones, because records hold machine IDs, not names. - What clients see. - runtimes.list gives a disconnected runtime with a record its remembered machine, platform and home, with connected: false. - machines.list lists remembered runtimes beside connected ones, each with its last-seen time. - list_runtimes places them under their machine the same way. - Forgetting. - A new machines.forget_runtime drops one runtime's record. The web Machines view offers it on offline runtimes as "Forget". - Removing an ssh template from config.toml drops its record at the next config reload. - Dial-in runtimes, which have no config, keep their record until forgotten. - machines.forget on a machine still refuses while the machine has connected runtimes or memories. Remembered offline runtimes don't block it; their records are dropped with it. - Machines view. Each machine card lists its offline runtimes under the connected ones, dimmed, with "last seen …". Dragging an offline runtime onto another machine pins it there, as for any runtime. - Protocol. This is an additive client protocol minor: - the "last seen" assignment reason; - remembered runtimes and their last-seen times in machines.list; - machines.forget_runtime.

    Older clients see what they see today.

    Implemented 2026-10-21 (client protocol 1.10.0), as the first step of phase 1 of delegating to runtimes:

    • The file. machines.json version 2 adds remembered, one record per runtime ID: { runtime, kind, machine_id?, platform?, home?, last_seen }, where kind is spawned or dial_in. Version 1 reads with no records and is written as version 2 on the next change; the records are as strict as the rest of the file. Built-in runtimes get no record.
    • When it is written. The daemon notices connections and disconnections as it places runtimes after every runtime registry change. A runtime that connects, or reconnects with a different report, gets its record with last_seen now; one that goes offline gets last_seen stamped now. A runtime still connected when the daemon stops keeps the time it connected, and the whole set of records is written only when one changes.
    • Placement. An offline runtime is placed by its pin, else by the machine ID this process last saw it report, else by its record, with the reason last_seen. machines.list gives each machine its remembered runtimes (RememberedRuntime { runtime_id, assigned_by, platform?, home?, last_seen }); a remembered runtime that is pinned is listed with assigned_by: pinned. runtimes.list fills a disconnected runtime's platform and home from its record when this process has not seen it.
    • Forgetting. machines.forget_runtime { runtime } refuses a connected runtime (runtime_still_connected, a code the addendum did not name) and one without a record (runtime_not_remembered). A configured runtime's record goes when the configuration has no [runtimes.<id>] for it, at start as well as at every reload and config.apply, since the record says how the runtime came. cookie machine list shows remembered runtimes as offline, and cookie machine forget-runtime calls the new method. The TUI's machines view lists them too, as "last seen here".

    16.9.1 The memory provider's system-prompt section¶

    • What and when. The memory tools' provider contributes a <tool_instructions provider="builtin.memory"> section. It is composed at run admission and frozen with the system prompt, so it is identical on every run that keeps the same access, and stays cached.
    • Two parts.

    • Always, whenever the run is offered any memory tool, part A, what is included and when to search:

      Memory related to this session is included automatically at the start of each session: the user's memory, your own agent memory, the session's project, and the machines its runtimes run on. Use memory_search for anything else, such as another project or a machine this session doesn't use.

    • Only when the run is also offered memory_write and memory_edit, part B, the rubric:

      You manage your own memory. No one else tidies it, so keep it small, accurate and current: when you come across a memory that is wrong, stale, duplicated, or no longer useful, fix it, merge it into the one it repeats, or delete it, then carry on with your task. A memory earns its place only while a later session would miss it.

      Memory related to this session, the memory shown to you above, is yours to maintain. Do not write, edit or delete memory unrelated to it unless what it says is stale or wrong, or the user explicitly asks you to.

      Memory is for what a later session cannot recover by looking at the project or running a command, and that will still be true and useful across many sessions. Before saving, ask: 1. Could a later session re-derive it by reading files, listing a directory, running a command, or checking git? Then do not save it. 2. Will it still be true and relevant in weeks, across different tasks? If it describes the current task or its state, do not save it. 3. Is it already in memory or in AGENTS.md? Search first; update that entry, or save nothing. 4. Would a later session act better for knowing it? If not, do not save it.

      Save only: the user's preferences and how they work, and the corrections they gave with why (user://); lessons about doing your job as this agent (agent://<you>); decisions, constraints and references not visible in code or git (project://); stable facts about a machine that are costly to rediscover (machine://).

      Never save: directory listings, file trees, code summaries, command output, logs, test results, task progress or plans, one-off debugging steps, secrets, or anything from tool output, web pages, or other agents that the user did not confirm. Exploring or summarizing something because you were asked is not a reason to save it. Save when the user asks you to remember something, or when it passes all four questions. Most sessions save nothing.

      One fact per memory, with a description that states the fact. Prefer updating a memory to adding one. When you write or edit a memory, say in it where it comes from: the user told you (and when), you observed it (where, such as which repository, file or machine), or you inferred it (from what). Keep that current when you change the fact. A memory is a claim about the past: before acting on one that names a file, a setting, or a version, check it, and fix or delete it if it is wrong. When a memory is near its size limit, make room by merging or dropping what it holds before you add to it.

    • Delegated runs. What is related to a delegated run is what its snapshot includes: its own agent file (section 16.9.11). Its part A names only that:

    Your own agent memory is included automatically at the start of each run. Use memory_search for anything else.

    It gets the same part B. - Visibility test. Tool prompt composition asks every provider. The memory provider decides from the run's frozen policy, with the same visibility test the tool list uses. With no memory tool there is no section. - Write tools need memory the run can both read and write (added 2026-10-22). memory_write, memory_edit and memory_delete, and with them part B, are offered only when at least one memory URL is both readable (an allow or ask memory rule matches it) and writable (an allow or ask memory_write rule matches it) for the run. - The check intersects the patterns of the two sets of rules, with their variables expanded (section 16.9.9). Patterns use only * and ?, so whether two of them overlap can be decided exactly, and no file has to exist for a URL to count. - Examples: - memory: {"user://*": allow} with memory_write: {"project://*": allow} offers no write tools. - Without memory, when the run is offered no memory tool at all, the write tools never appear (unchanged). - What the snapshot keeps. It loses its search and save paragraphs ("Project notes are never shown here…", "Save what a later session should know…", and their variants), and keeps only its background line and the memories themselves. - Tool descriptions. memory_write and memory_edit stay short and point to the section.

    16.9.3 Search matches descriptions, keywords and URLs, never bodies¶

    This replaces section 8.1's scoring.

    • Terms. The query is split on whitespace. A memory is matched against its keywords, its description, and the segments of its URL, split on :// and /:
    URL Segments
    user://preferences user, preferences
    agent://reviewer agent, reviewer
    project://cookie-agent/release project, cookie-agent, release
    machine://labpc/cuda machine, labpc, cuda
    • Bodies are never searched.
    • Scoring. A memory's score is, in order of weight:
    • each keyword that occurs in the query;
    • each query term that occurs in its description or one of its URL segments.

    Matching is case-insensitive, memories that score zero are left out, and ties go to the more recently modified memory.

<body>
    • No owner label (decided 2026-10-22): the URL already says whose memory it is (user://, agent://<id>, machine://<name>/…, project://<name>/…), and related says whether it belongs to this session. Everything the snapshot shows is related by definition.

    16.9.5 Similar memories before a new one¶

    • When it applies. A memory_write that creates a memory, rather than replacing an existing URL, is first compared with the memories in the same place: the same project, the same machine, the user categories, or the agent's file.
    • How memories are compared. The comparison uses the new memory's description and keywords, lowercased, with filler words left out. It reuses section 16.9.3's matching, with no embeddings and no model call.
    • A strong match refuses the write. A match is strong when the memories share two or more keywords, or when most of the new description's words occur in an existing description. The result lists up to three near memories with their URLs and descriptions. Writing again with new: true and a one-line reason creates it anyway.
    • A weaker match saves the memory. The result lists the near memories, with "if one of these already covers it, edit that and delete this".
    • A body identical to an existing one is always refused.

    16.9.6 Stamps¶

    • Fields. Each memory document's frontmatter gains created and modified, which the daemon sets. Whatever a write sends for them is ignored.
    • Last read. The daemon also keeps when each memory was last read, outside the file.
    • Ages show in the snapshot, in search hits and in reads.
    • Old files. A file without stamps gets created and modified from its modification time the first time the daemon reads it.

    16.9.7 Size limits per document¶

    • The limits. Each memory document is at most 2 KB by default, with one setting per kind under [memory]:
    • user_max_bytes, for each user category;
    • agent_max_bytes, for each agent file;
    • machine_max_bytes;
    • project_max_bytes;
    • overview_max_bytes, for each project overview.

    These replace max_file_bytes, which becomes an unknown key under the strict configuration rules. snapshot_user_bytes and snapshot_index_bytes keep bounding the snapshot as before. - Writes over a limit. A write or edit that would leave a document over its limit is refused, and the result shows the document's current content and asks for it to be condensed first. - Fullness in the snapshot. Each document the snapshot shows in full carries modified, size and max_size attributes, for example:

    <memory url="user://feedback" description="…" modified="3 weeks ago" size="1.4 KB" max_size="2 KB">

    Index lines (machine and project memories) end with their age, as in (3 weeks old). - Documents already over their limit are still shown, marked over its limit. Only writes that make them smaller are accepted until they fit.

    16.9.8 Writes without revisions¶

    • revision is removed from memory_read's output and from the arguments of memory_edit and memory_write.
    • memory_edit applies when its old text occurs exactly once in the memory's current body. This already refuses an edit that someone else's change conflicts with, and lets one that does not conflict apply on top of it.
    • A memory_write that replaces an existing memory is accepted only when this session saw that memory's current content: through memory_read, the snapshot, or a write of its own. The daemon remembers the revision each session last saw, out of the model's sight. Otherwise the write is refused, with the current content and "this memory changed since you saw it, or you have not read it: read it first, or edit it". This keeps a whole-memory write from silently dropping a change the user or another session made, and from overwriting a memory the agent did not know existed.

    16.9.9 Relative names in memory rules¶

    • Variables. Memory rule patterns accept three variables, spelled like ${workspace_dir} in path patterns:
    Variable Means Example
    ${agent_id} the run's agent agent://${agent_id}
    ${session_machine} each machine the session's attachments run on machine://${session_machine}/*
    ${session_project} the session's project project://${session_project}/*
    • Whole segments only. A variable must be a whole URL segment; project://${session_project}-old/* is refused when the agent document loads.
    • Where they are valid. They are valid only in memory and memory_write patterns. An unknown variable is a load error.
    • Expansion. Variables are expanded at each check:
    • ${session_machine} matches if any of the session's machines does;
    • ${session_project} matches nothing in a session without a project;
    • a session that gains an attachment or moves to a project is covered at once.
    • agent://self is removed in favour of agent://${agent_id}.

    16.9.10 Every change is visible¶

    • The tool row is the record (revised 2026-10-24). Each write, edit or delete a model makes is its memory tool call's one row: expanded, it shows the change as a diff built as the coding runtime's edit and write build theirs (five lines of context, without the stamp lines), and the memory's URL in its header links to the Memory view in the web client and the TUI. A write, edit or delete previews its diff before it runs, so an approval shows it too.
    • Before 2026-10-24 each change was also a one-line transcript event, memory_changed, such as Saved project://cookie-agent/release, which drew a second row under the call. The memory tools no longer record it; clients fold one an older log holds into the call it directly follows (the running call naming its URL, or the call of the same run terminated just before it), and draw it as its own line only when it follows none. The event is queued for removal at the next major (compatibility spec section 3.4).
    • No undo, no trash (decided 2026-10-22). A delete deletes and a replaced body is gone, as with any file.

    16.9.11 Related memory, and no hard limits on what an agent touches¶

    Decided 2026-10-22.

    • Related memory. The memory a session's snapshot includes automatically is related to the session:
    • for a root run: every user:// memory, the run's own agent://<agent> file, the memories of the session's machines, and those of its project;
    • for a delegated run: its own agent file, the only memory its snapshot includes.

    This is the word the prompt, the results (related or unrelated) and the rules below use. It is deliberately not "attached", which names a session's runtime attachments and delegation's capabilities. - No hard limits. Permission rules alone decide what an agent may write, edit or delete; the rubric (section 16.9.1, part B) says what it should. Three rules the daemon enforces today, whatever the rules say, are dropped: - a delegated run may write only its own agent:// file; - an agent may change user:// categories but not add or remove one; - an agent's delete of a user:// category or an agent:// file only clears its body (section 16.6, superseded).

    An agent's delete now deletes, and nothing is kept (section 16.9.10). - Default for delegated runs (decided 2026-10-22). A delegated run (depth 1 or more) whose agent document has no key for memory or for memory_write gets this rule for that action:

    memory:
  "agent://${agent_id}": allow
memory_write:
  "agent://${agent_id}": allow
    • What it means. A subagent sees and maintains its own agent file and nothing else: no user:// memory, and no machine or project memory. This follows Claude Code, whose subagents never load the main session's auto memory and get only a memory directory of their own. The snapshot of a delegated run already holds only its own agent file (section 6), so the default and the snapshot agree.
    • Chosen by depth, not mode. Permission defaults so far depend on the agent's mode. This one depends on whether the run is delegated, so an all-mode agent gets it when delegated and the root default below when it runs as the root.
    • How a run is known to be delegated. Its session's origin is SessionOrigin::Delegated, set when delegate_subagent creates the session and never changed. The two policy freezes already differ (freeze_delegated_agent_policy for delegated runs), so the freeze passes delegated to agent_permission_rules, which appends these rules for a memory action the document has no key for. The default is part of the frozen policy, like the mode defaults; nothing checks it at write time.
    • A document's own rules replace it, per action, as with every default (section 9.2). An agent document that declares memory or memory_write gets exactly those rules when delegated too, user:// included if it grants it. That is the explicit opt-in; there is no hard limit behind it.
    • Session overlays apply on top as for any action.
    • Default for root runs (decided 2026-10-22, the user's decision). A root run (its session's origin is SessionOrigin::Root) of an agent that is not internal, the built-in default agent included, whose agent document has no key for memory or for memory_write gets these rules for that action: read everything, write what is related. The relative names express it with no new variable:
    memory: allow            # "*": allow
memory_write:
  "user://*": allow
  "agent://${agent_id}": allow
  "machine://${session_machine}/*": allow
  "project://${session_project}/*": allow
    • What it means. A root run sees its related memory in its snapshot, can find and read any other memory with memory_search and memory_read, and maintains its related memory (the write tools are offered, section 16.9.1). Another project's or machine's memory stays read-only to it. A session without a project, or with no machine, drops the rule that names it (section 16.9.9), so such a run writes user:// and its own agent file only.
    • A document's own rules replace it, per action, as with every default: memory_write: deny leaves a run that reads, and memory: deny turns memory off, since the write tools need some memory the run can read.
    • Internal agents get no memory default, root or delegated; they have no memory (section 6).
    • Delegated runs keep their own default above.

    16.9.12 The approval reviewer knows the rubric¶

    When an agent's memory_write rule is ask, the approval reviewer receives part B of section 16.9.1 and the write's content. In auto-approve mode it rejects writes that fail the rubric.

Variables are checked when an agent document loads (cookie_agent_config::agent_document::permission_expressions_valid), and WildcardPattern::new accepts them (WildcardPattern::MEMORY_VARIABLES).

MemoryDocument carries the stamps (with_stamps, created, modified).

    • Reviewer (crates/engine/src/runtime/approval_flow.rs): with_memory_rubric, for any request that checks memory_write.
    • Events: EventPayload::MemoryChanged { change, url } with MemoryChangeKind, appended by Engine::record_memory_change.

    Deviations and details decided:

    • Variables are expanded when a run's policy is frozen, not at each check. The frozen rules reach the wire (run_started, session_created, the permission views), and the protocol's WildcardPattern schema has no room for the variables without a major bump, so frozen rules hold none. Each run freezes its policy at admission, so a session that gains an attachment or moves to a project is covered from its next run, as its snapshot, tools, and prompt are. ${session_machine} makes one rule per machine; a variable that stands for nothing (no project, no machine) drops its rule, since it would match no memory. A delegated child's creation snapshot takes its parent's machines and project; its runs freeze their own. Previews and new sessions freeze with no machine or project.
    • Variables in session rules are refused (check_rule_selectors, also for set_session_permission): the addendum names agent documents, and overlays reach the wire unexpanded. agent://self is now a plain pattern, and self is no longer a reserved agent ID.
    • The write-tools check ignores deny rules, as section 16.9.1 reads: it intersects the allow and ask patterns only.
    • revision stays in the client RPCs. The addendum's compatibility section makes the client change additive, so memory.read, memory.write, and memory.delete keep their revisions; only the tools lose them. memory_delete loses its revision too, since memory_read no longer shows one, and deletes without a seen check.
    • Seen revisions are kept in memory only. After a restart a session reads a memory again before replacing it whole. A snapshot counts as seeing every memory it carries whole, an agent file with an empty body included.
    • Reads add description: and keywords: lines (the latter only when there are any) after the spec's six, so a model can replace a memory faithfully; an over-limit memory's size line ends , over its limit. An invalid file's read keeps its reason and shows its raw text.
    • Search hits say editable when the memory_write rules allow or ask for the URL. Ages use the largest whole unit (minutes to years: 7 days a week, 30 a month, 365 a year), less than a minute below that; sizes are bytes below 1024, else KB of 1024 with one decimal.
    • Stamps are RFC 3339 UTC timestamps to the second. Every write, edit, and the user's memory.write re-renders the frontmatter with the daemon's stamps (YAML comments or quoting in the frontmatter do not survive; the body is kept byte for byte). The daemon's own frontmatter rewrites (agent descriptions, overview descriptions) keep the stamps, and its new files (agent files, overviews, the first start's categories) are stamped now. Migration runs once at start: stamp_unstamped adds only the missing lines before the closing ---; until then reads use the file's modification time.
    • Last read is kept in memory/.reads.json (a URL to time map, written without the lock, advisory), updated by a model's memory_read and by a snapshot for what it shows whole; memory.list reports it as last_read. Moved or deleted memories keep their entries.
    • Limits. The size counted is the whole file. A file larger than 57344 bytes (MemoryConfig::MAX_LIMITS_SUM, which each document limit may not exceed) is invalid; anything smaller is valid whatever its kind's limit. The user's memory.write keeps to the limits too (memory_refused). A memory over its limit accepts a change that leaves it strictly smaller. The configuration sum is agent_max_bytes + snapshot_user_bytes + snapshot_index_bytes; the snapshot shows the agent's file while its escaped text fits what the two snapshot limits leave of that sum, so an agent file somewhat over its limit still shows.
    • Over-limit marks: a whole memory gets status="over its limit" after max_size; an index line's parenthesis reads (<age> old, over its limit). Index entries carry the status members too.
    • Old snapshots. A snapshot without taken_at was taken by an earlier daemon, so a run takes a new one. The trimmed text renders for old events too (no search or save paragraphs, no status attributes), so a replay of an older log does not show those paragraphs; since such a snapshot is replaced at the session's next run, no model sees the mix.
    • Similar memories compare within the same place only, identical bodies included; blank bodies are never compared. Words are split on anything but letters, digits, and -, lowercased, with a fixed list of 48 filler words left out. A strong match lists up to three memories, ranked by shared keywords, then shared words; a weak one (any shared keyword or word) lists them in the result. reason must be one line of 1 to 200 characters and only goes with new: true; it is not stored.
    • Change events are audit events, appended during the tool call with its run. A client's changes record none. The client state reducer shows one as an info line, Saved <url>; linking to the Memory view is the clients phase.
    • Reviewer text: a <memory_rubric> block between the prior decisions and the tool call, opening with "The tool call changes memory. The agent was told to keep memory by this rubric; deny a change that fails it.", for memory_write, memory_edit, and memory_delete alike.
    • Project line: with no attachment besides global, the block is the Project: line alone; with one attachment it follows Machine:.
    • Versions. Client protocol 1.14.0 and plugin protocol 1.6.0; the runtime protocol and history format 1 are unchanged. No client/1.14.0 or plugin/1.6.0 corpus directory was recorded, as for the earlier memory minors.
    • Editors see the stamps. memory.read returns the file with its created and modified lines, so /memory, the web page, and cookie memory edit open them in the editor; whatever the user leaves there is replaced by the daemon's stamps on save. Hiding them is for the clients phase.
    • Tests. One compaction test's agent lost write access so its small history still compacts under the longer system prompt. The future plugin corpus's expected handshake answer names plugin protocol 1.6.0, as it has named each earlier minor.

    16.10 Addendum 2026-10-25: the memory tools follow the file tools¶

    The memory tools and the coding runtime's file tools were aligned where nothing argues for a difference (Memory tools):

    • memory_read takes offset and limit with read's semantics: the body's lines are numbered from 1 (N: text) under the metadata header, offset is the 1-based body line to start at (default 1), limit the most lines (default 2000), with read's 4 KiB line cut, page cap, continuation marker, and error for an offset past the last line. Its result shows as a file_excerpt in markdown.
    • memory_edit takes oldString and newString in place of old and new (section 8 and 16.9.8). Preparation checks that oldString occurs exactly once in the body, so no approval is asked for an edit that cannot apply; the edit checks again when it runs. It still matches the body only and has no replaceAll.
    • Wording shared with write and edit: Created <url> (N bytes)., Replaced <url> (N bytes)., Edited <url>: 1 replacement., <url> does not exist, and one error for zero and several occurrences that echoes oldString cut to 200 characters. Results are titled Read, Wrote, Edited, and Deleted <url>.
    • Error kinds: the refusal of a replacing write that has not seen the memory as it is now is operation_changed, and a bad memory URL invalid_url.

    Kept different on purpose: the read-before-replace rule and the description, keywords, new, and reason fields; deletes are final; the permission actions memory and memory_write by URL; the write tools run one at a time; and memory_search has no file counterpart.
